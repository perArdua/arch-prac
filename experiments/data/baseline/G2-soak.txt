5. 🔴 QA를 실제 read path로 — 설정 3가지를 자동으로 비교
------------------------------------------------------------------------------
  각 설정마다 DB를 새로 만들고 720턴을 다시 넣는다.
  근거가 필요한 문항만 센다 (abstention·coverage 8개 제외).

  설정                               근거도달     검색기여     트랩    p50토큰
  --------------------------------------------------------------
  A. 검색만 (원래 구현)             4/18 =  22%       4      없음      490
  B. + [알고 있는 것] 전량          10/18 =  56%       0     주입됨      799
  C. + 상시성(standing) 필터      9/18 =  50%       0      없음      689
  D. + 실험 12 (θ·게이트)         10/18 =  56%       1      없음      711

  읽는 법 — 각 줄이 다른 것을 말한다.
  A->B  docs/15에서 [알고 있는 것] / [꺼낼 만한 것]으로 나눠 설계해놓고,
        build_context는 [꺼낼 만한 것]만 구현했다. facts_at()은
        fact_demo에서만 불렸고 읽기 경로에 연결된 적이 없다.
        10줄 추가로 회상 22% -> 56%. 토큰은 490 -> 799.
  B     그런데 트랩(크로와상 importance 0.05)이 평범한 턴에도 들어간다.
        검색 경로에는 하드 게이트 τ가 있는데 **결정적 주입 경로에는
        채택 기준이 아예 없었다.** 게이트를 우회하는 길을 뚫은 것이다.
  B->C  importance로 거르면 될 것 같지만 틀렸다. 필요한 축은
        '중요한가'가 아니라 '항상 알고 있어야 하는 종류인가'다.
        술어에 다섯 번째 속성 standing을 추가했다. 트랩이 빠지고
        토큰도 799 -> 689. 회상 1건 손실은
        일상_사소 술어 문항이고, 그건 검색이 맡아야 할 몫이다.
  C->D  [실험 12](gate_sweep.py)가 θ(0.15->0.05)와 게이트(과거참조->내용어 접점)를
        **함께** 바꿨다. 회상 50% -> 56%,  검색 기여 0 -> 1.
        하나씩 바꾸면 둘 다 효과가 0이다 — 두 방어선이 직렬이라서다.

  ⚠️ 검색 기여: A에서 4건 -> B·C에서 0·0건.
     검색이 찾아내던 것을 결정적 주입이 전부 포함해버렸다.
     아키텍처 복잡도의 대부분(BM25/dense/hybrid·importance 가중·θ·top-k)이
     C 구성에서 그 경로의 **순증 기여는 0건**이었다.
     다만 D에서 1건으로 돌아온다 — **검색이 무능했던 게 아니라**
     **임계값이 정답을 깔고 앉아 있었다**(실험 12). 순증 0은 파라미터의 결과였다.
     시뮬레이션은 검색기를 격리해서 쟀기 때문에 이걸 볼 수 없었다.
