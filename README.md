# 캐릭터 챗 장기기억 설계 검토

캐릭터와 오래 대화해도 중요한 사건과 맥락을 정확히 기억하면서, 비용과 응답 지연은 줄일 수 있는지를 검토한 저장소입니다. 설계 문서와 결정 기록(ADR), 추천 구조를 구현한 프로토타입, 그 구조를 검증한 실험 코드와 결과 기록이 들어 있습니다.

> **현행 = 기준선.** 문서와 코드에서 «현행»(`G1`)은 특정 서비스가 아니라, 흔히 쓰는 계층형 메모리 + 검색 + 선별 구조를 재현한 기준선을 뜻합니다. 장기 요약, 대화 원문에서 관련도 상위 5개, 최근 10턴을 넣습니다.

## 무엇을 만들었나

- **프로토타입**(`prototype/`): 늘 참인 사실과 관계 상태는 검색하지 않고 매 턴 넣고, 특정 시점에만 참인 사건은 필요한 턴에만 중요도와 관련도 두 기준으로 걸러 꺼내는 기억 계층입니다. SQLite 한 파일로 돌아가며 관계 상태 FSM, 사실의 유효기간과 삭제 전파, 세션 요약 층을 포함합니다. 응답 생성 루프와 추출기는 없습니다.
- **평가 데이터**(`eval/`, `eval2/`, `eval3/`): 정답을 먼저 정하고 대화를 만든 합성 대화입니다. 연애 도메인 720턴, 업무 도메인, 3,000행 규모 코퍼스 세 벌이 있습니다.
- **실험**(`experiments/`): 실험 34개 중 28개는 키 없이 로컬에서 돌아가고, 6개는 Gemini 무료 티어로 돌렸으며 그 결과 기록이 `experiments/data/`에 있습니다. 판정 규칙은 가능한 한 값을 보기 전에 적어 두었습니다.
- **검사 도구**: 문서가 인용한 코드 줄이 실제 코드와 맞는지, 문서 사이 숫자가 같은지, 평가용 상수가 코드에 박혀 있지 않은지 확인하는 감사 스크립트입니다.

## 실행과 테스트

Python 3.13에서 확인했습니다. 대부분 표준 라이브러리만 쓰고, 시험과 일부 실험에 `pyyaml`이 필요합니다(몇몇 시뮬레이션은 `numpy`). 명령은 저장소 루트에서 실행합니다.

```bash
# 단위 시험
PYTHONIOENCODING=utf-8 python -B -m unittest discover -s prototype/tests -p "test_*.py"
PYTHONIOENCODING=utf-8 python -B -m unittest discover -s experiments/tests -p "test_*.py"

# 데모와 720턴 소크 테스트
python prototype/demos/demo.py
python prototype/soak.py

# 전체 실험 재실행 (약 15분, 결과는 experiments/data/RESULTS.txt)
PYTHONIOENCODING=utf-8 python -B experiments/run_all.py
```

- 로컬 모델 서버(ollama)나 검색 엔진 컨테이너가 없으면 해당 단계는 종료 코드 77로 건너뜁니다. 건너뜀은 통과로 세지 않고 따로 셉니다.
- `run_all.py` 아래에서는 기록된 모델 판과 실행 환경의 판이 다르면 새로 생성하지 않고 그 단계를 77로 끝냅니다(`MEMARCH_FORBID_REGEN`). 기록된 생성물을 덮어쓰지 않기 위해서입니다.
- 실제 모델로 요약을 만드는 시험은 `MEMARCH_REAL_GEN=1`일 때만 돕니다.
- 검색 엔진 비교(실험 32)에 쓰는 컨테이너 준비는 `experiments/engine_infra/README.md`에 있습니다.

## 결론

추천 구조를 한 줄로 적으면, 늘 참인 것은 검색하지 않고 매 턴 넣고, 특정 시점에만 참인 것은 필요한 턴에만 두 기준으로 걸러 꺼내며, 두 블록을 캐시가 깨지지 않는 순서로 배치하는 것입니다. 근거의 강도에 따라 세 칸으로 나눴습니다.

### 지금 판단할 수 있는 것

- 관계 상태 FSM은 규칙에 어긋난 상태 변경 20종을 모두 막았습니다(20/20 차단, 코드 경로라 결정적입니다).
- 사실에 유효기간을 붙이고 파생물까지 무효화하자 옛 직업이 주입되던 턴이 23턴 → 0턴이 됐습니다.
- 사실은 요약에 맡기지 않습니다. 심어 둔 사실 11개 중 세션 요약 뒤에는 10개가 남았지만 전체 기간 요약 뒤에는 1개만 남았습니다.
- 게이트는 회상을 떨어뜨리지 않고 검색 호출을 줄입니다. 게이트가 없을 때와 18문항 중 10문항으로 같았습니다.
- SQLite 한 파일과 어휘 검색으로 지연 예산 안에 듭니다. 720턴 컨텍스트 조립 p95는 6.3ms, 3,000행 첫 조회 p95는 약 20ms였습니다.
- 관련도 기준을 최종 점수에 거는 스위치는 현행 조합에서 «켬 나음» 0/5열이라 지금 조건에서는 켜지 않습니다. 기각이 아니라 이 조건에서 쓰지 않는다는 판단입니다.
- 기억은 있어야 합니다. 응답 품질 26문항에서 기억 없음 12%, 제안안 73%였습니다.

### 추가 검증이 필요한 것

- 상시 사실 블록을 연결해 근거 도달이 22%에서 56%로 올랐지만, 정답지를 그대로 넣은 이상적 추출 조건입니다. 추출기를 붙여 다시 재야 합니다.
- 캐시 배치로 입력 비용 63%를 줄인다는 값은 캐시 적중을 시뮬레이션한 결과입니다. 실제 과금 호출로 캐시 토큰을 세야 합니다.
- 관련도 기준 0.05와 중요도 기준 0.2는 짧은 합성 질문에서 정한 값입니다. 관련도 기준을 지금 위치에 두면 21행 코퍼스에서는 정렬 가중치를 바꿔도 주입 집합이 바뀌지 않았지만(가중치 축 False 0/36 · True 18/36), 3,000행 규모에서는 스위치를 끈 채로도 가중치 축이 움직였습니다.
- 세션 요약 24개 보관은 평가 대화 길이에 맞춘 값이고, 그보다 긴 대화로 생성해 본 적이 없습니다.

### 판단을 보류한 것

- 제안안이 현행보다 낫다는 주장입니다. 가중 회상은 96%로 같았고, 제안안이 앞선 정밀도(38% 대 22%)는 시뮬레이션 10문항 한 조건입니다.
- 잘못 넣은 기억이 못 찾은 기억보다 비싸다는 전제입니다. 측정한 적이 없고, 실사용 로그의 재방문율 같은 데이터가 있어야 가릴 수 있습니다.
- 임베딩 검색을 기본으로 끄는 선택입니다. 의역 질문에서는 임베딩이 나았지만(2/8 대 6/8), 어휘 검색 쪽 근거는 서버를 하나 더 두는 운영 비용뿐이라 수치로 비교하지 못했습니다.
- 상위 5개라는 값입니다. 문항마다 정답 근거가 하나라 이 데이터로는 어떤 값도 정할 수 없습니다.
- 기억 선택을 LLM에게 맡기지 않는 선택입니다. 나란히 잰 적이 없고, LLM 선택에 드는 지연 200~800ms도 추정입니다.

자세한 근거와 확인 방법은 [docs/10](docs/10-final-recommendation.md), [docs/11](docs/11-experiment-results.md), [docs/17](docs/17-gap-disposition.md)에 있습니다.
