# 평가 자산 — 설계와 사용법

> 근거: [ADR-009](../docs/adr/ADR-009-evaluation-design.md), [07 A5·A6](../docs/07-assumptions-audit.md), [09 §7](../docs/09-what-memory-is-for.md)

---

## 1. 왜 역방향 생성인가

대화를 먼저 만들고 정답을 나중에 라벨링하면 부정확해진다. 무엇이 어디에 있는지 사후에 찾아야 하고, 애매한 경우가 대량으로 생긴다.

**그래서 순서를 뒤집는다.**

```
1. fact-ledger.yaml 작성    ← 무엇이 언제 등장하고 언제 무효화되는지 먼저 확정
2. 대화 생성                 ← "F001을 S03 12턴에서 자연스럽게 언급하는 대화를 써라"
3. questions.yaml 파생       ← 대장 ID를 참조하므로 gold answer가 자동으로 정확
```

이렇게 하면 **근거 위치가 정확히 알려진 데이터**가 나오고, 그게 `A1 Oracle` arm과 유형별 채점을 가능하게 한다.

## 2. 무엇을 심었고 왜 심었나

각 항목은 **막고 싶은 실패**에 대응한다. 이유 없는 항목은 넣지 않았다.

| 심은 것 | 재현하려는 실패 | 출처 |
|---|---|---|
| **F007_TRAP** (크로와상 + "아쉽다") | «빵 유언» — 사소한 기억이 감정 어휘 때문에 끌려옴 | 유사 서비스 A 후기 |
| F002 → F021 (직업 갱신) | 갱신된 사실의 구 버전 재생 (stale fact) | 지식 갱신 |
| `never_mentioned` 4종 | 없던 일을 지어냄 (hallucination) | abstention |
| `coverage_plan` (S01-10 요약만) | *"그런 적 없다"*와 *"기억이 흐릿하다"*를 구별 못 함 | 커버리지 메타 |
| D004_UNPAID (회수 안 되는 복선) | LLM이 체호프의 총을 발사하지 않음 | CFPG 논문 |
| I001 (3회 반복 패턴) | 사실은 외우지만 **해석**은 못 만듦 | PPR 이해 축 |
| `relationship_arc` (다툼→화해) | 상태를 검색에 맡겨서 생기는 위반 | 유사 서비스 A stale fact |
| `speech_rules` + 호칭 변경 | 페르소나 붕괴 (범용 어시스턴트처럼 무너짐) | 유사 서비스 C |
| present_characters (S19) | 제3자 난입 | 유사 서비스 A U6 |
| **노이즈 65%** | 검색 난이도 확보 — 대장에 없는 잡담 | — |

**F007_TRAP과 I001이 이 코퍼스의 핵심이다.**
- F007_TRAP: `importance` 가중이 실제로 작동하는지 재는 유일한 장치. relevance만으로 정렬하면 반드시 걸려든다
- I001: [실험 D10](../docs/06-data-model.md#8-이-데이터-모델이-만드는-실험-질문)의 관찰 지점. *"해석이 사실을 이긴다"*가 참인지 확인한다

## 3. QA와 행동 프로브를 나눈 이유

**롤플레이에서 아무도 퀴즈를 내지 않는다.** *"내 고양이 이름 뭐였지?"*라고 묻는 유저는 시스템을 테스트하는 유저지 즐기는 유저가 아니다.

| | QA (Q01~Q26) | 행동 프로브 (P01~P18) |
|---|---|---|
| 방식 | 물어보고 답을 채점 | **묻지 않고 생성을 관찰** |
| 재는 것 | 어느 계층이 실패했나 | 실제 유저 경험 |
| 역할 | **진단** | **판정** |

유저가 겪는 건 *"갑자기 캐릭터가 이상해졌다"*이지 *"정답을 못 맞췄다"*가 아니다. 그래서 QA는 원인 규명용으로 남기고, 우열 판정은 프로브로 한다.

**P04와 P05가 짝이라는 점에 주의.** 능동 소환을 늘리면 `proactive_recall_rate`는 오르지만 `over_recall_discomfort`도 오른다. **같은 행동이 두 지표를 반대로 움직인다.** 적응 역설의 역U자를 실측해 최적 빈도를 찾는 것이 목적이고, **이 곡선은 아직 아무도 발표한 적이 없다.**

## 4. 실패 계층 분해 (L1/L2/L3)

같은 오답이라도 원인이 다르다. `A1 Oracle` arm이 이걸 가른다.

```
Oracle arm(정답 근거를 확실히 주입)에서도 틀림  →  L3 활용 실패
Oracle은 맞는데 실제 arm은 틀림 + evidence_recall 낮음  →  L2 검색 실패
Oracle은 맞는데 실제 arm은 틀림 + 애초에 저장 안 됨   →  L1 저장 실패
```

**이 분해가 투자 우선순위를 정한다.** L3가 크면 메모리 구조를 아무리 고쳐도 상한이 낮으므로 배치·프롬프트부터 손대야 한다.

실증적 근거: 유사 서비스 A 유저들이 재생성하면 대부분 다시 기억한다고 한다. **재생성은 컨텍스트를 안 바꾼다** — 정보는 이미 있었고 생성이 실패한 것이다.

## 5. ⚠️ 이 평가가 예측할 수 없는 것

**정직하게 먼저 적는다.**

**① 순환성.** LLM이 쓴 대화로 LLM 메모리 시스템을 테스트한다. 합성 대화는 실제 유저 대화보다 **더 명시적이고, 더 일관되고, 더 추출하기 쉽다.** 실제 유저는 파편·오타·이모지·`*행동 묘사*`·코드 스위칭·번복을 쓴다.
→ **결론을 "상대 순위"로만 쓴다.** 절대 성능은 예측할 수 없다.
→ 완화: 노이즈 65% 구간에 오타·파편·이모지·번복을 의도적으로 섞는다.

**② 참조 깊이가 내가 심은 대로 나온다.** 대장이 참조 분포를 인위적으로 결정한다. 실제 유저의 분포와 다를 수 있다.
→ 완화: 깊이 구간별로 **따로** 리포트한다. 평균 하나로 뭉치지 않는다.

**③ PPR을 제3자 관찰로 대리 측정한다.** 원래 PPR은 **당사자 자기보고** 지표다. LLM 심판이 밖에서 보는 순간 다른 걸 재게 된다.
→ 완화: 인간 라벨 20~30건으로 κ 교정. κ < 0.4면 지표를 폐기한다.

**④ 최종 지표(재방문율)는 못 잰다.** 전부 대리 지표다.

**⑤ 신규 지표 7개는 선례가 없다.** `misinjection_rate`, `over_recall_discomfort`, `payoff_rate` 등의 타당성이 미검증이다.

## 6. 코퍼스 생성 방법 (키 확보 후)

```
for each session S in S01..S24:
  1. 대장에서 이 세션에 속한 facts/events/debts를 뽑는다
  2. 프롬프트:
     "다음 설정으로 한국어 롤플레이 대화 {N}턴을 써라.
      캐릭터: {persona + speech_rules}
      관계 상태: {relationship_arc at S}
      이 세션에서 반드시 등장해야 하는 것:
        - {F001을 12번째 턴 근처에서 자연스럽게}
        - {E007을 3번째 턴에서}
      나머지 {65%}는 관련 없는 일상 잡담으로 채운다.
      잡담에는 오타·파편·번복을 자연스럽게 섞는다."
  3. 생성 결과에서 심은 항목의 실제 turn 위치를 파싱해 대장에 기록
     (계획 위치와 다르면 대장을 실측 위치로 갱신 — 대장이 진실원)
```

**비용:** 24세션 × 30턴 × ~130토큰 = ~94K 출력 토큰. Batch 기준 **$0.2 미만.**

**키 없이 하려면:** 이 대화의 어시스턴트가 직접 작성한다. 느리지만 대장 준수도가 가장 높다.

## 7. 실행 순서

```
Step 0.  A1(Oracle) arm만 돌려 L3 실패율 측정        ← ✅ 완료. 아래 참조
Step 1.  통제 baseline 5종 (A0/A1/A2/A3/G1)
Step 2.  Stage 0 — LLM 없이 되는 것부터
           evidence_recall@k, 토큰 회계,
           캐시 접두사 안정성, 검색 지연
Step 3.  모듈별 OFAT 스윕
Step 4.  상위 모듈 교차 → 파레토 프론티어
Step 5.  모델 × 메모리 구조 교차                     ← 사업적으로 가장 값진 숫자
```

> ### ✅ Step 0의 답 ([실험 13](../docs/11-experiment-results.md))
> ```
> L3 활용 실패  9/26 = 35%    ← 근거를 줘도 못 씀
> L2 검색 실패  2/26 =  8%    ← 메모리 구조로 고칠 수 있는 몫
> ```
> **L3 > L2.** 메모리 구조를 완벽히 고쳐도 상한이 낮다 → **배치·프롬프트·생성 제어가 먼저다.**
> 위 §4에 적은 *"L3가 크면 메모리 구조를 아무리 고쳐도 상한이 낮다"*가 **실제로 그렇게 나왔다.**
>
> 🔵 그리고 예상 못 한 것: **제안안이 Oracle을 abstention 3문항에서 이겼다.**
> Oracle은 정답 근거만 줘서 *"없음"*인 문항에서 지어냈고, 제안안은 `[알고 있는 것]` 전체가 있어 부정할 수 있었다.
> → **부정 지식은 정답이 아니라 경계 정보에서 나온다.** `coverage`를 심어둔 것이 여기서 값을 했다.

**Step 2는 키 없이 가능하다.** 로컬 임베딩([KURE](https://github.com/nlpai-lab/KURE))으로 `evidence_recall@k`를 재면 **검색기 품질과 캐시 가설의 상당 부분이 여기서 결판난다.** 검색기가 못 찾은 걸 LLM이 답할 수는 없다.

> 그리고 **수기 세션을 쓰다가 U10(유저 오류 동조)이라는 새 실패 유형을 발견**했다 — [상세](sessions/README.md)
