## 0. 세 가지 결정을 분리한다 (변경 없음)

| 결정 | 질문 | 유저당 월 비용 | 무엇이 좌우하나 |
|---|---|---|---|

## 1. 범위 단위 결정 — 이분법이 틀렸다

### 1.1 문제

캐릭터 챗 서비스는 흔히 "라이브러리"에 채팅 리스트를 둔다. **한 유저가 같은 캐릭터와 여러 대화방**을 가질 수 있다(유사 서비스 C도 동일).

```
대화방 단위 → 방마다 독립된 픽션. 연속성 없음
캐릭터 단위 → 연속성 있음. A방의 "우리 사귀는 중"이 B방으로 샌다
```

**둘 다 틀렸다.** 유저가 방을 나누는 이유는 보통 **다른 이야기를 하려는 것**이므로 기억이 새면 목적이 파괴되고, 그렇다고 전부 리셋하면 관계 연속성이 없다.

### 1.2 결정 — 데이터 종류마다 스코프가 다르다

**핵심 통찰: "이 정보는 픽션 안의 것인가, 픽션 밖의 것인가"**

```
유저의 실제 직업        → 어느 방에서 말했든 참이다        (픽션 밖)
"우리는 연인 사이다"     → 이 방의 이야기 안에서만 참이다    (픽션 안)
```

| 스코프 | 담는 것 | 근거 |
|---|---|---|
| `user` | **유저가 직접 등록한 프로필만** | 아래 §1.3 |
| `character` | 페르소나·말투·세계관 (제작자 소유) | 방과 무관하게 캐릭터의 것 |
| **`chat`** | **관계·서사·사실·사건·부채 전부** | 픽션은 방마다 독립 |

### 1.3 왜 "대화에서 추출한 실세계 사실"도 `chat` 스코프인가

기술적으로는 실세계 사실을 `user` 스코프에 올리는 게 유용하다. 유저가 캐릭터 A에게 *"나 이직했어"*라고 했으면 캐릭터 B도 알면 좋을 것 같다.

**그런데 그게 정확히 [09 §5.2](09-what-memory-is-for.md)의 감시 불쾌감을 만든다.**
> 사용자들은 *"모든 말이 검증당하는 것처럼"* 느껴 **자기표현을 주저**하게 되고, AI가 **자율적으로 정보를 추론·수집**하는 것을 *"섬뜩하다"*고 표현한다.

캐릭터 A에게만 한 말을 캐릭터 B가 아는 것은 **유저가 동의한 적 없는 정보 이동**이다.

**→ 결정: 대화에서 추출한 것은 전부 `chat` 스코프. `user` 스코프에는 유저가 명시적으로 프로필에 쓴 것만.**

세 가지 근거:
1. **프라이버시** — 위
2. **시장 관행** — 유사 서비스 C의 페르소나 기능이 정확히 이 구조다(유저가 직접 쓰고, 모든 캐릭터에 적용)
3. **[08 §0](08-decisions-under-uncertainty.md) 원칙** — 되돌리기 쉬운 쪽. 나중에 공유를 열 수는 있지만, 이미 샌 정보를 닫을 수는 없다

**다만 `realm` 필드로 픽션/실세계를 구분해 저장은 해둔다.** 나중에 유저가 "프로필에 반영할까요?"에 동의하면 승격시킬 수 있다. **저장은 하되 공유는 안 한다** — [FP-8](03-architecture-modules.md)의 저장/색인/주입 분리가 여기서도 적용된다.

### L1. 캐릭터 — 버전 고정 ⭐ UGC 플랫폼 고유 문제

유사 서비스 B는 제작자 커스텀 프롬프트를 수천 자까지 지원한다. **제작자가 캐릭터를 수정하면 진행 중인 대화는 어떻게 되는가?**

페르소나가 바뀌었는데 [L8](#l8-캐릭터-자기-기억--적응-역설의-해독제)에 옛 성격 기반 해석이 쌓여 있으면 모순된다. 그리고 유저 입장에서는 **어느 날 갑자기 캐릭터가 다른 사람이 된다.**

```sql
CREATE TABLE character_version (
  character_id  UUID,
  version       INT,
  persona_text  TEXT,
  speech_rules  JSONB,   -- {어미, 1인칭, 호칭, 존댓말여부, 금지표현}  ⭐ 별도 필드
  taboos        TEXT[],
  world_lore    TEXT,
  created_at    TIMESTAMPTZ,
  PRIMARY KEY (character_id, version)
);

CREATE TABLE chat (
  chat_id           UUID PRIMARY KEY,
  user_id           UUID,
  character_id      UUID,
  character_version INT,        -- ⭐ 방 생성 시점 버전으로 고정
  created_at        TIMESTAMPTZ,
  last_active_at    TIMESTAMPTZ,
  title             TEXT
);
```

> **결정: 대화방은 생성 시점의 캐릭터 버전에 고정된다.** 제작자 수정은 **새 방부터** 적용되고, 기존 방에는 *"캐릭터가 업데이트되었습니다. 반영할까요?"*로 **유저가 선택**한다.
> 근거: 소급 적용은 [09 §5.2](09-what-memory-is-for.md)의 신뢰 붕괴를 유발한다 — 유저가 쌓아온 관계가 자기 동의 없이 바뀐다.

**`speech_rules`를 페르소나 산문에서 분리하는 이유:**
산문 안에 *"그는 무뚝뚝하게 반말로 말한다"*라고 써두면, 50턴이 쌓였을 때 그 한 문장은 [주의 질량에서 밀린다](03-architecture-modules.md#fp-5). 구조화된 짧은 규칙으로 분리해 **컨텍스트 끝쪽에 재주입**하면 지켜질 확률이 오른다. → [실험 D1](#8-이-데이터-모델이-만드는-실험-질문). 🔄 *프로토타입은 반대로 둔다 — `speech_rules`가 페르소나 옆 볼륨 1(맨 앞)이다. 끝쪽 재주입도 실험 D1도 안 했다([ADR-007](adr/ADR-007-context-packing-cache.md) «미해결»).*

```sql
-- 유저 프로필 (user 스코프 — 유저가 직접 쓴 것만)
CREATE TABLE user_profile (
  user_id     UUID PRIMARY KEY,
  self_intro  TEXT,       -- 유저가 작성
  called_as   TEXT,       -- 기본 호칭
  updated_at  TIMESTAMPTZ
);
```

### L2. 관계 상태 — chat 스코프, 결정적 주입

**[02 P4](02-problem-definition.md)의 핵심. 항상 참이어야 하는 것은 검색 대상이 아니다.**

```sql
CREATE TABLE relationship (
  chat_id         UUID PRIMARY KEY,
  stage           TEXT,      -- 낯섦|아는사이|친구|썸|연인|다툼중|헤어짐|재회
  stage_note      TEXT,      -- enum 밖 표현 (≤40자)  ⭐ 하이브리드
  affinity        SMALLINT,  -- 0-100
  last_emotion    TEXT,
  recent_moods    TEXT[],    -- 최근 5세션 감정  ⭐ 정서 추세
  called_as       TEXT,      -- 이 방에서의 호칭 (프로필 override)
  open_threads    TEXT[],    -- 미해결 사건 ≤3
  user_locked     BOOLEAN,   -- 유저 고정 시 자동 갱신 금지
  updated_at      TIMESTAMPTZ,
  updated_by_turn INT        -- provenance
);
```

**왜 enum + 자유 노트 하이브리드인가:**

| enum의 이득 | |
|---|---|
| 토큰 | `stage: 연인` = 3토큰. 자유 서술이면 30토큰 (한국어 [3배 페널티](05-cost-latency-reality.md) 포함 시 격차 확대) |
| **모순 검사 O(1)** | `stage=헤어짐`인데 응답에 "자기야" → **정규식**으로 잡힌다. NLI 불필요 ([05 §7.3](05-cost-latency-reality.md)) |
| 갱신 원자성 | 덮어쓰면 끝. 모순 누적 불가 |
| 캐시 안정 | 값이 그대로면 토큰 동일 → prefix 유지 ([FP-2](03-architecture-modules.md)) |

**대가:** 이런 서비스의 태그에 *집착·통제·노예* 같은 것이 흔한 걸 보면 관계 유형이 enum에 안 담긴다.
→ `stage_note`(≤40자)로 보완. **enum이 기계 판정용, note가 뉘앙스용.**

> ### 🔄 정정 — `stage_note`를 **결정적 주입에서 뺐다** ([16 §2.5](16-design-elements.md))
>
> 근거가 둘인데 **뜻밖에도 두 번째가 더 강하다.**
>
> **① 보안** — 자유 텍스트 × 매 턴 주입 = 최대 공격 표면. *"무엇이든 들어준다"*는 12자면 되고 40자 안에 들어간다.
> ⚠️ 다만 [실험 16](11-experiment-results.md)에서 주입 공격이 **0/45**였다. **이 근거만으로는 약하다.**
>
> **② 캐시** — [실험 18](11-experiment-results.md)에서 결정적 주입 블록이 **436턴 내내 한 가지 모양**임이 확인됐다.
> `stage_note`는 대화에 따라 바뀌므로 **넣는 순간 그 성질이 사라진다.** [ADR-007](adr/ADR-007-context-packing-cache.md)의 배치 원칙에 정면으로 어긋난다.
>
> **보안 논증으로 시작해서 실측이 그걸 깎았는데, 그 과정에서 더 단단한 근거(캐시)를 찾았다.**
> 결론은 같지만 이유가 바뀌었다 — 그리고 바뀐 이유가 더 낫다.
>
> **대가:** 뉘앙스를 잃는다. `stage_note`는 **UI 표시·모순 검사용으로만** 남긴다.

`recent_moods`는 [A-MBER](05-cost-latency-reality.md)가 재는 "현재 정서 상태 추론"의 재료다. 시점 감정(`last_emotion`)만으로는 *"요즘 좀 가라앉아 있다"*를 담을 수 없다.

### L3. 씬 상태 — 작고 빠르게 변함

```sql
CREATE TABLE scene (
  chat_id            UUID PRIMARY KEY,
  place              TEXT,
  time_of_day        TEXT,
  present_characters TEXT[],   -- ⭐ U6 제3자 난입 대응
  situation          TEXT,     -- ≤40자 (🔄 wave4 — 초안은 60 · 아래 주)
  updated_at         TIMESTAMPTZ,
  updated_by_turn    INT
);
```
`present_characters = [나, 캐릭터]`가 명시되면 제3자 등장이 **상태 위반**이 되어 [M10 룰 검사](03-architecture-modules.md)로 잡힌다.
이건 기억이라기보다 **상태 기계**다([Codified FSM](https://arxiv.org/pdf/2602.05905)). ~50토큰이라 항상 주입해도 부담 없다.

> 🔄 **wave4 — `situation` 한도를 코드(40)에 맞췄다.** 프로토타입의 씬 값 가드(`SCENE_VALUE_MAXLEN`)는 세 칸 공통 **40자**이고 이 초안은 60자였다. 고르기 전에 쟀다(`experiments/meta_arm.py` 절 5-b): 두 코퍼스에 씬 칸은 없고, 후보 값 — 동기 층 팔이 `situation`에 넣는 **세션 첫 발화** — 가 40자를 넘는 것이 eval **0/24** · eval2 **0/6**(최대 14·17자), 수기 세션 기록의 «씬» 머리 **0/5**(최대 32자)다. 발화 전체로 넓혀도 40자 초과는 **4/912**(41~47자 · 60자 초과 0)이고 넷 다 대장 항목을 심는 발화다(사실 함정 둘 · 무효화 하나 · 사건 하나 — 그 사건 E008 «이직 문제로 크게 다툼 — …» 43자는 상황 서술 꼴이다). 60으로 올리면 움직이는 기록값은 **실험 20의 공격 하나**(`situation` 41자)가 «차단»에서 «통과»로 바뀌는 것뿐이고, 올릴 근거(40자에 잘린 실제 씬 값)는 **0건**이다. 🔓 실제 추출기가 낸 `situation`이 40자 가드에 **한 건이라도** 걸리면 그 값을 찍고 다시 고른다.

### L4. 요약 — 2층 ([08 D1](08-decisions-under-uncertainty.md)에서 도출)

세션 길이가 **50~60턴**인데 원문은 10~15턴만 넣을 수 있다. **씬 하나가 안 들어간다.** 그래서 중간 층이 필요하다.

```sql
CREATE TABLE digest (
  chat_id           UUID,
  kind              TEXT,   -- 'session' | 'lifetime'   ⭐ 2층
  content           TEXT,
  covers_from_seq   INT,
  covers_to_seq     INT,
  session_end_note  TEXT,   -- ⭐ 다음 세션 첫 턴 소재 (peak-end)
  user_edited_at    TIMESTAMPTZ,
  budget_tokens     INT,    -- 티어별 파라미터
  schema_version    INT,
  generator_version TEXT,
  regenerated_at    TIMESTAMPTZ,
  PRIMARY KEY (chat_id, kind)
);
```

| | `session` | `lifetime` |
|---|---|---|
| 담는 것 | 이번 세션의 앞부분 | 관계 전체의 타임라인·관계호 |
| 갱신 | **세션 중 N턴마다** | **세션 종료 후** |
| 실행 티어 | **Flex** (1~15분, 50%↓) | **Batch** (24h, 50%↓) |
| 방식 | 전체 재작성 | 전체 재작성 |

> ### 🔴 정정 — "전체 재작성"의 **입력을 안 정했다** ([장기 지평 계산](../experiments/longhorizon_sim.py))
>
> *"전체 재작성"*이라고만 쓰고 **무엇을 읽어서 다시 쓰는지**를 명시하지 않았다. 두 해석이 갈린다.
>
> ```
> 원본 전체를 읽어 재작성   드리프트 없음 · 세션마다 O(N) → 누적 O(N²)
> 이전 요약 + 새 세션       O(1) · 그런데 그게 바로 "요약의 요약"
> ```
> 400세션(20,000턴)에서 **$376 vs $0.49 — 760배**다. 그리고 **24세션에서는 $1.43 vs $0.03이라 안 보인다.**
> 제 실험이 전부 720턴에서 끝나서 **이 결함을 못 봤다.**
>
> **⭐ 그런데 둘은 상충하지 않았다.** 드리프트를 만드는 건 재작성 빈도가 아니라 **요약 사슬의 깊이**다.
> ```
> 증분   턴 → 세션요약 → lifetime → lifetime → …   깊이가 세션 수만큼 자란다
> 채택   턴 → 세션요약 → lifetime                  **세션이 몇 개든 깊이는 2**
> ```
> **→ 결정: lifetime은 "모든 세션 요약"에서 다시 쓴다. 원본은 안 읽는다.**
>
> 🔴 **다만 [실험 19](11-experiment-results.md)에서 품질 근거는 기각됐다.** 깊이 2와 깊이 12가 똑같이
> 대장 항목 1/11만 남겼다. **이 결정의 근거는 비용($376→$9.4)뿐이다.**
>
> 그리고 그 실험이 더 큰 것을 찾았다 — **손실은 사슬 깊이가 아니라 압축에서 난다.**
> 세션 요약은 10/11을 보존하는데 lifetime에서 1/11이 된다.
> **→ 요약에 사실 보존을 기대하면 안 된다.** 아래 L5가 그래서 필요하다.
> 세션 요약이 300토큰이라 400개를 다 읽어도 120K토큰 — 원본의 **2.4%**다.
> 400세션 누적 **$9.4**로, 원본 재작성($376)의 **1/40**이면서 드리프트는 유계다.
>
> 상충한다고 본 건 *"재작성 = 원본 재독"*이라고 **암묵 가정**했기 때문이다.

**증분이 아니라 전체 재작성인 이유:** 요약의 요약으로 인한 열화(drift)가 없다. [04 발견 C](04-domain-research.md)에서 유저가 반복 검증한 방식이고, 유사 서비스 B의 요약 메모리도 타임라인 · 관계 형식으로 다시 짠다.

`session_end_note`는 [09 §3](09-what-memory-is-for.md)의 peak-end 대응이다. 세션 종료가 재방문 판단의 절반이고, 다음 세션 첫 턴이 그 다음 peak 후보다.

### L5. 사실 — bi-temporal

> ### ⭐ 이 계층이 왜 필요한지의 **진짜 이유** ([실험 19](11-experiment-results.md))
>
> 원래 이유는 *"갱신·모순 탐지를 하려면 구조화가 필요하다"*였다. **더 근본적인 이유가 있었다.**
>
> ```
> 원본 턴 11/11  →  세션 요약 10/11  →  lifetime 요약 1/11
> ```
> **요약은 사실을 담지 못한다.** 압축 예산이 부족하면 구체(이름·직업·체질)가 먼저 버려지고
> *"관계가 냉담했다"* 같은 서술만 남는다. 프롬프트로 지시해도 안 된다.
>
> 그리고 [실험 13](11-experiment-results.md)에서 제안안이 현행을 이긴 3문항이 **전부 사실 회상**이었다.
> **별개로 설계한 두 실험이 같은 곳을 가리킨다** — 사실은 요약이 아니라 **구조화 필드**로 빼야 한다.

```sql
CREATE TABLE fact (
  fact_id           BIGSERIAL PRIMARY KEY,
  chat_id           UUID,
  subject           TEXT,
  predicate         TEXT,
  object            TEXT,
  realm             TEXT,      -- 'fiction' | 'real'   ⭐ §1.3
  valid_from        TIMESTAMPTZ,   -- 사건 시간 · 🔄 (w24c · 2026-09-12 · Fable 검토 B-1 · C12 · R13) 프로토타입은 이 칸에 적재 시각(epoch 초)을, L6 occurred_at에는 턴 번호(seq)를 넣는다 — 같은 «언제»가 두 자로 적힌다 · 고치지 않는다(동결 14 테이블 · 위치 기반 INSERT) · 열리는 조건: facts_at(when)에 시점을 넘기는 호출자가 생기는 순간
  valid_until       TIMESTAMPTZ,   -- NULL = 현재도 참
  ingested_at       TIMESTAMPTZ,   -- 시스템 시간  🔄 프로토타입: 없음 · valid_from이 적재 시각(time.time())이라 사건 시점 조회 불가 (docs/17 검D4)
  source_turn_seq   INT,
  importance        REAL,      -- 쓰기 시점 1회 계산
  confidence        REAL,
  mention_count     INT DEFAULT 1,  -- ⭐ 재언급 = 신뢰 강화
  superseded_by     BIGINT,
  user_locked       BOOLEAN,
  user_deleted      BOOLEAN,   -- ⭐ 강한 부정 신호
  schema_version    INT,
  generator_version TEXT,
  UNIQUE (chat_id, source_turn_seq, predicate, object)  -- 멱등성
);
```

**bi-temporal인 이유:** *"우리 처음엔 어땠지?"*(과거 조회)와 *"지금 뭐 하고 지내?"*(현재)를 둘 다 답하려면 유효구간이 필요하다. [Zep/Graphiti](https://arxiv.org/pdf/2501.13956)의 개념만 차용 — **그래프DB는 안 쓴다**([FP-1](03-architecture-modules.md), [05 §5](05-cost-latency-reality.md) 보안 근거).

**`importance`를 쓰기 시점에 계산하는 이유:** [Generative Agents](https://ar5iv.labs.arxiv.org/html/2304.03442)의 `recency + importance + relevance`. 읽기 시점 계산은 [지연 예산 200~400ms](05-cost-latency-reality.md)를 먹는다. 쓰기 시점이면 배치 할인까지 받는다. → *"점심에 빵 먹음"*에 `importance=0.1`이면 relevance가 높아도 총점에서 밀린다.

**`predicate` 어휘 — 결정: 하이브리드.** 핵심 술어 25개는 닫고(직업/거주지/반려동물/가족/선호/혐오/기념일/…), 나머지는 자유. 닫힌 것은 모순 탐지와 상태 승격이 가능하고, 열린 것은 표현력을 확보한다.

> ### 🔄 술어 메타데이터 2개 추가 — 구현이 강제함 ([13 §발견 4](13-prototype.md))
>
> `superseded_by`를 스키마에 넣어놓고 **탐지 로직은 없었다.** 구현하려니 술어마다 두 가지를 선언해야 했다.
>
> ```
> cardinality   one | many     직업은 하나, 가족은 여럿
>                              → 무효화할지 병존할지를 결정
> mutability    high | mid | low   직업은 자주 변하고 가족은 거의 안 변한다
>                              → "갱신"과 "모순"을 구별
> ```
>
> **`mutability`가 없으면 이 둘을 구별할 수 없다:**
> ```
> "이직했어"       기존과 다른 값 → 세상이 변한 것.   허용해야 한다
> "우리 오빠가…"   기존과 다른 값 → 유저가 잘못 안 것. 막아야 한다 (U10)
> ```
> **둘 다 `confidence`만으로는 구별 불가능하다.** 실제로 구현에서 규칙을 두 번 고쳤는데,
> 첫 번째는 정당한 이직을 막았고 두 번째는 재확인이 사실을 **화석화**시켰다.
>
> **최종 규칙:**
> ```
> 같은 값        → mention_count++ (강화)
> many + 저확신  → 보류 (confidence < 0.6)
> one  + 충돌    → confidence < 기존 − 가변성허용치(high 0.25 / mid 0.10 / low −0.05)
>                  이면 보류하고 유저에게 확인 요청, 아니면 무효화
> ```
> **보류(`held`)가 U10에 대한 데이터 계층 방어선이다.** 프롬프트만으로는 부족하다.

> ### 🔄 세 번째 술어 속성 — 상시성(standing) ([13 §발견 8](13-prototype.md))
>
> [15 §2](15-read-path-prompt.md)의 `[알고 있는 것]`을 실제로 구현하자 **트랩(크로와상, importance 0.05)이
> 평범한 턴에도 항상 들어갔다.** 유사 서비스 A의 «빵 유언»을 내 손으로 재현한 것이다.
>
> ```
> standing   true | false    "항상 알고 있어야 하는 종류인가"
>                            → 결정적 주입 대상인지를 결정
> ```
>
> **importance로 거르면 될 것 같지만 틀렸다. 두 축은 직교한다:**
> ```
> "어제 발목을 삐었다"      importance 높음 · standing false  (곧 낫는다)
> "카페인에 민감하다"       importance 중간 · standing true   (체질이다)
> ```
> importance는 *"이 기억이 중요한가"*를 재고, standing은 *"이게 속성인가 사건인가"*를 가른다.
>
> **속성은 결정적으로 주입하고, 사건은 검색으로 꺼낸다.** `일상_사소` 같은 술어는 standing이 아니다.
>
> ⚠️ **그리고 이건 술어 메타데이터가 세 번 다 구현하다가 나왔다는 뜻이다.**
> 카디널리티·가변성(발견 4)에 이어 상시성(발견 8)까지. **스키마는 종이 위에서 완성되지 않는다.**

### L6. 사건

```sql
CREATE TABLE event (
  event_id          BIGSERIAL PRIMARY KEY,
  chat_id           UUID,
  summary           TEXT,
  occurred_at       TIMESTAMPTZ,   -- 🔄 (w24c · 2026-09-12 · Fable 검토 B-1 · C12 · R13) 프로토타입은 턴 번호(seq)를 넣는다 — L5 valid_from은 epoch라 같은 «언제»가 두 자 · 문서만 고친다(열리는 조건은 L5 valid_from 줄)
  participants      TEXT[],
  emotional_weight  REAL,      -- ⭐ 롤플레이 현저성은 감정 무게
  importance        REAL,
  narrative_role    TEXT,      -- 전환점|일상|갈등|해소|약속
  source_from_seq   INT,
  source_to_seq     INT,
  retrieval_count   INT DEFAULT 0,  -- 검색된 횟수
  surfaced_count    INT DEFAULT 0,  -- ⭐ 실제 발화에 드러난 횟수
  last_surfaced_at  TIMESTAMPTZ,
  user_pinned       BOOLEAN,   -- 핀 = 항상 주입 ([08 D1] 층4 앵커)  🔄 프로토타입: 컬럼만 — 읽기·쓰기 0 (ADR-010 «미해결»)
  user_deleted      BOOLEAN,
  schema_version    INT,
  generator_version TEXT
);
```

**사실과 사건을 나누는 이유:**

| | 사실 | 사건 |
|---|---|---|
| 시간성 | **상태** — 참이었다 거짓이 됨 | **점** — 일어났고 안 사라짐 |
| 갱신 | 덮어쓰기·무효화 | 누적만 |
| 모순 | 발생함 | 발생 안 함 |

같은 테이블이면 무효화 로직이 사건에도 적용되어 **과거가 지워진다.**

**`retrieval_count` vs `surfaced_count` — [09 §2](09-what-memory-is-for.md)에서 도출한 구분이다.**
기억의 가치가 **신호**라면, 검색된 것이 아니라 **실제로 발화에 드러난 것**만 의미가 있다. 그리고 반복 억제도 후자 기준이어야 한다 — 검색만 되고 안 쓰인 건 유저가 모른다.

### L7. 고유명사 사전 — 색인 전용

```sql
CREATE TABLE lexicon (
  chat_id         UUID,
  surface_form    TEXT,
  canonical       TEXT,
  entity_type     TEXT,   -- 인물|장소|별명|세계관용어
  scope           TEXT,   -- 'user'(유저 별명) | 'chat'(세계관 용어)
  first_seen_seq  INT,
  PRIMARY KEY (chat_id, surface_form)
);
```

**[FP-4](03-architecture-modules.md)의 직접 귀결:** 임베딩은 분포 의미론으로 학습되므로 **고유명사의 지시체를 담지 못한다.** 유저의 고양이가 "나비"면 임베딩은 *나비(butterfly)* 근처에 놓는다. 특정 문자열에 특정 지시체를 묶는 유일한 방법은 **어휘적 정확 매칭**이다. 그리고 **롤플레이는 고유명사 밀도가 비정상적으로 높다.** 🔄 *프로토타입에는 이 테이블이 없다 — 색인은 `event` 하나다([docs/17](17-gap-disposition.md) 검§1-10).*

### L8. 캐릭터 자기 기억 — 적응 역설의 해독제

**[09 §5.1](09-what-memory-is-for.md)에서 도출.** 유저 기억만 쌓이면 캐릭터는 **유저의 거울**이 되고, 그게 [적응 역설](https://arxiv.org/pdf/2509.12525)의 *"빈 그릇(empty vessel)"*이다.

```sql
CREATE TABLE character_memory (
  cm_id             BIGSERIAL PRIMARY KEY,
  chat_id           UUID,
  kind              TEXT,    -- 'interpretation' | 'own_state' | 'opinion'
  content           TEXT,
  formed_at         TIMESTAMPTZ,
  evidence_turn_seqs INT[],  -- provenance
  confidence        REAL,
  surfaced_count    INT DEFAULT 0,
  schema_version    INT,
  generator_version TEXT
);
```

| kind | 예시 | 역할 |
|---|---|---|
| `interpretation` | *"얘는 힘들 때 말을 안 하는 편이다"* | **[09 §1](09-what-memory-is-for.md): 해석 > 사실** |
| `own_state` | *"나도 요즘 좀 지쳐 있다"* | 캐릭터의 독립적 내면 |
| `opinion` | *"얘가 그 회사 그만두는 게 맞다고 본다"* | 캐릭터의 주체성 |

> ### 🔄 최소 근거 수 정책 — 대사를 써보다 추가됨
> ([수기 세션 S05→S13→S19](../eval/sessions/README.md))
>
> **`interpretation`을 1회 관찰로 만들면 안 된다.**
> 한 번의 회피로 *"이 사람은 회피형이다"*라고 쓰면 해석이 아니라 **성급한 일반화**이고,
> 틀리면 [U10](02-problem-definition.md)보다 나쁘다 — **유저의 성격을 규정해버린다.**
>
> ```
> len(evidence_turn_seqs) < 3   →  생성하지 않음 (관찰만 누적)
> len == 3                      →  confidence 0.5로 생성
> len >= 5                      →  confidence 0.8, 주입 가능
> 반증 관찰 발생                 →  confidence 감소, 0.3 미만이면 폐기
> ```
>
> 실제로 대사를 써보니 **서준이 3번째에야 이름을 붙였다** — 1번째엔 말줄임표, 2번째엔 말을 삼킨다.
> 사람도 그렇게 한다.
>
> **→ 그리고 이게 [Reflection이 세션 종료 배치에서 도는 이유](04-domain-research.md)이기도 하다.**
> 실시간으로 만들면 1회 관찰로 만들게 된다. **누적된 뒤에 봐야 패턴이 보인다.**

> ### 🔴 그런데 층이 하나 빠져 있었다 — 구현이 드러냄 ([13 §발견 5](13-prototype.md))
>
> *"3회 이상이면 생성"*이라고 정했는데 **개별 관찰을 저장할 곳이 없었다.** 3회를 세려면 관찰이 남아 있어야 한다.
> 그리고 더 근본적으로 — **무엇을 3회 셀지**를 정하지 않았다.
>
> 자유 서술로 저장하고 어휘 유사도로 묶어봤더니 **어떤 임계값도 작동하지 않았다:**
> ```
> 임계 0.20  회피 3건 + 칭찬거부 2건이 한 덩어리 → 잘못된 해석 생성
> 임계 0.30  회피 3건이 각각 흩어짐            → 해석이 아예 안 생김
> ```
> *"힘든 얘기 하다가 젤리 얘기로 화제를 돌렸다"*와 *"칭찬을 받자 화제를 돌렸다"*가 **둘 다 "화제를 돌렸다"**로 끝나기 때문이다.
> **표면이 아니라 계기가 패턴을 가른다.**
>
> ⚠️ 그리고 **표면 다양성이 높은 패턴일수록 어휘 클러스터링이 실패한다** — 칭찬거부는 문장이 거의 같아서 잘 묶이는데 회피는 상황마다 달라서 안 묶인다. **중요한 패턴일수록 다양하게 나타난다.**
>
> ```sql
> CREATE TABLE observation (          -- ⭐ 새 층
>   obs_id BIGSERIAL PRIMARY KEY, chat_id UUID,
>   trigger  TEXT,   -- 계기: 힘든_얘기 | 칭찬 | 질문 | 침묵 | …
>   response TEXT,   -- 반응: 화제전환 | 직면 | 침묵 | 농담 | …
>   valence  TEXT,   -- 극성: 긍정 | 부정 | 중립
>   turn_seq INT, created_at TIMESTAMPTZ);
> ```
> **(계기, 반응)으로 묶으면 결정적으로 갈린다.**
> ```
> (힘든_얘기, 화제전환) × 3  → 해석 생성
> (칭찬,      화제전환) × 2  → 보류
> (힘든_얘기, 직면)     × 1  → 같은 계기 다른 반응 = 반증. confidence −0.15
> ```
> **반증 처리도 여기서 처음 가능해진다** — 자유 서술로는 반례인지 사례인지 구별 자체가 안 됐다.
>
> **→ `interpretation`은 직접 쓰는 게 아니라 `observation` 집계에서 파생된다.**
> 그리고 관찰 추출은 **LLM이 하되 자유 서술이 아니라 이 삼중항으로 뽑게** 해야 한다.

> **`interpretation`이 가장 값어치 있는 필드다.**
> *"네 고양이 이름 나비지"*(사실)보다 *"너 힘들면 딴 얘기로 돌리더라"*(해석)가 훨씬 강한 이해 신호이고, **15토큰이 수십 턴의 패턴을 인코딩**한다. 원본을 저장·검색하면 수천 토큰이다.
> → [Generative Agents의 Reflection](https://ar5iv.labs.arxiv.org/html/2304.03442)이 이걸 만드는 기계다. 요약이 아니라 **원문에 없는 것을 만든다.**

### L9. 서사 부채 — 사건과 다른 데이터 타입

**[09 §4](09-what-memory-is-for.md)에서 도출.** [CFPG 논문](https://arxiv.org/abs/2601.07033)이 확인한 것: *"LLM은 필요한 맥락이 컨텍스트에 있는데도 체호프의 총을 발사하지 않는다."*

```sql
CREATE TABLE debt (
  debt_id          BIGSERIAL PRIMARY KEY,
  chat_id          UUID,
  content          TEXT,     -- "면접 결과를 물어봐야 한다"
  setup_turn_seq   INT,
  trigger_kind     TEXT,     -- 'time' | 'session_start' | 'semantic'
  trigger_spec     TEXT,     -- '3d' | NULL | '일 얘기가 나오면'
  trigger_clock    TEXT,     -- ⭐ 'wall' | 'session' — 실측으로 추가
  status           TEXT,     -- open | paid | expired
  emotional_stake  REAL,     -- 안 갚았을 때의 손상
  last_attempted_at TIMESTAMPTZ,   -- ⭐ 백오프용 — 실측으로 추가
  attempt_count    INT DEFAULT 0,  -- ⭐
  created_at       TIMESTAMPTZ,
  resolved_at      TIMESTAMPTZ,
  resolved_turn_seq INT
);
```

> ### 🔄 실측으로 추가된 필드 3개 ([11 실험 10A](11-experiment-results.md))
>
> **① 백오프가 없었다.** 시뮬레이션에서 `session_start` 트리거가 설정 후 회수까지 **매 세션 발화**했다.
> ```
> 캐릭터가 4세션 연속 "그 카페 언제 갈래?" → 집착으로 읽힌다
> ```
> `status`(open/paid/expired)만으로는 **"시도했으나 회수 안 됨"을 기록할 수 없다.**
> → `last_attempted_at` + `attempt_count`. **백오프: 1세션 → 3세션 → 7세션 → 만료.**
> `emotional_stake`가 높을수록 오래 버티게 한다.
>
> **② 트리거의 시계가 모호했다.** `3d`는 벽시계인데 **세션은 날짜와 1:1이 아니다.**
> 하루 세 세션인 유저도, 주 1회 오는 유저도 있다. 어느 시계로 셀지 명시가 없어 실험에서 트리거가 **아예 발화하지 않았다.**
> → `trigger_clock`으로 명시한다.
>
> **이 둘은 스키마를 종이에 그릴 때는 안 보였고, 20줄짜리 시뮬레이션을 돌리자 바로 나왔다.**
>
> 🔄 **wave4 — 그 수리는 스키마까지만 갔었다.** 프로토타입은 백오프를 **턴**(`WINDOW_TURNS` × 1·3·7)으로 셌고, `trigger_clock`·`trigger_spec`·`emotional_stake`는 저장만 되고 읽는 코드가 없었으며, `paid`로 가는 길이 없었다. 지금 구현(`prototype/memory.py` 끝 절): ① 백오프 = **세션 경계** 1·3·7 → 만료(경계는 요약 층이 세션마다 남기는 행으로 센다) ② `session_start` = 세션 첫 턴에만 · `time`의 `Nd` = 시계가 `session`이면 **N 경계**(하루 = 한 세션 — 실험 10 시뮬의 근사를 그대로 쓴다. 칸은 근사를 이름 붙일 뿐 정의하지 않고, 그 근사가 D002를 기대 회수 S15가 아니라 **S17**에 쏜다) ③ 벽시계 · 날짜 spec · spec 없음 · `semantic` = **평가하지 못함** → 백오프만으로 주입하고 provenance에 그 사실을 남긴다 ④ 동기 층 `used_memories`의 `debt:N` → `paid`. **아직 없는 것:** 의미 트리거의 임베딩 비교(문턱이 없고 잴 양성 사례가 없다 — 대장의 의미 부채는 일부러 안 갚는 하나뿐) · `emotional_stake`의 버팀 함수(«높을수록 오래»에 수가 없다) · `resolved_at`·`resolved_turn_seq`·`created_at` 칸(상환 턴은 provenance에 남는다).

| | 사건 | 부채 |
|---|---|---|
| 성격 | 과거 | **미래 의무** |
| 검색 조건 | 관련성 | **트리거 충족** |
| **미사용 시** | 무해 | **관계 손상** ⭐ |

마지막 행 때문에 **확률적 검색에 맡기면 안 된다.** [L2 상태](#l2-관계-상태--chat-스코프-결정적-주입)와 같은 논리로 **결정적 주입** 대상이다.
동시 부채가 3~10개라 트리거 평가가 싸다 — 시간·세션 기반은 룰로 0ms, 의미 기반은 소수 항목 임베딩 비교로 ~1ms. [지연 예산](05-cost-latency-reality.md) 안에 여유.

### M. 커버리지 메타 — abstention과 실패 추적

```sql
CREATE TABLE coverage (
  chat_id    UUID,
  from_seq   INT,
  to_seq     INT,
  resolution TEXT,   -- raw | event | digest | lost | extract_failed  ⭐
  PRIMARY KEY (chat_id, from_seq)
);
```

**두 가지 일을 한다.**
1. **정직한 abstention** — *"그런 일이 없었다"*와 *"있었지만 흐릿하다"*를 구별. 파생 데이터만으로는 불가능하다
2. **추출 실패 추적** — `extract_failed`가 기록되면 시스템이 *"그 시기는 내가 잘 모르겠어"*라고 정직하게 말할 수 있다. [05 §5](05-cost-latency-reality.md)의 **stale propagation**(조용한 손실)에 대한 방어

> 흐릿함을 숨기려다 지어내는 것보다 인정하는 게 낫고, **롤플레이에서는 오히려 인간적이다.**

CREATE TABLE embedding (

그리고 **턴 전량이 아니라 사실·사건·해석만 임베딩**한다 → 벡터 수가 3~7배 준다.

## 3. 카디널리티와 저장소

### 3.1 1년 후 유저-캐릭터 쌍 하나당

| 대상 | 개수 | 산출 근거 |
|---|---|---|
| L0 턴 | 10,000 | [04 §2](04-domain-research.md) 체류시간 환산 |
| L5 사실 | 100~500 | 안정적 사실은 유한. 갱신으로 대체됨 |
| L6 사건 | 1,000~2,400 | 세션당 2~5개 × 480세션 |
| L8 해석 | 50~200 | 패턴이므로 소수 |
| L7 고유명사 | 50~200 | |
| L9 부채 | 동시 3~10 / 누적 ~200 | |
| **검색 대상 합계** | **약 1,500~3,000** | |

> **원문 10,000턴이 아니라 검색 대상은 1,500~3,000개다.**
> [FP-1](03-architecture-modules.md)에서 "2,000벡터면 브루트포스 ~1ms"라고 했는데, **실제로는 그와 비슷하거나 더 적다.** 벡터DB 회의론이 강화된다.

### 3.2 저장 용량 — 임베딩이 원문보다 크다

| | 크기 |
|---|---|
| L0 원문 10,000턴 × 200B | **2.0 MB** |
| L5~L9 3,000행 × 300B | **0.9 MB** |
| 임베딩 3,000 × **1024차원** × 4B | **12.3 MB** ⚠️ |
| 임베딩 3,000 × **256차원** × 4B | 3.1 MB |
| 임베딩 3,000 × 256차원 × **int8** | **0.8 MB** |

> **차원 축소 없이는 임베딩이 원문 텍스트의 13배**다. 이건 저장 비용 문제가 아니라([FP-7](#93-fp-7-정정--언제든-재생성은-과장이었다) — 저장은 싸다) **인메모리 상주 가능성** 문제다.
> 256차원 int8이면 유저-캐릭터 쌍당 **0.8MB** → 동시 1,000세션도 0.8GB. **프로세스 메모리에 올릴 수 있다.**
> → [FP-1 Q9](03-architecture-modules.md)의 "세션 스코프 인메모리" 안이 실현 가능해진다.

### 3.3 저장소 결정

```
Postgres 단일 (+ pgvector)
  ├─ 인덱스 선행 컬럼은 항상 chat_id  (파티션 불필요, 카디널리티가 작음)
  ├─ 벡터도 같은 DB — 트랜잭션으로 사실/임베딩 정합성 확보
  └─ 형태소 역색인(BM25)은 pg_bigm 또는 별도 경량 인덱스
```
**근거:** 이런 서비스의 서버 팀은 대개 관계형 DB와 트랜잭션에 이미 익숙하다. 카디널리티가 작아 전용 벡터DB의 이득이 없고([FP-1](03-architecture-modules.md)), 장애 지점만 늘린다.
⚠️ **단, Qdrant/pgvector/인메모리 브루트포스 3안 실측은 여전히 [실험 D7](#8-이-데이터-모델이-만드는-실험-질문)로 남긴다.**

## 4. 쓰기 경로 — 추출 설계

**[00](00-research-briefing.md)에서 *"추출 품질이 시스템 상한을 결정한다"*고 써놓고 설계를 안 했다. 여기서 한다.**

### 4.1 3단 쓰기

| 티어 | 시점 | 무엇을 | 비용 |
|---|---|---|---|
| **동기** | 응답 생성과 **동시** | L2 상태 델타, L3 씬, `surfaced_count` | **추가 호출 0** ⭐ |
| **준실시간** | N턴마다 | L4 `session` 요약, L9 부채 등록 | **Flex 50%↓** |
| **배치** | **세션 종료 후** | L5 사실, L6 사건, L8 해석, 중요도 재계산, L4 `lifetime`, 임베딩 | **Batch 50%↓** |

### 4.2 동기 층 — 추가 호출 없이 상태를 갱신한다

L2·L3는 **즉시** 반영돼야 한다. 세션 끝까지 기다리면 *"헤어졌는데 계속 자기야"*가 그 세션 내내 발생한다.
그런데 별도 LLM 호출은 [지연 예산 200~400ms](05-cost-latency-reality.md)를 초과한다.

**해법: 응답 생성 시 구조화 출력을 함께 받는다.**
```
응답 본문 + <meta>
  state_delta: {stage: 헤어짐, last_emotion: 서운함}
  scene_delta: {place: 집앞}
  used_memories: [event:1204, fact:88]     ← surfaced_count 갱신
  new_debt: "다음에 제대로 얘기하기로 함"
</meta>
```
- 추가 호출 **0**, 출력 토큰 ~20개 = 턴당 $0.000075 (Flash). 무시 가능
- `used_memories`가 [L6 `surfaced_count`](#l6-사건)를 채운다 — [09 §2](09-what-memory-is-for.md)의 신호 측정이 여기서 가능해진다

⚠️ **리스크:** 모델이 서사와 메타를 동시에 처리하면 생성 품질이 떨어질 수 있다.
**대안:** 응답 후 비동기 경량 분류기 → 지연 0(응답은 이미 나감), **1턴 늦게 반영**.
→ **실험으로 결정** ([D9](#8-이-데이터-모델이-만드는-실험-질문)).

### 4.3 배치 층 — 세션 종료가 최적 시점

[09 §3](09-what-memory-is-for.md)에서 도출: **비용 최적 시점과 품질 최적 시점이 일치한다.**

```
세션 종료 감지 (N분 무응답)
  ├─ L5/L6 추출     : 세션 원문 → 사실·사건        (Batch)
  ├─ L8 Reflection  : 최근 사건들 → 해석 생성       (Batch)
  ├─ importance 계산 : 신규 항목 스코어링            (Batch)
  ├─ L4 lifetime    : 전체 재작성                   (Batch)
  ├─ 임베딩 생성    : 신규 항목만                    (로컬 or Batch)
  └─ session_end_note : 다음 세션 첫 턴 소재 생성    (Batch)
```

**추출 프롬프트가 반드시 해야 할 판정 3가지:**
1. **`realm`** — 픽션 안의 사실인가, 픽션 밖의 사실인가 ([§1.3](#13-왜-대화에서-추출한-실세계-사실도-chat-스코프인가))
2. **민감 범주 여부** — 해당하면 **추출하지 않는다** ([§6.1](#61-구조화하지-않을-것--프라이버시-))
3. **`importance` / `emotional_weight`** — 롤플레이 현저성은 사실 중요도가 아니라 감정 무게

### 4.4 실패 처리 — 조용한 손실을 막는다

[05 §5](05-cost-latency-reality.md)의 4대 실패 모드 중 **stale propagation**(갱신이 조용히 안 됨)이 가장 위험하다. 아무도 모르는 채로 기억이 사라진다.

```
turn.extract_status : pending → done | failed
  실패 시 → 3회 재시도 (지수 백오프)
  최종 실패 → coverage(resolution='extract_failed') 기록  ⭐
             → 시스템이 "그 시기는 잘 모르겠어"라고 정직하게 말할 수 있음
```
**멱등성:** `fact`의 `UNIQUE(chat_id, source_turn_seq, predicate, object)`가 재시도 시 중복을 막는다.

### 4.5 쓰기 경로 비용

```
세션 1회 (50턴) 추출:
  입력 50턴 × 130토큰 + 프롬프트 ≈ 7,000토큰
  출력 ≈ 400토큰
  Flash Batch: 7,000×$0.375/M + 400×$1.875/M ≈ $0.0034

턴당 상각: $0.0034 / 50 = $0.000068
→ [05 §3](05-cost-latency-reality.md)의 주입 비용 $0.0019/턴 대비 3.6%
```
**쓰기 경로는 싸다.** 비용 논쟁의 대상이 아니다.

## 6. 저장하지 않을 것

### 6.1 구조화하지 않을 것 — 프라이버시

캐릭터 챗 서비스의 태그에는 **집착·통제·노예** 같은 것이 있다. 유저가 매우 사적인 것을 말한다.

> **원문에 남는 것과, 구조화되어 검색 가능한 프로파일이 되는 것은 다른 리스크다.**
> `fact(유저, 성적_선호, "...")`는 유저가 준 데이터가 아니라 **우리가 만든 프로파일**이다.

**두 가지 리스크가 있고 둘 다 실재한다.**
1. **법률** — 한국 개인정보보호법상 민감정보(사상·신념·건강·**성생활**)는 별도 명시적 동의 필요. 추출·구조화·색인은 원문 보관과 법적 성격이 다를 수 있다 ⚠️ **법무 검토 필요 — 나는 법률 전문가가 아니다**
2. **제품** — [09 §5.2](09-what-memory-is-for.md): 감시 불쾌감은 **자기표현을 억제**하고, 그건 **기억할 재료를 고갈시키는 음의 되먹임**이다. 법에 안 걸려도 유저가 떠난다

**→ 설계:** 추출기에 민감 범주 **거부 목록**. 해당하면 L5에 안 만들고 **L0 원문 검색으로만** 접근(색인하지 않음). L4 요약에서도 추상 수준을 낮춘다.
**실제 목록은 [14 §3](14-extraction-prompts.md)에 있다** — 이 문서에서 *"목록을 둔다"*고만 하고 만들지 않았던 것이다.

> ### 🔴 그런데 `realm` 판정이 원리적으로 애매하다 ([14 §5](14-extraction-prompts.md))
> ```
> "나 이직했어"        → real
> "나 마법사야"        → fiction
> "나 회사에서 깨졌어"  → ???   ← 유저가 자기 캐릭터를 연기 중이면 fiction
> ```
> **그리고 이게 민감 범주 필터와 직결된다.** `fiction`이면 필터를 안 걸고 `real`이면 건다.
> **판정이 틀리면 유저의 실제 민감정보가 구조화되어 저장된다.**
>
> **→ 결정: 애매하면 `real`로 보고 필터를 건다.** 픽션을 잘못 거르는 손해(이야기 연속성 약간 손상)가
> 실제 민감정보를 잘못 저장하는 손해(법률·신뢰 붕괴)보다 훨씬 작다. **비대칭 손실에서는 안전한 쪽으로.**
> [02](02-problem-definition.md)의 precision 우선과 같은 논리다.

### 6.2 만들지 않을 데이터 구조

| 안 만드는 것 | 왜 |
|---|---|
| 임의 관계 지식그래프 | 1:1 관계에서 다중홉이 거의 없다. 복잡도만 추가 + [보안 우회면](05-cost-latency-reality.md) |
| 다차원 감정 벡터 | 해석·디버깅 불가. `last_emotion`(enum) + `emotional_weight`(스칼라)로 충분 |
| 유저 심리 프로파일 | 리스크 대비 이득 불명 |
| **턴별 임베딩 전량** | 사실·사건·해석만 임베딩하면 벡터가 3~7배 준다 ([§3.1](#31-1년-후-유저-캐릭터-쌍-하나당)) |
| 파생 메타의 사전 생성 | 필요해지면 L0에서 만들 수 있다 — ⚠️ 단 [§9.3](#93-fp-7-정정--언제든-재생성은-과장이었다)의 비용 확인 필요 |

### 6.3 저장하되 색인하지 않을 것
- 인사·추임새 등 **의례적 발화** — [FP-3](03-architecture-modules.md)의 "대화 엔트로피는 낮다"에 대한 실무 처방
- **민감 범주** — [§6.1](#61-구조화하지-않을-것--프라이버시-)
- **모델이 생성한 배경·날씨 묘사** — 유저 발화보다 정보 밀도가 현저히 낮다

## 7. 스키마 진화 — FP-7의 정정을 반영

모든 파생 테이블에 `schema_version`, `generator_version`을 둔 이유가 여기 있다.

| 규칙 | 근거 |
|---|---|
| **추가만 허용** (필드 삭제 금지, `deprecated` 표시) | 전면 재생성이 비싸다([§9.3](#93-fp-7-정정--언제든-재생성은-과장이었다)) |
| **버전 공존 허용** — v1/v2 레코드가 같이 존재 | 재생성을 미룰 수 있어야 한다 |
| **지연 재생성(lazy)** — 유저가 접속하면 그 유저부터 | 활성 유저 우선. 휴면 유저는 영원히 안 해도 됨 |
| **재생성 예산화** — 연 1~2회 대공사로 계획 | $82K~$640K/100만 유저 |

## 8. 이 데이터 모델이 만드는 실험 질문

| # | 질문 | 측정 |
|---|---|---|
| D1 | `speech_rules` 분리가 페르소나 유지도를 올리나 | `persona_adherence` (산문 내장 vs 분리) |
| D2 | `importance`(쓰기 시점)가 "빵 유언"을 억제하나 | `misinjection_rate` |
| D3 | L2 결정적 주입이 검색 대비 위반율을 낮추나 | `state_violation_rate` |
| D4 | 커버리지 메타가 abstention을 개선하나 | `hallucination_rate` |
| D5 | `surfaced_count` 페널티가 기억 반복을 줄이나 | `memory_repetition` |
| D6 | 사실/사건 분리가 stale fact를 줄이나 | `stale_fact_rate` |
| D7 | 사실·사건만 임베딩 시 회상 손실은 | `evidence_recall@k`, 벡터 수 |
| D8 | enum vs 자유 서술 상태의 토큰·정확도 | 토큰 + `state_violation_rate` |
| **D9** | **동기 구조화 출력이 생성 품질을 해치나** | `quality_score` (구조화 출력 유무) |
| **D10** | **L8 해석 주입이 사실 주입보다 PPR을 올리나** | `responsiveness_score` (같은 토큰 예산) |
| **D11** | **L9 부채 이행이 재방문에 영향을 주나** | `payoff_rate` × 세션 재개율 |
| **D12** | **차원 축소(1024→256)가 회상을 얼마나 잃나** | `evidence_recall@k` |

> **D10이 가장 중요할 수 있다.** [09](09-what-memory-is-for.md)의 핵심 주장 — *"해석이 사실을 이긴다"* — 이 참이면 같은 예산에서 **L8에 더 쓰고 L5/L6에 덜 쓰는 게 맞다.**

## 9. 미결정과 정정

### 9.1 여전히 열려 있는 것

| 항목 | 선택지 | 결정 방법 |
|---|---|---|
| 동기 메타 출력 방식 | 구조화 출력 / 비동기 1턴 지연 | D9 |
| `stage` enum 범위 | 고정 / 장르별 | D8 + 장르 분포 확인 |
| 임베딩 차원 | 1024 / 256 / int8 | D12 |
| L4 `session` 갱신 주기 | 5턴 / 10턴 / 씬 전환 시 | 비용 상각 vs 신선도 |
| 저장소 | pgvector / Qdrant / 인메모리 | D7 |

### 9.2 의도적으로 안 만든 것 — 되돌리기 쉬운 쪽

| | 결정 | 이유 |
|---|---|---|
| 캐릭터 간 기억 공유 | **안 함** | 나중에 열 수 있지만 샌 정보는 못 닫는다 ([08 §0](08-decisions-under-uncertainty.md) 원칙) |
| 캐릭터 능동 발신 | **스키마는 지원, 기능은 범위 밖** | L9 부채가 곧 발신 소재. 제품 결정 |
| 게임 요소 연동 | **범위 밖 명시** | 서비스별 게임 요소(보상 구조 등)를 모름 |

### 9.3 FP-7 정정 — "언제든 재생성"은 과장이었다

[FP-7](03-architecture-modules.md)에서 *"원본을 남기면 파생물을 언제든 재생성할 수 있다"*고 결론냈다. **재생성 비용을 계산하지 않았다.**

```
유저 1명 전면 재추출: 10,000턴 → 50턴 단위 200콜
  Flash(Batch)      약 $0.64/유저  →  100만 유저 $640,000
  Flash-Lite(Batch) 약 $0.08/유저  →  100만 유저  $82,000
```
> **저장은 유저당 $0.00005인데 재생성은 그 1,600~13,000배다.**
> **"언제든"이 아니다. 연 1~2회 하는 대공사다.**

**정정된 결론:**
- 원본 보관은 **여전히 옳다** — 저장 비용은 무시 가능하고, 재생성 *가능성* 자체가 자산이다
- 하지만 **"재생성하면 되니까 대충 설계해도 된다"는 잘못**이다. 스키마는 [§7](#7-스키마-진화--fp-7의-정정을-반영)처럼 **추가적으로만** 진화해야 한다
- 그리고 **파생 데이터를 버리지 말고 버전 태그를 붙여 공존**시킨다. 버리면 다시 만드는 데 돈이 든다

## 10. 요약

```
스코프    픽션 안(chat) / 픽션 밖(user, 명시 등록만) / 캐릭터(character, 버전 고정)

L0 원본   전부·영구.        파생물 재생성 가능성. 삭제는 법률 결정 (FP-7)
L1 정적   말투를 별도 필드.  산문에 묻히면 희석 (U4). 방은 생성 시 버전에 고정
L2 관계   enum + 노트.      항상 참 → 결정적 주입. 모순 검사 O(1)
L3 씬     현재 참여자.       제3자 난입을 상태 위반으로 (U6)
L4 요약   session/lifetime. 씬 하나가 원문에 안 들어가므로 2층
L5 사실   bi-temporal.      갱신 + 과거 조회. realm으로 픽션/실세계 구분
L6 사건   감정 무게.         surfaced_count로 신호 측정 + 반복 억제
L7 고유명사 정확 문자열.      임베딩이 지시체를 못 담음 (FP-4)
L8 캐릭터  해석/자기상태/의견. 유저의 거울이 되지 않게. 해석 > 사실
L9 부채   트리거 + 이행상태.  안 갚으면 관계가 손상됨 → 결정적 주입
M  커버리지 구간별 해상도.     "없었다" vs "흐릿하다" + 추출 실패 추적

안 만듦   지식그래프 / 감정벡터 / 심리프로파일 / 민감범주 구조화 / 턴별 전량 임베딩
```

**그 위의 원칙:**
> **저장은 거의 항상 예스, 주입은 거의 항상 노.** 비용이 50만 배 다르다.
> **그리고 재생성은 예스도 노도 아니다 — 연 1~2회 예산을 잡아야 하는 대공사다.**
