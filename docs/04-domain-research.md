## 1. 문제 정의를 바꾸는 발견들

### 발견 A — "기억 못 함"은 하나의 실패가 아니다 ⭐⭐

유사 서비스 A 유저 커뮤니티의 관찰:

> 답변을 재생성하면 대부분(약 70%) 다시 기억해서 이야기가 이어진다는 후기

**이 문장이 함의하는 것을 끝까지 밀어보자.**

재생성은 **컨텍스트를 바꾸지 않는다.** 같은 입력으로 다시 샘플링할 뿐이다.
그런데 70%가 복구된다면 → **정보는 이미 컨텍스트 안에 있었다.**
→ **그건 저장 실패도 검색 실패도 아니다. 생성 단계의 실패다.**

**→ 기억 실패를 3계층으로 분해한다:**

| 계층 | 실패 | 원인 | 메모리 구조로 풀리나 |
|---|---|---|---|
| **L1 저장(Retain)** | 아예 남기지 않음 | 쓰기 정책, 요약 손실 | ✅ M1·M2·M4 |
| **L2 검색(Recall)** | 남겼는데 못 찾음 | 색인·게이팅·선별 | ✅ M3·M6·M7·M8 |
| **L3 활용(Utilize)** | **찾아서 넣었는데 모델이 안 씀** | 위치 편향, 주의 희석, 샘플링 | ❌ **배치(M9)와 프롬프트로만** |

> **거의 모든 메모리 벤치마크가 L1+L2만 측정하고 L3를 측정하지 않는다.** 그래서 "메모리 시스템을 개선했는데 유저 불만이 그대로"인 상황이 생긴다.

**측정 방법 — 이건 이미 우리 실험에 들어있다:**
```
L3 실패율 = A1(Oracle) arm의 오답률
```
Oracle arm은 **정답 근거를 컨텍스트에 확실히 넣어준다.** 그런데도 틀리면, 그건 L3다.
→ **`A1 Oracle`의 역할이 "상한선 측정"에서 "L3 실패 격리"로 승격된다.** 이게 이번 조사의 가장 실용적인 산출물이다.

그리고 여기서 **투자 우선순위가 나온다:**
```
if L3 실패율이 크다면 → 메모리 구조를 아무리 고쳐도 상한이 낮다. 배치·프롬프트부터.
if L3 실패율이 작다면 → L1/L2 개선이 그대로 품질로 이어진다.
```
**이 한 숫자가 프로젝트의 방향을 정한다.** 실험 순서를 여기에 맞춰 바꿔야 한다.

### 발견 B — 5턴 기억 한계는 용량 문제가 아니다

> 기본 모델: **약 5턴**, 상위 모델: **15~20턴** 정도로 기억 한계가 보고됨

5턴이면 롤플레이 기준 **1,000토큰도 안 된다.** 어떤 현대 모델도 이걸 컨텍스트에 담는다.
**→ 용량(P1)이 병목이라는 통설의 반증이다.**

**메커니즘 — [FP-2](03-architecture-modules.md)에서 다룬 RoPE가 여기서 다시 나온다:**

> lost-in-the-middle의 구조적 원인은 **RoPE의 long-term decay 성질**이다. 멀리 떨어진 토큰 쌍의 내적 유사도를 감소시켜 컨텍스트 중간부의 어텐션 가중치를 체계적으로 낮추고, **softmax 정규화가 이를 증폭**시켜 최고점 토큰에 주의를 집중시킨다. 정확도는 정보 위치에 대해 **U자 곡선**을 그리며, 중간에 있으면 **30% 이상 하락**한다. — [Lost in the Middle (arXiv:2510.10276)](https://arxiv.org/pdf/2510.10276), [원논문](https://arxiv.org/pdf/2410.10813)

> **RoPE가 두 곳에서 동시에 작동한다는 게 핵심이다.**
> - [FP-2](03-architecture-modules.md): 절대 위치 회전 → **캐시 무효화**를 결정
> - 여기: long-term decay → **주목도 감쇠**를 결정
>
> 같은 메커니즘이 비용과 품질을 동시에 지배한다. **그래서 배치(M9)가 두 축 모두에 걸린 유일한 모듈이다.**

**설계 함의:** 기억을 "어디에" 넣느냐가 "얼마나 많이" 넣느냐보다 중요할 수 있다. U자 곡선의 양 끝(맨 앞/맨 뒤)만이 안전 지대다.
⚠️ 그런데 [FP-2](03-architecture-modules.md)의 캐시 규칙은 가변 블록을 **맨 뒤**로 보내라고 한다. **다행히 두 요구가 충돌하지 않고 같은 답을 가리킨다** — 가변 기억은 맨 뒤. 이건 운이 좋은 경우다.

### 발견 C — 유저가 이미 최적해를 찾아냈다 ⭐⭐⭐

유사 서비스 A 유저가 자기 시간을 써서 검증한 우회법 3가지와 그 평가:

| 방법 | 유저 평가 |
|---|---|
| 유저 프로필에 요약 기입 | 글자 수 제한 때문에 진행할수록 더 줄일 게 없어 **한계가 있다** |
| 기억력 좋은 상위 모델 섞어 쓰기 | 중요한 순간에 몇 턴씩 섞으면 괜찮다 |
| **외부 LLM 요약 → 나레이터로 주입** | 기본 모델을 써도 **기억력 붕괴가 거의 없다** ⭐ |

세 번째 방법의 구체적 절차:
1. 지금까지의 **모든 대화**를 긁어서 제미나이/GPT에 넣는다
2. 시간 순서대로 등장인물의 **감정선과 디테일**을 살려 요약시킨다
3. 나레이터 발화 형식으로 요약본을 대화에 주입한다
4. **5턴마다 반복**한다

불만은 품질이 아니라 **노동**이다: 프롬프트가 너무 길어지고, 매번 요약시키기가 지치고, 손이 많이 간다는 것

> **이건 통제된 실험은 아니지만, 유저가 자기 비용을 지불하고 반복 검증한 결과다.** 그리고 그 구조를 뜯어보면:
>
> | 유저의 우회법 | 아키텍처 용어 |
> |---|---|
> | 전체 대화를 서사적으로 요약 | **문서형 메모리 (M1-R2)**, 전체 재작성 |
> | 감정선과 디테일을 살린다 | **현저성 판단을 LLM에 위임 (M4-W3)** |
> | 시간 순서대로 | **타임라인 구조 (M5 시간축)** |
> | 나레이터 발화로 뒤쪽 주입 | **배치 = 최근 대화 뒤 (M9-K2)** |
> | 5턴마다 갱신 | **주기적 재작성 (증분 갱신 아님)** |
> | 외부 모델로 별도 처리 | **비동기 쓰기 경로 분리** |
>
> **벡터 검색이 없다.** 매번 전체를 다시 요약해서 통째로 넣는다.

**→ 이 발견이 실험 arm을 하나 강제한다.** `E2: 주기적 전체 재작성 문서형` — 증분 갱신이 아니라 **N턴마다 전체 히스토리를 다시 요약**하는 방식. 비싸 보이지만:
- 쓰기 경로라서 **배치 할인 대상**이고
- 5턴에 1회면 턴당 상각 비용이 1/5이며
- **요약의 요약으로 인한 열화(drift)가 없다** — 매번 원본에서 다시 만들기 때문

> ⚠️ **출처 신뢰도 주의:** 커뮤니티 개인 후기다. 방향성 근거로는 강력하지만 정량 근거가 아니다. **그래서 우리가 통제 실험으로 재현·검증하는 것이 이 검토의 기여가 된다.**

### 발견 D — 시장 전체가 문서형으로 수렴했다

주요 서비스의 메모리 기능을 실제 사양으로 비교했다.

| 서비스 | 유저 편집 문서 | 자동 요약 | 고정 주입(핀) | 구조화 사실 | 벡터 검색 |
|---|---|---|---|---|---|
| **유사 서비스 C** | 자유 서술 기억, 페르소나 수백 자(무료)~수천 자(유료) | 자동 기억 | **고정 기억 십여 개** — 대화가 길어져도 working context에 유지 | **구조화 사실** (페르소나/캐릭터/조연 탭 분리) — **유료 전용** | 표면상 없음 |
| **유사 서비스 B** | 유저 메모 **수백 자(무료) → 수천 자(유료)**, 프롬프트보다 우선 적용 | **요약 메모리** — 사건 타임라인과 캐릭터 관계 중심 | 특정 표기로 유지 확률↑ | 친밀도, 관계 마일스톤 | 표면상 없음 |
| **유사 서비스 A** | 유저 프로필 (수백 자) | 있음(개선 이력) | — | — | 표면상 없음 |

**세 가지 관찰:**

**① 아무도 벡터 검색을 제품 전면에 내세우지 않는다.** 전부 **문서와 필드**다.
→ [FP-1](03-architecture-modules.md)에서 원리적으로 도출한 회의론("유저당 파티션이 작아 ANN 인덱스의 전제가 성립하지 않는다")에 **시장 증거가 붙었다.** 내부적으로 쓸 수는 있지만, 제품의 중심은 아니다.

**② 유사 서비스 C의 "고정 기억(핀)"이 [02 P4](02-problem-definition.md)의 정확한 구현이다.**
> 핀으로 고정한 메시지는 대화가 얼마나 길어지든 모델의 working context에 남는다(기능 설명의 요지)
→ 이게 **결정적 주입(deterministic injection)**이다. 확률적 검색이 아니라. 내가 "상태는 검색 대상이 아니다"라고 주장한 것과 같은 결론에 제품이 먼저 도달해 있다.

**③ 유사 서비스 B의 요약 메모리가 "사건 타임라인 + 캐릭터 관계"라는 것.**
→ 내가 제안한 **사건(event) / 상태(state) 이원화와 동일한 축**이다. 프로덕션에서 수렴한 설계라는 뜻이다.
→ 그리고 유저가 다른 형식으로 고쳐도 다음 갱신 때 다시 타임라인 · 관계 형식으로 재구성된다 — **스키마를 강제**한다. 자유 서술이 아니라 구조화된 문서다.

> **결론:** 우리가 "문서형 + 상태 스키마"를 후보로 올린 것은 남들이 안 한 발명이 아니라, **시장이 이미 수렴한 지점을 원리로 재도출한 것**이다. 이건 오히려 좋은 신호다 — 그리고 **이 검토의 기여는 "왜 그것이 옳은지를 통제 실험으로 보이는 것"**이 된다.

### 발견 E — 메모리 용량이 과금 상품이다 ⭐

| 서비스 | 무료 | 유료 |
|---|---|---|
| 유사 서비스 B 유저 메모 | 수백 자 | **수천 자** |
| 유사 서비스 C 페르소나 | 수백 자 | **수천 자** |
| 유사 서비스 C 구조화 사실 | ❌ | **✅ 유료 전용** |
| 유사 서비스 C 고정 기억(핀) | 유료에서 먼저 제공 | |

> **메모리는 비용 센터가 아니다. 매출 상품이다.**

이건 [02 §1.3](02-problem-definition.md)의 목적함수를 한 번 더 정교하게 만든다. 나는 비용을 "제약조건"으로 강등했는데, 그것도 완전히 맞지는 않았다.

```
잘못:  minimize 비용
덜 맞음: 비용 ≤ 상한  (제약조건)
맞음:  기억 품질은 지불 의사(willingness to pay)와 직결된다
       → 원가 절감으로 확보한 예산을 "더 나은 기억"에 재투자할 수 있다
       → 그리고 그 기억 품질 자체를 상품화할 수 있다
```

**설계 함의:** 메모리 예산을 **티어별로 다르게** 줄 수 있다면, 아키텍처는 **예산 파라미터화**되어야 한다. 무료 유저 1,000토큰 / 유료 유저 4,000토큰이 같은 코드로 돌아가야 한다.
→ **모듈 설계에 "예산"이 1급 파라미터로 들어가야 한다.** 이건 [03](03-architecture-modules.md)에 없던 요구사항이다.

### 발견 F — 외부 API를 쓰는 서비스는 구조적 원가 열세에 있다

> 자체 소형언어모델(SLM)을 운영하는 유사 서비스 중에는 비용을 낮춰 흑자를 냈다고 알려진 곳이 있다(유사 서비스 A). B2C AI 시장에서는 드문 구조다.

반면 이 검토가 전제하는 서비스는 **외부 LLM Provider를 사용한다**.

```
자체 모델 보유 → 토큰당 단가를 직접 낮출 수 있음 (GPU 상각 + 최적화)
외부 API 사용 → 토큰당 단가가 고정. 낮출 수 있는 건 토큰 "수"뿐
```

> **→ 외부 API를 쓰는 서비스에게 컨텍스트 효율은 선택이 아니라 전략적 필수다.**
> 자체 모델이 없으면 **원가 곡선을 바꾸는 유일한 레버가 "턴당 토큰 수"와 "캐시 적중률"**이다.
>
> 이건 [02 §1.3](02-problem-definition.md)에서 "비용은 목적함수가 아니다"라고 한 것과 모순되지 않는다. **비용은 여전히 제약조건이지만, 외부 API를 쓰는 쪽에게는 그 제약이 자체 모델을 가진 곳보다 타이트하다.** 같은 품질을 더 적은 토큰으로 내야 한다.

## 2. 실측 규모 근거 — "수천~수만 턴"은 과장이 아니다

공개된 대형 캐릭터 챗 운영 사례의 수치(대략값):

| 항목 | 수치 |
|---|---|
| WAU | **백만 명대** |
| 채팅 모델 RPS | **초당 수천 요청** |
| 사용자당 체류 | **월 수십 시간 (주 10시간 안팎)** |
| 일평균 사용시간 | **2~3시간** |
| 인프라 | 여러 클라우드 리전, 쿠버네티스, 여러 세대의 GPU |
| 서빙 엔진 | **여러 오픈소스 서빙 엔진** |
| 동시 서빙 모델 | 수백 개 |
| 성과 | 비용과 운영 리소스를 크게 줄였다고 보고 |
| **향후 계획** | **공유 스토리지 기반 KV Cache 공유** (수백 대 GPU 인스턴스 간) ⭐ |

**턴 수 환산:**
```
일 2~3시간(가운데 160분으로 잡음) = 9,600초
턴당 20~60초 (읽기 + 작성 + 생성 대기) 가정
→ 하루 160 ~ 480턴
→ 월 5,000 ~ 14,000턴
→ 1년 6만 ~ 17만 턴
```

> **원래 질문의 "수천~수만 턴"은 헤비 유저 기준 한 달이면 도달한다.** 그리고 이 서비스들은 이미 1년 이상 운영 중이다.
> `O(N²)` 붕괴가 이론이 아니라 **이미 발생 중인 문제**임이 확인된다.

**그리고 KV Cache 공유가 프로덕션 레버임이 확인된다.** 그 운영 사례가 수백 대 GPU 간 공유 캐시를 다음 목표로 잡고 있다는 건, [FP-2](03-architecture-modules.md)에서 도출한 "캐시가 비용을 지배한다"가 현장에서 검증된 명제라는 뜻이다.

**참고 — 서빙 측 캐시 기술** (자체 서빙으로 전환할 경우 대비):
- **vLLM**: PagedAttention 기반, **블록 단위 해시 접두사 매칭**. 캐싱 패턴을 예측·구조화할 수 있을 때 유리
- **SGLang RadixAttention**: KV 블록을 **radix 트리 + LRU**로 관리해 자동으로 접두사 공유를 발견. **접두사 중복 60% 이상 워크로드에서 TTFT 대폭 감소**, 멀티턴 대화에서 vLLM 대비 약 10% 우위
→ **캐릭터 챗은 시스템 프롬프트·페르소나가 유저 간 공유되므로 접두사 중복률이 구조적으로 높다.** 자체 서빙 시 SGLang이 유력.

## 3. 새로 확보한 방법론 재료

### 3.1 현저성 스코어링의 고전 해법 — Generative Agents

[Generative Agents (arXiv:2304.03442)](https://ar5iv.labs.arxiv.org/html/2304.03442)의 memory stream 검색 함수:

```
score = α_recency · recency + α_importance · importance + α_relevance · relevance
        (논문에서는 모든 α = 1)

recency    : 마지막 접근 시점에 대한 지수 감쇠
importance : LLM이 1~10으로 ad hoc 채점 (저장 시 1회)
relevance  : 쿼리 임베딩과의 코사인 유사도
```

> **이게 [02 P2](02-problem-definition.md) 현저성 문제에 대한 가장 단순하고 검증된 답이다.**
> 그리고 [FP-6](03-architecture-modules.md)에서 "유사도만으로는 중요도를 잴 수 없다"고 도출한 것에 대한 구체적 처방이기도 하다 — **유사도에 중요도와 최근성을 곱하거나 더하는 것.**
>
> **"빵 사고"를 이 함수로 검증할 수 있다:** `importance("점심에 빵 먹음") ≈ 2/10`이면 relevance가 높아도 총점에서 밀린다.
> → **M7 슬롯의 강력한 후보이자, 값싸게 구현 가능한 옵션이다.** (importance는 쓰기 시점 1회 계산 → 배치 할인)

**Reflection(성찰)도 함께 제안된다:** 최근 기록들로부터 상위 수준의 통찰을 LLM이 추출하고, 근거 레코드를 인용한다.
→ 이건 **유사 서비스 B의 "요약 메모리"와 발견 C의 유저 우회법과 같은 계열**이다. 세 곳에서 독립적으로 같은 답이 나왔다.

### 3.2 비동기 쓰기 경로의 이름 — Sleep-time Compute

[Letta sleep-time agents](https://docs.letta.com/guides/agents/architectures/sleeptime/) / [논문 arXiv:2504.13171](https://arxiv.org/pdf/2504.13171):
> 주 에이전트와 **메모리를 공유하는 별도 에이전트**가 백그라운드에서 비동기로 메모리 블록을 수정한다. 대화 중 게으른 증분 갱신 대신, **유휴 시간에 메모리를 재구성·개선**한다. 응답 시간과 메모리 품질을 동시에 개선.

> 롤플레이는 **세션 간 유휴 시간이 길다**(유저가 앱을 닫고 몇 시간~며칠). 이건 sleep-time 처리에 이상적인 조건이다.
> → 발견 C의 "5턴마다 전체 재요약"을 **세션 종료 시점에 배치로** 돌리면 유저가 지연을 전혀 느끼지 않는다.

### 3.3 한국어 임베딩 모델

| 모델 | 특징 |
|---|---|
| **[KURE](https://github.com/nlpai-lab/KURE)** (고려대) | **BGE-M3를 한국어 검색용으로 추가 파인튜닝.** 한국어 검색 특화 — 1순위 후보 |
| **BGE-M3** | MTEB 한국어에서 다국어 모델 중 최고 수준, 검색·분류 우수, 긴 문서 대응 |
| **ko-sroberta** | KLUE-STS 고득점, 순수 한국어 태스크에 경쟁력. 단 110M~340M로 작고 **512토큰 초과 시 성능 급락**, 한영 혼합에 약함 |

- 리더보드: [mteb_ko_leaderboard](https://github.com/su-park/mteb_ko_leaderboard), [ko-embedding-leaderboard](https://onand0n.github.io/ko-embedding-leaderboard/)
- **결정:** KURE를 기본, BGE-M3를 대조군. 둘 다 로컬 실행 가능 → **[01 Phase 1](01-problem-and-hypotheses.md)이 키 없이 성립함이 확인됨.**
- ⚠️ 롤플레이 대사는 벤치마크 도메인(뉴스·위키·QA)과 분포가 다르다. **리더보드 순위가 우리 도메인에서 유지된다는 보장이 없으므로 자체 측정 필요.**

### 3.4 페르소나 일관성 측정의 근거

[02 §3.2](02-problem-definition.md)에서 `persona_adherence`를 새 지표로 제안했는데, 선행 연구가 있었다.

- **[PersonaGym](https://arxiv.org/html/2407.18416)**: 5개 축 — **Expected Action, Linguistic Habits, Persona Consistency, Toxicity Control, Action Justification**. 200 페르소나 / 150 환경 / 자동 생성 1만 문항. **PersonaScore**는 인간 판단과 정렬된 최초의 자동 지표라고 주장.
- **CharacterEval**: 중국어 롤플레이. 1,785 멀티턴 대화 / 77 캐릭터 / **4개 차원 13개 지표** (대화 능력, 역할 일관성, 롤플레이 매력, 성격 회상 테스트).

> **→ `persona_adherence`를 자체 정의하지 말고 PersonaGym의 축을 빌린다.** 특히 **Linguistic Habits**(말투 습관)는 유사 서비스 A의 U5(어미 반복)·U4(페르소나 붕괴)와 직결되고, 룰 기반으로도 부분 측정이 가능하다.

## 4. 갱신된 문제 정의

[02 §3](02-problem-definition.md)의 정의를 **폐기하지 않고 층을 하나 추가**한다.

```
기억 실패 = L1(저장) + L2(검색) + L3(활용)

  L1·L2 → 메모리 아키텍처의 문제        [02]의 P2 현저성 · P4 상태 일관성
  L3    → 배치·프롬프트·모델의 문제      [02]의 P3 페르소나와 같은 뿌리(위치 편향·주의 희석)
```

**그리고 실험 순서가 바뀐다.**

기존 계획: baseline → 대안들 → 비교
**변경:** **L3 실패율을 먼저 측정한다.**

```
Step 0.  A1(Oracle) arm만 돌려 L3 실패율을 잰다
         ├─ L3가 크다 (>20%?)  → 메모리 구조 개선의 상한이 낮다.
         │                        배치(M9)·프롬프트 실험을 앞으로 당긴다.
         └─ L3가 작다 (<10%?)  → L1/L2 개선이 그대로 품질이 된다.
                                  원래 계획대로 진행.
```

> **이 한 번의 측정이 남은 실험 전체의 방향을 정한다.** 그리고 값싸다 — arm 하나, 문항 60개.
> **"무엇을 먼저 측정할지 정하는 것"도 실험 설계의 일부**이고, 이번 조사가 그 답을 바꿨다.
