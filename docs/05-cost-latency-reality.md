## 0. 이 문서의 결론 먼저

> **메모리 아키텍처가 줄일 수 있는 비용은 총액의 약 40%다. 모델 등급을 한 단계 내리면 88%가 줄어든다.**
>
> **→ 메모리 시스템의 경제적 가치는 "토큰을 줄이는 것"이 아니라, "더 싼 모델로 내려가고도 품질을 유지할 수 있게 하는 것"이다.**

이건 [02 §1.3](02-problem-definition.md)에서 "비용은 목적함수가 아니라 제약조건"이라고 한 것을 정량적으로 뒷받침하면서, 동시에 **메모리의 역할을 재정의한다.**

> → 쓰기 경로를 **두 단계로 쪼갤 수 있다.** 급한 갱신은 Flex, 무거운 재구성은 Batch. 둘 다 50% 할인.

**⚠️ 중요한 제약 하나:**
[Interactions API에서는 explicit caching이 지원되지 않는다](https://ai.google.dev/gemini-api/docs/caching). 즉 **[H6](01-problem-and-hypotheses.md)에서 검증하려는 Interactions API와, [FP-2](03-architecture-modules.md)에서 도출한 명시적 캐시 전략은 서로 배타적일 수 있다.** 둘 중 하나를 골라야 한다면 어느 쪽이 더 큰지가 실험 질문이 된다.

## 2. 한국어 토큰 페널티 — 영어 벤치마크를 그대로 옮기면 안 된다

> 한국어는 영어 대비 평균 **2~3배** 토큰을 쓴다. 영어로 100토큰인 내용이 한국어로는 200~300토큰. 한글은 **1글자당 약 1.3~1.7토큰**으로 쪼개진다. 🔄 *프로토타입의 `ntok`(글자당 1.5)은 이 줄의 **Gemini** 가정에서 왔다. 로컬 `qwen3:8b` 실측은 글자당 0.72 안팎이다([ADR-016](adr/ADR-016-summary-layer.md) 결과 6) — 한 상수가 **두 모델을 겸한다**.*
> 토큰 효율은 **Gemini > GPT > Claude** 순.

**세 가지 함의:**

**① 컨텍스트 예산의 실질 가치가 1/3이다.**
```
4,000토큰 예산 = 영어 기준 약 1,300~2,000토큰어치의 정보량
```
→ **한국어 서비스에서 압축·구조화의 가치가 영어보다 3배 크다.** 같은 예산으로 1/3의 정보만 담기 때문이다.
→ 이건 [00](00-research-briefing.md)에서 인용한 영어 벤치마크 수치들(LongMemEval의 4K 예산 등)을 한국어로 옮길 때 **반드시 보정해야 한다는 뜻**이기도 하다.

**② Provider 선택에 근거가 생긴다.**
Gemini가 한국어 토큰 효율이 가장 좋다면, **같은 명목 단가에서 실질 단가가 더 싸다.** 단가표 비교만으로는 안 보이는 요인이다.
⚠️ 다만 이 순위는 2차 출처다. **자체 측정이 필요하다** — 같은 한국어 롤플레이 텍스트를 각 토크나이저에 넣어 토큰 수를 세면 30분이면 끝난다. Phase 1에 포함.

**③ 구조화의 이득이 커진다.**
`{관계단계: 연인, 호감도: 78}` 같은 구조화 필드는 자연어 서술보다 토큰이 훨씬 적다. 한국어에서는 이 격차가 더 벌어진다.

## 3. 턴당 원가 모델

### 3.1 가정 (전부 명시)

| 변수 | 값 | 근거 |
|---|---|---|
| 헤비 유저 월 턴 수 | **10,000턴** | [04 §2](04-domain-research.md) — 공개 운영 사례 체류시간(일 2~3시간) 환산 |
| 응답 출력 길이 | **400토큰** | 한국어 롤플레이 평균 추정 ⚠️ 2차 출처 |
| 컨텍스트 예산 B | 4,000토큰 | 실험 변수 |
| 캐시 적중률 h | 0 / 0.75 | 배치 전략에 따라 |

```
턴당비용 = B(1−h)·p_in + B·h·p_cached + O·p_out
          + (쓰기경로비용 × 0.5) / 상각턴수      ← Batch/Flex 할인
          + 임베딩비용 + 인프라고정비/턴
```

### 3.2 계산 — Gemini 3.7 Flash

| 시나리오 | 입력 비용/월 | 출력 비용/월 | **합계/월** | 출력 비중 |
|---|---|---|---|---|
| B=4,000, **캐시 없음** (h=0) | $30.00 | $15.00 | **$45.00** | 33% |
| B=4,000, **캐시 75%** (h=0.75) | $9.75 | $15.00 | **$24.75** | **61%** |
| B=2,000, 캐시 75% | $4.88 | $15.00 | **$19.88** | 75% |
| **B=0 (컨텍스트 완전 제거)** | $0 | $15.00 | **$15.00** | **100%** |

> ### ⚠️ 여기서 결론이 하나 나온다: **출력 비용 바닥**
>
> **컨텍스트를 0으로 만들어도 $15/월이 남는다.**
> Gemini Flash에서 **출력 단가가 입력 단가의 5배**($3.75 vs $0.75)이고, 롤플레이는 응답이 길다.
>
> → **메모리 최적화가 건드릴 수 있는 것은 총비용의 40% 정도다.**
> → 캐시를 켜서 $45 → $24.75로 45% 줄인 뒤에는, **남은 61%가 메모리와 무관한 출력 비용**이다.

**그리고 이건 [02 U8](02-problem-definition.md)과 연결된다.**
유사 서비스 A 유저 불만 중 응답이 스크롤해야 할 만큼 길고 대부분이 중요하지 않은 배경 · 날씨 묘사라는 것 — 나는 이걸 "메모리와 무관한 생성 제어 문제"로 분류했다. 맞다. 하지만 **동시에 비용의 61%를 차지하는 문제**다.
→ **응답 길이를 400 → 250토큰으로 줄이면 품질도 오르고 비용도 37% 준다. 파레토 개선이다.** 드문 경우이므로 리포트에 명시할 가치가 있다.

### 3.3 모델을 바꾸면 — 이게 진짜 레버다

| 모델 | 입력(B=4k, h=0.75) | 출력(400tok) | **합계/월** | Flash 대비 |
|---|---|---|---|---|
| Gemini 3.7 Flash | $9.75 | $15.00 | **$24.75** | 1.0× |
| Gemini 3.1 Flash-Lite | $3.25 | $6.00 | **$9.25** | 2.7× 저렴 |
| **Gemini 2.5 Flash-Lite** | **$1.30** | **$1.60** | **$2.90** | **8.5× 저렴** |

```
메모리 아키텍처로 절감 가능:  $45.00 → $24.75   (45%↓)
모델 등급 한 단계 내리기:      $24.75 → $2.90   (88%↓)
```

> ### ⭐ 핵심 결론 — 메모리의 경제적 역할이 바뀐다
>
> 모델 선택이 메모리 아키텍처보다 **약 8배 큰 비용 레버**다.
> 그런데 모델을 내리면 **품질이 떨어진다.**
>
> **→ 그러므로 메모리 시스템의 진짜 경제적 가치는 토큰 절감이 아니다.**
> **→ "더 싼 모델로 내려가고도 품질을 유지할 수 있게 하는 것"이다.**
>
> 그리고 [FP-5 Q6](03-architecture-modules.md)에서 찾은 반직관적 사실이 여기 붙는다:
> **작은 모델이 노이즈에 더 강하고, 큰 모델이 더 쉽게 산만해진다.**
> → **정밀한 메모리 + 작은 모델** 조합이 원리적으로 유망하다. 작은 모델은 애초에 노이즈에 덜 흔들리고, 좋은 메모리는 노이즈를 줄여준다. 두 효과가 같은 방향이다.

**→ 실험 arm이 하나 추가된다: `모델 × 메모리 구조` 교차.**
같은 메모리 구조를 Flash와 Flash-Lite에서 각각 돌려, **"좋은 메모리가 작은 모델의 품질 손실을 얼마나 보상하는가"**를 측정한다.
이게 사업적으로 가장 값어치 있는 숫자다: *"메모리를 이렇게 바꾸면 Flash-Lite로 내려가도 품질이 유지됩니다. 원가가 8.5배 줄어듭니다."*

### 3.4 그래서 흑자가 나는가 — 안 난다

한국 모바일 광고 단가: 리워드 광고 eCPM **약 2,300원**, 전면 광고 **약 1,600원** (2026)

```
헤비 유저 월 광고 수익 (낙관적 추정)
  리워드 일 10회 = 월 300회 → 0.3 × 2,300원 = 690원
  전면   일 20회 = 월 600회 → 0.6 × 1,600원 = 960원
  합계 ≈ 1,650원 ≈ $1.2/월     (1,400원/USD 가정)
```

| 모델 | 원가/월 | 광고수익 대비 |
|---|---|---|
| Gemini 3.7 Flash (캐시 있음) | $24.75 | **20배 초과** |
| Gemini 2.5 Flash-Lite | $2.90 | **2.4배 초과** |

> **헤비 유저는 어떤 모델·어떤 메모리 구조로도 광고만으로 흑자가 안 난다.**

그래서 선택지는 셋뿐이다:
1. **자체 모델로 단가 자체를 낮춘다** ← [유사 서비스 A가 한 것](04-domain-research.md). 외부 API를 쓰면 불가
2. **유료 전환** — 헤비 유저를 결제로 유도
3. **티어별 예산 차등** — 무료는 작은 예산 + 싼 모델, 유료는 큰 예산 + 좋은 모델

> **그리고 2번의 지렛대가 바로 메모리다.**
> [04 발견 E](04-domain-research.md): 유사 서비스 B는 유저 메모를 수백 자 → 수천 자 유료로, 유사 서비스 C는 구조화 사실을 유료 전용으로 판다. **메모리 품질이 곧 지불 의사다.**
>
> **논리가 닫힌다:**
> ```
> 메모리 품질 ↑ → (a) 유료 전환률 ↑        [수익]
>                → (b) 더 싼 모델 사용 가능 ↑ [원가]
> ```
> **메모리는 비용 센터도, 단순 품질 기능도 아니다. 원가와 수익 양쪽에 동시에 작용하는 유일한 레버다.**
> 이게 이 검토에서 내릴 수 있는 가장 사업적인 주장이고, [02 §1.3](02-problem-definition.md)의 목적함수를 최종적으로 완성한다.

**설계 요구사항 확정:** 아키텍처는 **예산 파라미터화**되어야 한다.
```
무료 티어:  B=1,000, Flash-Lite, 문서형만
유료 티어:  B=4,000, Flash,      문서형 + 검색 + 상태
→ 같은 코드, 다른 파라미터
```

## 4. 지연 예산 분해

### 4.1 체감 임계

| 임계 | 체감 | 출처 |
|---|---|---|
| **< 200ms** | 즉각적 | 널리 쓰이는 무지연 임계 |
| **< 300ms (P99)** | 채팅에서 이상적 — 유저가 지연을 인지하지 못하고 읽기 시작 | LLM SLO 가이드 |
| **< 500ms** | 반응적 | |
| **< 1,000ms** | 사고 흐름은 유지되나 지연을 인지함 | Nielsen 3대 임계 |
| **> 2,000ms** | *"같은 총 시간에 같은 답을 줘도 고장난 것처럼 느껴진다"* | |

### 4.2 메모리 파이프라인 예산 배분

TTFT p95 목표를 **1,000ms**로 잡고, 모델 자체 TTFT를 400~600ms로 가정하면:

```
사용 가능한 메모리 파이프라인 예산 = 약 200 ~ 400ms
```

| 모듈 | 옵션 | 지연 | 예산 대비 | 판정 |
|---|---|---|---|---|
| M6 게이팅 | 룰 | ~0ms | 0% | ✅ |
| M6 게이팅 | 소형 분류기 | ~5ms | 2% | ✅ |
| M6 게이팅 | **LLM 판단** | 200~800ms | **50~400%** | ❌ 예산 초과 |
| M3/M7 검색 | 인메모리 브루트포스 | ~1ms | 0.5% | ✅ |
| M3/M7 검색 | Qdrant 네트워크 | 1~5ms | 2% | ✅ |
| M8 선별 | 점수 임계 | ~0ms | 0% | ✅ |
| M8 선별 | **크로스인코더 리랭커** | 20~50ms | **10~25%** | ✅ 안전 |
| M8 선별 | **LLM Selector** | 200~800ms | **50~400%** | ❌ 예산 초과 |
| M10 검증 | 룰 | ~1ms | 0.5% | ✅ |
| M10 검증 | LLM 검증+재생성 | +전체 1회 | 200%+ | ❌ |

> **[H2](01-problem-and-hypotheses.md)에 정량 근거가 붙었다.**
> LLM Selector는 메모리 파이프라인 예산 전체를 먹거나 초과한다. 반면 크로스인코더 리랭커는 10~25%만 쓴다.
> 그리고 [FP-6](03-architecture-modules.md)에서 "Selector의 기능은 원리적으로 필요하다"고 결론냈다.
> **→ 기능은 유지하고 구현을 리랭커로 바꾼다.** 근거가 원리(FP-6)와 수치(여기) 양쪽에서 나왔다.

## 5. 운영 실패 모드 — ADR "새로 생기는 장애 지점"에 들어갈 것

멀티테넌트 메모리 시스템의 실패 유형 4가지가 정리되어 있다:

| 실패 모드 | 내용 | 우리 설계에서의 위험 |
|---|---|---|
| **Unauthorized leakage** | 권한 밖 메모리를 검색 | 유저 A의 기억이 유저 B에게 — **캐릭터 챗에서 치명적** (사생활) |
| **Stale propagation** | 갱신이 동기화되지 않음 | 비동기 쓰기 경로의 고유 위험. 요약은 갱신됐는데 사실 저장소는 안 됨 |
| **Contradiction persistence** | 모순이 해소되지 않고 누적 | [02 P4](02-problem-definition.md)·[M5](03-architecture-modules.md)가 직접 다루는 문제 |
| **Provenance collapse** | 기억의 출처 추적 불가 | *"왜 이걸 기억했지?"*를 디버깅 못 함 |

**추가로 확인된 것:**
- 벡터 검색 계층에서 권한을 강제해도 **그래프 순회로 우회**될 수 있다 → 두 계층 모두에서 검사 필요. **[FP-1](03-architecture-modules.md)의 "그래프DB를 안 쓴다"는 결정에 보안 근거가 하나 더 붙는다.**
- vLLM 자체 서빙 시: **KV 캐시 축출**로 진행 중 시퀀스가 선점되면 재계산이 필요해 **p99가 중앙값의 몇 배로 튄다**. 평균 처리량은 그대로라 **모니터링에서 놓치기 쉽다.**

> **설계 함의 — provenance를 1급 요구사항으로 승격한다.**
> 모든 주입된 기억에 `(출처 턴 ID, 생성 시각, 주입 이유, 점수)`를 남긴다.
> 비용은 거의 0인데, *"왜 유언이 빵 먹고 싶다가 됐는가"*를 사후에 추적할 수 있는 유일한 방법이다.
> 이런 서비스의 서버 개발에서 흔히 요구하는 지표와 로그로 병목을 찾는 일과도 정확히 맞는다.

## 6. FP-3 업그레이드 — 망각의 이론적 틀

[FP-3](03-architecture-modules.md)에서 "망각 = 캐시 교체 문제와 동형"이라고 도출했다. 한 단계 더 내려갈 수 있는 근거를 찾았다.

**[What to Keep, What to Forget: A Rate-Distortion View of Memory Compaction (arXiv:2607.08032)](https://arxiv.org/pdf/2607.08032)**

> 메모리 압축을 **rate-distortion 문제**로 정식화한다.
> - **Rate**: 유지하는 정보의 크기/비용
> - **Distortion**: 정보 손실로 인한 성능 저하
> **information bottleneck 원리**와 연결 — 미래 토큰 예측을 위한 **최소 충분 통계**를 찾는 문제.
> LRU/LFU 같은 전통적 캐시 교체는 **태스크를 모른다(task-agnostic)**. rate-distortion 접근은 **출력에 미치는 영향**에 근거해 결정하므로 위치·빈도 기반 방법을 능가한다.

**→ FP-3에 Q6를 추가한다:**

> **Q6. 캐시 교체와 메모리 망각은 정말 같은 문제인가?**
> → **아니다. 결정적인 차이가 하나 있다.**
>
> | | 캐시 교체 | 메모리 망각 |
> |---|---|---|
> | Distortion | **이진** — 히트 아니면 미스 | **연속** — "얼마나 나쁜 답을 하는가" |
> | 부분 정보 | 무의미 (반쯤 캐시된 페이지는 없음) | **유의미** — 요약본은 원문의 부분 정보 |
> | 대체 가능성 | 없음 | **있음** — 다른 기억으로 유추 가능 |
>
> **→ 그래서 LRU 유추는 여기까지다.**
> 메모리는 "버리거나 남기거나"가 아니라 **"얼마나 압축할 것인가"**라는 연속 결정이고, 이건 rate-distortion 문제다.
> **→ 그리고 이것이 [FP-3 Q5](03-architecture-modules.md)의 결론("최적을 추구하지 말고 oracle 격차를 재라")을 강화한다.** 연속 distortion 공간에서는 최적해가 더더욱 닫힌 형태로 안 나오지만, **oracle과의 거리는 여전히 측정 가능**하다.

**실무 정책도 확인됐다:**
> 장기 방치 항목에 **TTL**, 검색 점수에 **LRU식 감쇠**, 그리고 **모든 쓰기에서 능동적 대체(active supersession)** — 그래야 모순이 누적되지 않는다.
→ [M5-C3 bi-temporal 무효화](03-architecture-modules.md)와 같은 처방이다. 독립적으로 같은 결론.

## 7. 그 외 확보한 재료

### 7.1 프롬프트 압축 (M1 슬롯 추가 옵션)

- **LLMLingua**: 최대 20배 압축에서 품질 손실 2% 미만 (CoQA/HotpotQA/TriviaQA)
- **LLMLingua-2**: 2~5배 압축에서 **종단간 지연 최대 2.9배 감소**
- **LongLLMLingua**: 질문 인지형 압축, 약 4배 적은 토큰으로 **성능 21.4% 향상**
- 실무 기준: **30~70% 입력 토큰 감소는 정확도 손실이 미미**. 80% 초과부터 측정 가능한 손실

> ⭐ **"압축이 비용뿐 아니라 품질도 올린다"**는 관찰이 있다 — **RAG 컨텍스트에서 노이즈를 걸러내기 때문**이다.
> → [FP-5](03-architecture-modules.md)("무관한 컨텍스트는 중립적이지 않고 해롭다")와 정확히 같은 메커니즘이다. **압축은 우연히 현저성 필터로도 작동한다.**
> ⚠️ 단 압축기 자체가 추론 비용과 지연을 추가한다. 응답 경로에 넣으면 [§4](#4-지연-예산-분해) 예산을 먹는다. **쓰기 경로에서만 쓰는 게 맞다.**

### 7.2 LLM-as-judge의 신뢰성 — 우리 평가 전체가 여기 의존한다

| 편향 | 현황 |
|---|---|
| **위치 편향** | 심판 모델 선택이 가장 큰 영향. 15개 심판 / 약 15만 사례에서 심판·태스크별로 편차 큼 |
| **장황함 편향** | 2023년엔 15~30점 부풀림. **2026년 기준 MT-Bench에서 21개 심판 전부 0.011 미만으로 감소** |
| **자기 선호** | 자기 생성물을 알아보고 선호. **자기 인식 능력과 선호 강도가 선형 상관** |
| **교정** | **각 태스크마다 인간 라벨로 경험적 교정이 필요.** Cohen's κ > 0.6 수용, > 0.8 강함 |

**→ 평가 프로토콜을 이에 맞춰 확정한다:**
1. **심판 모델을 생성 모델과 다른 벤더로** (자기 선호 차단) — Gemini 생성 / Claude 또는 GPT 심판
2. **A/B 위치 무작위화 + 순서 뒤집어 재평가**, 두 결과가 다르면 위치 편향으로 기록
3. **인간 라벨 20~30건으로 κ 교정** — 전부는 못 하니 표본으로
4. 심판을 **arm에 대해 블라인드**로

> ⚠️ **정직하게 남길 한계:** 짧은 기간 안에 완전한 인간 교정은 불가능하다. **"κ 교정을 표본으로만 했다"는 것을 리포트에 명시**한다. 방법론의 한계를 아는 것과 모르는 것은 다르다.

### 7.3 모순 탐지 (M10 검증 모듈 구현안)

- **NLI**를 2-way(contradiction / non-contradiction)로 축소해 쓰는 방식이 표준
- **Dialogue NLI** 데이터셋 (PersonaChat 기반, fact-utterance / fact-fact / utterance-utterance 쌍)
- ⚠️ 한계: NLI 모델은 **가짜 상관(spurious correlation)에 취약**하고, **대화 맥락 없이 claim만 보면 담화 수준 단서를 놓친다**

> **→ M10-V3(상태 모순 검사)를 NLI가 아니라 스키마 비교로 구현하는 근거가 된다.**
> `{관계단계: 헤어짐}`인데 응답에 "자기야"가 나오면 정규식으로 잡힌다. NLI보다 빠르고 정확하고 설명 가능하다.
> **구조화의 이득이 또 하나 나온다** — 구조화된 상태는 모순 검사를 O(1) 문자열 비교로 만든다.

> ### 🔄 실측 후 정정 — **과했다** ([11 실험 9](11-experiment-results.md))
>
> | 가드 | 정밀도 | 재현율 |
> |---|---|---|
> | 순수 정규식 | 50% | 57% |
> | **+ 억제 문맥 처리** | **100%** | **57%** |
>
> **정밀도는 100%까지 올릴 수 있지만 재현율이 57%에서 멈춘다.**
> *"우리 다시 만나서 진짜 좋다"* @ `stage=헤어짐` 같은 **의미적 위반은 금지어가 없어 원리적으로 못 잡는다.**
>
> **→ 스키마 비교는 NLI를 *대체*하는 게 아니라 NLI가 *필요한 양을 줄인다*.**
> 정밀도 100%라는 특성이 유용하다 — **울리면 반드시 맞으므로 재확인 없이 조치 가능**하고, 놓친 것만 비싼 검증으로 보내면 된다.
>
> ⚠️ 그리고 롤플레이는 **자기 언급이 잦다**(관계를 이야기하는 게 콘텐츠다). 억제 문맥(인용·부정·회상) 처리 없는 순수 금지어 매칭은 **이 도메인에서 쓸 수 없다** — FP 50%였다.

### 7.4 감정 기억 벤치마크 (A-MBER)

**[A-MBER (arXiv:2604.07017)](https://arxiv.org/abs/2604.07017)**: 멀티세션 상호작용 이력에 근거해 **현재 감정 상태를 해석**하는 능력을 평가.
세 작업군: **판단**(현재 감정 상태 추론), **검색**(관련 과거 턴 식별), **설명**(이력에 근거한 정당화).

> 기존 메모리 벤치마크는 사실 회상·시간 일관성·지식 갱신에 집중하는데, **A-MBER는 감정 해석을 본다.**
> → 롤플레이/컴패니언에 [02 §3.2](02-problem-definition.md)에서 정의한 지표들보다도 더 직접적이다.
> → **"검색" 작업군이 특히 유용하다** — 감정 해석에 필요한 과거 턴을 찾아내는 능력은 우리의 `evidence_recall@k`를 **감정 축으로 확장**한 것이다.
> **📌 시간이 되면 채택, 아니면 지표 설계에만 참고.**
