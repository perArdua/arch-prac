## 1. 왜 이렇게 자르는가 — 분해 원칙

모듈 경계를 아무 데나 그으면 안 된다. 좋은 경계는 **교체 가능성(substitutability)**이 있는 곳이다. 즉 **"이 안의 구현을 바꿔도 바깥 인터페이스가 안 바뀌는" 지점**에 선을 긋는다.

메모리 시스템을 자르는 축은 두 개다.

**축 1 — 시간축: 쓰기 경로 vs 읽기 경로**
```
쓰기(비동기, 지연 민감도 0)  :  대화 → [표현] → [분할] → [중요도] → [갱신] → [색인]
읽기(동기, 지연이 곧 품질)   :  발화 → [게이팅] → [검색] → [선별] → [배치] → LLM → [검증]
```
이 축이 1급인 이유: **지연 예산이 완전히 다르다.** 쓰기는 초 단위를 써도 되고 배치 할인도 받는다. 읽기는 밀리초 단위다. 같은 연산(예: LLM 추출)이라도 어느 쪽에 놓느냐로 비용과 지연이 10배 갈린다.

**축 2 — 데이터 성격: 상태(state) vs 사건(event)**
[02 P4](02-problem-definition.md)에서 도출한 구분.
```
상태: 항상 참이어야 함 → 결정적 주입, 고정 토큰, 덮어쓰기
사건: 필요할 때만      → 확률적 주입, 가변 토큰, 누적
```
이 둘을 하나의 파이프라인으로 다루면 둘 다 못 한다. **"관계 단계"를 벡터 검색에 맡기는 순간 top-k에서 밀려날 수 있고, 그건 설계 오류다.**

→ 이 두 축의 교차로 아래 10개 모듈이 나온다.

```
┌─ 쓰기 경로 (비동기) ────────────────────────────────┐
│  M1 표현(Representation)  ← 무엇을 어떤 형태로       │
│  M2 분할(Segmentation)    ← 어떤 단위로              │
│  M4 쓰기정책(Write Policy) ← 무엇을 남기고 버리나     │
│  M5 갱신/충돌(Reconcile)  ← 모순을 어떻게            │
│  M3 색인(Indexing)        ← 어떻게 찾을 수 있게      │
└─────────────────────────────────────────────────────┘
┌─ 읽기 경로 (동기) ──────────────────────────────────┐
│  M6 게이팅(Gating)        ← 언제 검색하나            │
│  M7 검색(Retrieval)       ← 무엇을 후보로            │
│  M8 선별(Selection)       ← 후보 중 무엇을           │
│  M9 배치(Packing)         ← 프롬프트 어디에, 어떤 꼴로│
│  M10 검증(Guard)          ← 응답 후 확인하나         │
└─────────────────────────────────────────────────────┘
```

## 2. 모듈별 선택지와 트레이드오프

### M1. 표현 (Representation) — 말을 어떤 형태로 남길 것인가

> 사용자가 지적한 "OpenSearch식 의미 단위 분할 말고 다른 방식"이 여기다. 실제로 6가지 계열이 있다.

| 옵션 | 형태 | 얻는 것 | 잃는 것 |
|---|---|---|---|
| **R1 원문 보존** | 턴 텍스트 그대로 | 정보 손실 0, 뉘앙스·말투 보존, 쓰기 비용 0 | 부피 큼, 노이즈 그대로, 모순 공존 |
| **R2 요약(abstractive)** | "3월에 이직 얘기를 나눔" | 압축률 높음, 서사 흐름 보존 | **비가역 손실**, 요약의 요약으로 열화(drift), 쓰기에 LLM 필요 |
| **R3 사실 문장(fact)** | "유저의 고양이 이름은 나비" | 갱신/무효화 가능, 검색 정밀도↑, 토큰 효율 최상 | 추출 실패 = 영구 소실, **말투·감정 소실**, 쓰기 LLM 필요 |
| **R4 트리플(triple)** | `(유저, 반려동물, 나비)` | 구조적 질의, 그래프 확장, 모순 탐지 자동화 | 자연어 뉘앙스 완전 소실, 스키마 설계 부담, 관계 추출 정확도 병목 |
| **R5 구조화 상태(schema)** | `{관계단계: 연인, 호감도: 78}` | **결정적 주입**, 고정 토큰(캐시 가능), 모순 원천 차단 | 스키마에 없는 건 못 담음, 스키마 진화 = 마이그레이션 |
| **R6 잠재 벡터만** | 임베딩만 저장, 원문 폐기 | 저장 최소 | **프롬프트에 못 넣음** (텍스트로 복원 불가) → 검색 키로만 쓸 수 있음 |

> **R6이 왜 "선택지가 아닌가"를 이해하는 게 중요하다.** 임베딩은 검색용 색인이지 컨텍스트 재료가 아니다. LLM은 텍스트를 먹는다. → **표현(M1)과 색인(M3)은 다른 모듈**이라는 게 여기서 확인된다.

**핵심 통찰:** 이건 배타적 선택이 아니다. **표현마다 잘하는 게 다르다.**
- 페르소나·말투 유지 → R1/R2 (뉘앙스가 살아있어야 함)
- 사실 회상·갱신 → R3
- 항상 참인 상태 → R5
→ **"어떤 정보를 어떤 표현으로 남길 것인가"의 라우팅**이 진짜 설계 결정이다. 단일 표현을 고르는 게 아니라.

### M2. 분할 (Segmentation) — 어떤 단위로 자를 것인가

| 옵션 | 단위 | 근거/수치 |
|---|---|---|
| **S1 고정 토큰** | 256/512 토큰 | 단순. [벤치마크에서 91% 정확도 — 의미 분할과 사실상 동급](https://arxiv.org/html/2602.16974) |
| **S2 턴(라운드)** | 유저-캐릭터 1왕복 | [LongMemEval: 세션 단위 대비 고정 예산에서 최대 +6%p](https://arxiv.org/pdf/2410.10813) |
| **S3 세션** | 대화 세션 1개 | 문맥 온전. 단 덩어리가 커서 예산 낭비 |
| **S4 의미 경계** | 임베딩 유사도 급변점 | 코히런스↑. 단 **비용 대비 이득이 비례하지 않음** |
| **S5 이벤트 경계** | 서사적 사건 단위 | 롤플레이에 개념적으로 맞음. 경계 탐지가 어려움 |
| **S6 명제(proposition)** | 원자 명제로 분해 | ⚠️ **정확도 72% — 고정(91%)보다 크게 나쁨.** 과도 세분화가 문맥 연속성 파괴 |
| **S7 Late chunking** | 문서 전체 인코딩 후 분할 | 대명사·참조 보존, [nDCG +1.9~6.5%p](https://medium.com/kx-systems/late-chunking-vs-contextual-retrieval-the-math-behind-rags-context-problem-d5a26b9bbd38). 실시간엔 비효율 |

> **S6이 나쁜 이유가 우리 도메인엔 특히 치명적이다.** 롤플레이 대사는 그 자체로 원자 명제가 아니다. *"...그래서 말인데."* 같은 발화는 앞뒤가 없으면 무의미하다. 명제화하면 **말투가 죽고 화자 정보가 날아간다.**
>
> 반대로 **S2(턴)가 유력한 이유**: 대화는 원래 턴 단위로 구조화되어 있다. 인위적 경계를 만들 필요가 없다. **자연 경계가 있으면 그걸 쓰는 게 거의 항상 맞다.**

### M3. 색인 (Indexing) — 어떻게 찾을 수 있게 할 것인가

| 옵션 | 방식 | 강점 | 약점 |
|---|---|---|---|
| **I1 BM25 (형태소)** | nori 등 형태소 분석 후 역색인 | **고유명사·별명·설정어**에 강함, 결정적, 설명 가능 | 어휘 불일치("걔"↔"나비")에 취약 |
| **I2 Dense (임베딩)** | 벡터 유사도 | 어휘 불일치 극복, 의역 대응 | **고유명사·인스턴스 식별에 약함** (→ FP-4) |
| **I3 Hybrid** | BM25 + Dense + RRF/가중합 | [단순 dense 대비 Recall +5~12%](https://velog.io/@autorag/RAG%EC%97%90%EC%84%9C-BM25%EA%B0%80-%EB%8D%94-%EC%A2%8B%EC%9D%84-%EC%88%98%EB%8F%84%EC%9E%88%EC%8A%B5%EB%8B%88%EB%8B%A4) | 두 인덱스 운영, 가중치 튜닝 |
| **I4 시간 인덱스** | 타임스탬프 B-tree | "지난주에" 류 질의에 필수 | 단독으로는 무력 |
| **I5 직접 조회(KV)** | `user_id → state` 단일 행 | O(1), 100% 정확, 캐시 가능 | 스키마에 있는 것만 |

> **한국어 데이터는 방향이 엇갈린다.** 어떤 데이터셋에선 dense가 BM25 대비 Recall@5 +19%, 반면 한국어 금융 문서에선 **BM25가 벡터 검색보다 5배 좋았다.** → **일반론으로 결정할 수 없다. 우리 데이터로 재야 한다.** 이게 이 모듈을 슬롯으로 남기는 이유다.

### M4. 쓰기 정책 (Write Policy) — 무엇을 남기고 무엇을 버릴 것인가

**[02 P2 현저성](02-problem-definition.md)의 절반이 여기서 결정된다.**

| 옵션 | 정책 | 얻는 것 | 잃는 것 |
|---|---|---|---|
| **W1 전부 저장** | 필터 없음 | 손실 0, 구현 0 | 노이즈 축적 → 검색 정밀도 하락 |
| **W2 휴리스틱 필터** | 길이·품사·개체명 유무 | 비용 0, 결정적 | 감정적 중요도를 못 봄 |
| **W3 LLM 중요도 스코어** | 배치로 0~1 점수 | 감정·서사 중요도 포착 | 쓰기 LLM 비용(배치 할인 대상) |
| **W4 이벤트 트리거** | "고백/이별/약속" 등 사건 감지 시만 | 정밀도 최상, 저장량 최소 | 트리거 목록 밖은 통째로 소실 |
| **W5 시간 감쇠** | `score × e^(-λΔt)` | 오래된 잡담 자동 퇴장 | 오래됐지만 중요한 것도 함께 퇴장 |

> **여기서 "빵 사고"가 발생한다.** W1(전부 저장)이면 "점심에 빵 먹음"이 저장되고, 검색이 그걸 올리면 유언이 된다. W3/W4면 애초에 저장 안 된다.
> 하지만 반대 위험도 있다 — W4로 걸렀는데 유저가 그 잡담을 기억해주길 바랐을 수도 있다. **이건 정확도 문제가 아니라 정책 문제다.** 어느 쪽 실수가 더 나쁜지가 [02 §1.3](02-problem-definition.md)의 목적함수로 결정된다.

### M5. 갱신·충돌 (Reconcile) — 모순을 어떻게 처리할 것인가

| 옵션 | 방식 | 얻는 것 | 잃는 것 |
|---|---|---|---|
| **C1 누적** | 그냥 쌓음 | 구현 0 | **stale fact 재생** — 헤어졌는데 연인처럼 굶 |
| **C2 덮어쓰기** | 같은 키면 교체 | 항상 최신 | **과거 조회 불가** ("우리 처음엔 어땠지?") |
| **C3 Bi-temporal 무효화** | `valid_from/until` + `ingested_at` | 최신 + 이력 둘 다, 시간 질의 가능 | 스키마 복잡, 무효화 판정 로직 |
| **C4 버전 체인** | `superseded_by` 링크 | 변화 서사 추적 가능 | 체인 순회 비용 |

> **[Zep/Graphiti](https://arxiv.org/pdf/2501.13956)에서 가져올 것은 C3의 개념이지 그래프DB가 아니다.** `(주어, 속성, 값, valid_from, valid_until)` 5-튜플이면 관계형 테이블 한 개로 끝난다. 그래프 순회가 필요한 다중 홉 관계 추론은 우리 도메인(1:1 캐릭터-유저)에서 거의 발생하지 않는다.
> **→ 아이디어는 채택, 구현체는 거절.**

### M6. 게이팅 (Gating) — 언제 장기기억을 꺼낼 것인가

| 옵션 | 방식 | 지연 | 비고 |
|---|---|---|---|
| **G1 항상 검색** | 무조건 | +검색지연 | 현행 추정. P2를 악화시킴 |
| **G2 룰 게이트** | 질문형/과거시제/개체명 포함 시 | ~0ms | 한국어 어미 패턴 활용 가능 |
| **G3 소형 분류기** | 임베딩 → 이진 분류 | ~5ms | 학습 데이터 필요 |
| **G4 LLM 판단** | 소형 LLM에게 질의 | +200~800ms | 정확하지만 TTFT 직격 |
| **G5 모델 자율(tool)** | LLM이 필요하면 도구 호출 | +1왕복 | 우아하지만 지연 2배 |

> **G5는 개념적으로 가장 매력적이고 실무적으로 가장 위험하다.** 모델이 "기억을 찾아볼게"라고 판단하면 응답이 두 번의 왕복을 거친다. 롤플레이 TTFT 예산에서 이건 치명적일 수 있다. **단, 스트리밍 중 사고 과정을 보여주는 UX라면 오히려 몰입 요소가 될 수도 있다.** → 측정해볼 가치가 있다.

### M7. 검색 (Retrieval) — 무엇을 후보로 올릴 것인가

| 옵션 | 방식 |
|---|---|
| **T1 top-k 유사도** | 표준 |
| **T2 MMR (다양성)** | 유사하되 서로 다른 것 → **기억 반복 억제** (P5) |
| **T3 시간 가중** | `sim × decay(Δt)` |
| **T4 중요도 가중** | `sim × importance` |
| **T5 다중 쿼리** | 원 발화 + 확장 쿼리 병렬 |

---

### M8. 선별 (Selection) — 후보 중 무엇을 넣을 것인가

| 옵션 | 방식 | 지연 | 비고 |
|---|---|---|---|
| **L1 top-k 그대로** | 컷 없음 | 0 | 정밀도 낮음 |
| **L2 점수 임계** | `score > τ`인 것만, **없으면 0개** | 0 | **"넣지 않을 자유"가 핵심** |
| **L3 크로스인코더 리랭커** | 쿼리-후보 쌍 재점수 | ~20-50ms | 정밀도↑ |
| **L4 LLM Selector** | LLM이 고름 | +200~800ms | 현행 추정 |
| **L5 예산 배낭(knapsack)** | 토큰 예산 내 효용 최대화 | ~0 | 명시적 예산 관리 |

> **L2의 "0개를 반환할 수 있다"가 설계적으로 가장 중요하다.** top-k는 항상 k개를 준다 — 관련 없어도. 그게 "빵"을 유언으로 만든다. **임계값 컷은 단순하지만 P2에 직접 대응하는 유일한 옵션 중 하나다.**

---

### M9. 배치 (Packing) — 프롬프트 어디에 어떤 꼴로 넣을 것인가

**여기가 비용을 결정한다. 그리고 그 이유는 취향이 아니라 수학이다 (→ FP-2).**

| 옵션 | 배치 |
|---|---|
| **K1 앞쪽 주입** | `[persona][기억][최근턴]` — 캐시 파괴 |
| **K2 뒤쪽 주입** | `[persona][상태][최근턴][기억]` — 캐시 보존 |
| **K3 상태/사건 분리** | 상태는 앞(고정), 사건은 뒤(가변) |
| **K4 계층 캐시 경계** | 변경 빈도 오름차순 정렬 + 명시적 캐시 breakpoint |

형식 변수도 있다: 원문 인용 / 요약 서술 / 구조화 필드 / **"관련도 낮음" 태깅해서 모델에 판단 위임**.

---

### M10. 검증 (Guard) — 응답 후 확인할 것인가

| 옵션 | 방식 | 지연 |
|---|---|---|
| **V1 없음** | | 0 |
| **V2 룰 검사** | 금지어·호칭·상태 위반 정규식 | ~1ms |
| **V3 상태 모순 검사** | 응답이 확정 상태와 충돌하는지 | ~10ms |
| **V4 LLM 검증 + 재생성** | | +전체 1회 |

> V4는 스트리밍과 근본적으로 충돌한다(다 만들고 나서야 검증 가능). **V2가 비용 대비 효과가 가장 클 가능성이 높다** — 유사 서비스 A의 "이름 오류"(U9) 같은 건 정규식으로 잡힌다.

## 3. 근본 원리 추적 — "왜 A인가? A일 수밖에 없는가?"

각 체인은 **더 이상 질문이 나오지 않을 때까지** 내려간다.

---

### FP-1. 왜 벡터 DB인가? — 그리고 왜 아닐 수 있는가 ⭐

**Q1. 왜 벡터 DB를 쓰는가?**
→ 의미 유사도로 과거 기억을 찾기 위해.

**Q2. 왜 의미 유사도인가? 키워드로는 안 되나?**
→ 어휘 불일치(lexical gap). 유저가 *"고양이 이름"*이라 안 하고 *"걔 이름 뭐였지"*라고 한다. 키워드 매칭은 실패한다.

**Q3. 왜 임베딩이 의미를 담는가?**
→ 분포 가설(distributional hypothesis): *"비슷한 문맥에 나타나는 표현은 비슷한 의미를 가진다."* 임베딩 모델의 학습 목표가 문맥 예측/대조 학습이므로, 유사 문맥에서 쓰이는 문장들이 벡터 공간에서 가까워진다.

**Q4. 왜 코사인 유사도인가?**
→ 고차원 임베딩에서 벡터의 **크기(norm)**는 빈도·길이 같은 부수적 특성을 반영하고, **방향**이 의미를 반영한다. 정규화하면 내적 = 코사인이 되어 크기 영향이 제거된다.

**Q5. 왜 근사 최근접(ANN/HNSW)인가?**
→ 정확 최근접은 모든 벡터와 비교해야 하므로 `O(N·d)`. N이 수백만이면 실시간 불가. HNSW는 small-world 그래프를 계층으로 쌓아 `O(log N)` 탐색으로 낮춘다. **정확도(recall 95~99%)를 내주고 속도를 산다.**

**Q6. → 그런데 우리 N은 얼마인가?** ⭐ **여기서 전제가 무너진다.**

> 벡터 검색은 **항상 단일 유저 파티션 안에서만** 일어난다. 다른 유저의 기억을 검색할 일이 없다.
> 유저 1명 = 2,000턴 = 벡터 2,000개.
>
> ```
> 저장량:   2,000 × 1,024차원 × 4바이트 =  8.2 MB
> 연산량:   2,000 × 1,024 = 약 200만 곱셈-누산
> 브루트포스 소요:  메모리 대역폭 律속 → 8.2MB / ~10GB/s ≈ 0.8 ms
> ```
>
> **numpy 행렬곱 한 줄로 1ms 안에 끝난다.** 그런데 Qdrant에 네트워크 왕복을 하면 그것만 **1~5ms**다.
> **→ 이 규모에서는 벡터 DB가 브루트포스보다 느리다.**

**Q7. 그럼 벡터 DB는 왜 존재하는가?**
→ ANN 인덱스의 존재 이유는 **"N이 커서 선형 탐색이 불가능하다"**이다. 유저별 파티션에서는 그 전제가 성립하지 않는다. 벡터 DB는 *유저 간 공유되는 대규모 코퍼스*(문서 검색, 상품 검색)를 위한 도구다.

**Q8. 그럼 유저 100만 명이면 총 20억 벡터인데?**
→ 총량은 크지만 **쿼리는 절대 파티션을 넘지 않는다.** 필요한 건 "거대 ANN 인덱스"가 아니라 **"작은 인덱스 100만 개"**다. 이건 완전히 다른 문제이고, 답은 **샤딩/파티셔닝**이지 HNSW가 아니다.

**Q9. 그럼 벡터를 어디에 두는가?**
→ 여기서 실제 아키텍처 결정이 나온다. 세 가지:
1. **Postgres + pgvector, `user_id` 파티션** — RDBMS 하나로 상태·사실·벡터를 함께 관리. 트랜잭션으로 정합성 확보. (JD의 "RDBMS, 트랜잭션, 데이터 정합성"과 정확히 맞는다)
2. **세션 스코프 인메모리** — 세션 시작 시 유저 벡터 블롭(8MB)을 로드해 프로세스 메모리에 상주. 대화는 본래 **길고 상태를 갖는(stateful)** 세션이므로 자연스럽다. 단 동시 1,000세션 = 8GB 메모리 압박 → 차원 축소(1024→256)나 양자화(float32→int8)로 8MB→0.5MB까지 줄일 수 있다.
3. **전용 벡터 DB** — 운영 도구·필터링·영속성은 얻지만, 이 규모에선 **성능 이득이 없고 장애 지점만 추가**된다.

**결론:**
> **"벡터 검색이 필요하다"와 "벡터 DB가 필요하다"는 다른 명제다.**
> 전자는 참일 가능성이 높고, 후자는 이 규모에서 **거짓일 가능성이 높다.**
>
> → **실험 슬롯으로 남긴다.** Qdrant / pgvector / 인메모리 브루트포스 3안을 같은 데이터로 재고, **recall·지연·운영 복잡도**를 비교한다. 사용자가 선택한 Qdrant는 "운영 재현"의 가치가 있으므로 유지하되, **브루트포스가 더 빠르다는 결과가 나오면 그것 자체가 리포트의 발견**이다.

---

### FP-2. 왜 프롬프트 캐시가 작동하는가? — 그리고 왜 순서가 비용을 결정하는가 ⭐

**Q1. 왜 캐시 히트가 입력가의 10%인가?**
→ prefill 연산을 건너뛰기 때문. 생성 전에 입력 전체를 한 번 forward pass 해야 하는데, 그게 입력 길이에 비례하는 계산량이다.

**Q2. 왜 prefill을 건너뛸 수 있는가?**
→ Transformer는 각 토큰마다 Key/Value 벡터를 만들어 캐시한다(KV cache). 이 K,V를 재사용하면 계산을 생략할 수 있다.

**Q3. 왜 재사용이 가능한가? K,V가 뒤쪽 토큰에 의존하지 않는가?**
→ **인과 마스크(causal mask)** 때문이다. 디코더 모델에서 토큰 `i`는 `j ≤ i`인 토큰만 볼 수 있다. 따라서 위치 `i`의 K,V는 **앞쪽 토큰들에만 의존**한다. 접두사가 같으면 그 구간의 K,V는 비트 단위로 동일하다.

**Q4. 그럼 왜 접두사가 1토큰만 바뀌어도 전부 무효인가?**
→ 두 가지 이유가 겹친다.
1. **의존성 전파**: 위치 `p`의 토큰이 바뀌면, `q > p`인 모든 위치의 은닉 상태가 `p`를 attend하므로 (1층 이상에서) K,V가 전부 달라진다.
2. **위치 인코딩**: RoPE는 각 토큰의 q,k를 **절대 위치에 비례하는 각도로 회전**시킨다. 토큰을 삽입/삭제하면 뒤쪽 전체의 위치가 밀리고, 내용이 같아도 회전각이 달라져 K,V가 바뀐다.

**Q5. 왜 RoPE는 절대 위치를 쓰는가? 상대 위치를 원하는 것 아닌가?**
→ 맞다, 목표는 상대 위치다. RoPE는 위치 `m`의 쿼리와 위치 `n`의 키를 각각 회전시켜 **내적이 `(m-n)`에만 의존**하도록 만든다. 상대 위치 효과를 얻기 위해 **개별 벡터에는 절대 위치 회전을 적용**하는 것이다. 그래서 캐시된 K,V는 절대 위치가 고정되어야만 유효하다.

**결론 — 설계 규칙이 수학에서 직접 나온다:**
> **프롬프트 블록을 "변경 빈도 오름차순"으로 배치하라.**
> ```
> [시스템·페르소나]  거의 안 변함    ← 캐시 히트
> [캐릭터 상태]      느리게 변함     ← 대부분 히트
> [최근 N턴]         턴마다 append   ← append는 접두사를 안 깨뜨림 ✅
> [검색된 기억]      턴마다 교체     ← 반드시 맨 뒤
> [현재 발화]        매번 새것
> ```
> **`append`는 캐시를 유지하지만 `insert`는 파괴한다.** 이건 취향이 아니라 causal attention과 RoPE의 귀결이다.
>
> → **현행 구조가 검색 결과를 최근 대화 *앞*에 넣고 있다면, 그것만으로 캐시가 매 턴 전멸한다.** 코드 위치 한 줄 문제이고, 비용에 미치는 영향은 알고리즘 교체급이다.
>
> ⚠️ **단, 이건 상충을 만든다.** [Lost in the middle](https://arxiv.org/pdf/2410.10813) 현상 때문에 중요한 정보는 **앞이나 뒤 끝**에 있어야 잘 읽힌다. 뒤에 놓는 건 캐시와 주목도 양쪽에 유리하지만, "최근 대화보다 뒤"라는 위치가 **시간 순서를 혼란시킬 수 있다.** → 실험으로 확인할 지점.

### FP-3. 왜 "무엇을 버릴지"가 근본적으로 어려운가 ⭐

**Q1. 왜 요약·압축이 정보를 잃는가?**
→ 정보이론. 압축률이 원본 엔트로피를 넘으면 무손실 압축은 불가능하다.

**Q2. 대화의 엔트로피는 실제로 얼마나 되는가?**
→ 낮다. 인사·추임새·중복이 대부분이고 턴당 신규 정보는 몇 비트 수준이다. **그래서 이론적으로는 극단적 압축이 가능하다.**

**Q3. 그럼 왜 실제로는 손실이 발생하는가?**
→ 압축 자체가 문제가 아니다. 문제는 **"어떤 비트가 미래에 필요한지 지금은 모른다"**는 것이다. 이건 **압축 문제가 아니라 온라인 의사결정 문제**다.

**Q4. 온라인 의사결정 문제의 이론적 한계는?**
→ **이 문제는 캐시 교체(cache replacement) 문제와 동형이다.**

| 캐시 교체 | 대화 메모리 |
|---|---|
| 캐시 크기 `k` | 컨텍스트 예산 |
| 페이지 접근 | 미래 질의 |
| 페이지 축출 | 기억 망각 |
| **Belady OPT** (가장 나중에 쓰일 것 축출) | **oracle** — 미래 질의를 알아야 함 |
| LRU (최근성) | 시간 감쇠 |
| LFU (빈도) | 언급 횟수 |

> **Belady의 최적 알고리즘은 미래를 알아야 하므로 온라인에서 구현 불가능하다.** 그리고 결정론적 온라인 알고리즘의 경쟁비(competitive ratio) 하한은 `k`다 — 어떤 영리한 정책도 최적 대비 `k`배 나쁠 수 있다.

**Q5. 그럼 우리는 무엇을 할 수 있는가?**
→ 세 가지, 그리고 이게 M4 슬롯의 근거가 된다.
1. **최적을 추구하지 말고 oracle과의 격차를 측정한다.** (실험에 `A1 Oracle` arm이 있어야 하는 이유가 여기서 나온다.)
2. **더 나은 예측 신호를 찾는다.** 대화 메모리는 캐시와 달리 **의미적 신호**를 쓸 수 있다 — 감정 강도, 서사적 사건성, 유저의 자발적 재언급. LRU/LFU에는 없는 정보다. **LLM 추출이 값을 하는 지점이 정확히 여기다.**
3. **버리지 않는 선택지를 남긴다.** 원본 저장 비용은 LLM 토큰 비용보다 몇 자릿수 싸다. **"컨텍스트에서 뺀다"와 "디스크에서 지운다"는 다른 결정이다.** 후자를 할 이유가 거의 없다.

> **결론:** 망각 정책은 근본적으로 최적해가 없는 문제다. 그러므로 **"최선의 망각 알고리즘"을 찾는 게 아니라, "oracle 대비 몇 %를 회수하는가"를 재고 복잡도 대비 회수율이 가장 좋은 지점을 고르는 것**이 옳은 접근이다.

---

### FP-4. 왜 한국어에서 하이브리드 검색인가 — 일반론이 아니라 도메인 강제

**Q1. 왜 BM25 단독으로는 한국어가 어려운가?**
→ 교착어. `나비가 / 나비를 / 나비는 / 나비랑`이 전부 다른 표면형이다. 정확 매칭이 실패한다.

**Q2. 형태소 분석(nori)으로 해결되지 않나?**
→ 상당 부분 해결된다. `나비 + 가`로 분리하면 어간이 매칭된다. **그래서 한국어 BM25는 반드시 형태소 분석기와 함께 써야 한다** — 이건 선택이 아니라 필수다.

**Q3. 그럼 dense가 다 흡수하지 않나? 서브워드 임베딩이 굴절을 처리하는데.**
→ 굴절은 흡수한다. 하지만 **고유명사와 인스턴스 식별에서 무너진다.**

**Q4. 왜 dense가 고유명사에 약한가?**
→ 임베딩은 분포 의미론(FP-1 Q3)으로 학습된다. 즉 **"단어의 의미 = 그 단어가 나타나는 문맥의 통계"**다. 그런데 **고유명사의 의미는 지시 대상(referent)이지 문맥 통계가 아니다.**
→ 유저의 고양이 이름이 "나비"일 때, 임베딩 모델은 이걸 *나비(butterfly)*의 의미 근처에 놓는다. **"이 유저의 특정 고양이"라는 정보는 학습 분포에 존재하지 않는다.** 특정 문자열에 특정 지시체를 묶는 유일한 방법은 **어휘적 정확 매칭**이다.

**Q5. 이게 우리 도메인에서 왜 특히 중요한가?**
→ 롤플레이는 **고유명사 밀도가 비정상적으로 높다.** 캐릭터 이름, 유저 별명, 세계관 용어, 둘만 아는 은어, 지어낸 지명. **이건 전부 학습 분포 밖이다.**
→ 유사 서비스 A의 U9(이름 오류)가 이 실패의 증상이다.

**결론:**
> **하이브리드가 필요한 이유는 "일반적으로 하이브리드가 좋다"가 아니다.**
> **롤플레이 도메인이 dense의 구조적 약점(고유명사)에 정면으로 놓여 있기 때문**이다.
> → **BM25는 "보조"가 아니라 이 도메인에서 1급 색인이다.** 가중치를 실험으로 정하되, dense 쪽에 기울일 것이라고 미리 가정하면 안 된다.
> ⚠️ 데이터가 엇갈린다: 한국어 금융 문서에선 BM25가 5배 우수, 다른 데이터셋에선 dense가 +19%. **측정 없이는 결정 불가.**

> ### 🔴 실측 후 정정 — 이 체인의 결론이 과했다 ([11 실험 5](11-experiment-results.md))
>
> Q4에서 *"특정 문자열에 특정 지시체를 묶는 유일한 방법은 어휘적 정확 매칭"*이라고 썼다. **너무 강한 주장이었다.**
>
> 실측에서 **dense(e5-small)가 `나비`·`크로와상`·`카페인`을 전부 1~2위로 찾았고 BM25와 동률**이었다.
> 의역형에서는 dense가 명확히 우세(1.2위 vs 4.2위)했고, **naive RRF 하이브리드는 dense 단독보다 나빴다**(2.6위).
>
> **다만 이 실험은 반증의 자격이 없다.** 검색 대상 22개에 어휘적 방해물(실제 나비, 다른 고양이)이 없어 **Q4가 예측하는 실패 조건 자체가 없었다.**
>
> **→ 두 가지를 모두 인정한다:** 내가 과신했고, 동시에 제대로 테스트하지 못했다.
> Q1~Q3(분포 의미론 → 고유명사의 의미는 지시체)의 **메커니즘 설명은 유효**하지만, **그 효과 크기를 과대평가**했다.
> [07 A3](07-assumptions-audit.md)에서 배운 것과 같은 실수다 — **메커니즘의 존재와 크기는 다른 문제다.**

### FP-5. 왜 무관한 컨텍스트가 "중립적"이지 않고 "해로운"가 ⭐

**Q1. 왜 관련 없는 기억을 넣으면 성능이 떨어지는가? 모델이 무시하면 되지 않나?**
→ 실측상 무시하지 못한다. hard negative(의미적으로 유사하지만 무관한 구절)는 정답이 함께 있어도 모델을 오답으로 끌고 간다 ([Distracting Effect](https://arxiv.org/pdf/2505.06914)).

**Q2. 왜 무시하지 못하는가?**
→ 어텐션은 softmax로 정규화된다. **주의 가중치의 총합이 1**이므로 확률 질량이 유한하다. 토큰이 늘면 정답 토큰에 갈 질량이 희석된다. 그리고 hard negative는 정의상 의미적으로 가까우므로 **높은 어텐션 점수를 받는다.**

**Q3. 그런데 왜 모델은 그걸 "관련 있다"고 취급하는가?**
→ **컨텍스트에 넣는 행위 자체가 관련성 주장이기 때문이다.** 인스트럭션 튜닝된 모델은 *"주어진 컨텍스트를 근거로 답하라"*는 형태로 학습된다. 즉 **모델은 검색기의 판단을 위임받은 것으로 간주한다.** 컨텍스트에 있는 것은 "누군가 관련 있다고 판단해서 넣은 것"이다.

**Q4. 그래서 "빵 먹고 싶다"가 유언이 되는 메커니즘은?**
1. 죽음 장면 → 발화에 "마지막", "원하는 것" 같은 어휘
2. 검색기가 의미 유사도로 *"점심에 빵 먹고 싶다"* 기억을 상위에 올림 (욕구/음식 축에서 유사)
3. 컨텍스트에 삽입됨 = **"이 기억은 지금 관련 있다"는 주장**
4. 모델은 그 주장을 신뢰하고 서사에 통합
5. → 유언이 "빵 먹고 싶다"가 된다

**Q5. 그럼 근본 해법은?**
→ 세 가지 층위가 있고, 셋 다 M6/M8/M9 슬롯에 대응한다.
1. **넣지 않는다** (M8-L2 임계 컷): 애매하면 0개를 반환. **기대손실이 비대칭이므로 이게 기본값이어야 한다.**
   - 기억 누락 → 유저가 다시 말해줌 (**회복 가능**)
   - 오기억 주입 → 몰입 파괴, 되돌릴 수 없음 (**회복 불가**)
2. **주장을 약화시킨다** (M9): *"참고 (관련도 낮음): ..."*처럼 태깅해 판단을 모델에 넘김
3. **길이 자체를 줄인다**: [관련성과 무관하게 입력이 길다는 사실만으로 성능이 떨어진다](https://aclanthology.org/2025.findings-emnlp.1264.pdf)

**Q6. 부수적 관찰 — 반직관적인 것 하나:**
→ **작은 모델이 노이즈에 더 강하고 큰 모델이 더 쉽게 산만해진다.** 큰 모델일수록 컨텍스트의 미묘한 신호를 더 잘 활용하는데, 그게 노이즈일 때는 오히려 독이 된다.
→ **함의: 모델을 업그레이드하면 메모리 정밀도 요구가 더 높아진다.** 비용 절감을 위해 작은 모델로 내리면 노이즈 내성은 오히려 올라갈 수 있다. 이건 실험해볼 만하다.

### FP-6. 왜 임베딩 유사도로 "중요도"를 잴 수 없는가

**Q1. top-k 유사도 검색의 문제는?**
→ 유사도 순위가 곧 유용성 순위라고 가정한다.

**Q2. 왜 그 가정이 틀리는가?**
→ **유사도(similarity) ≠ 관련성(relevance) ≠ 유용성(utility)**이다.
- 유사도: 벡터 공간의 거리
- 관련성: 이 질의에 답하는 데 쓰이는가
- 유용성: **이걸 넣으면 다음 응답이 실제로 좋아지는가**

**Q3. 왜 임베딩이 유용성을 못 재는가?**
→ 임베딩 모델의 학습 목표에 그 개념이 없다. 대조 학습으로 (질의, 관련 구절) 쌍을 가깝게 만들도록 학습되는데, **"이 유저의 이야기에서 이 기억이 갖는 서사적 무게"** 같은 건 그 목적함수 어디에도 없다.

**Q4. 그럼 무엇이 유용성을 잴 수 있는가?**
→ `P(이 기억을 넣으면 응답이 개선된다 | 현재 발화, 캐릭터, 관계 상태)`. 이건 **유사도가 아니라 효용**이고, **하류 결과로부터의 지도(supervision)**가 필요하다.

**Q5. 그 지도 신호를 어디서 얻는가?**
→ 두 곳.
- **평가 환경**: 사실 대장(fact ledger)이 있으므로 ground truth를 만들 수 있다
- **프로덕션**: 암묵적 신호 — 재생성 버튼, 세션 지속 시간, 유저의 정정 발화("아니 그거 말고"), 이탈

**결론 — 그리고 내 이전 가설의 수정:**
> 유사도는 **후보 생성기(candidate generator)**이지 **선별기(selector)**가 아니다.
> 따라서 **2단계 구조(광범위 검색 → 효용 기반 선별)는 원리적으로 정당하다.**
>
> → **[01 문서의 H2를 수정한다.** 나는 "Selector는 지연만 늘리는 사치"라는 뉘앙스로 의심했는데, 그건 틀렸다. **Selector의 *기능*은 원리적으로 필요하다.** 의심해야 할 것은 그 기능이 **응답 경로의 LLM 호출로 구현되어야 하는가**이다.
> 크로스인코더 리랭커는 같은 기능을 20~50ms에 수행한다. **기능은 유지하고 구현을 바꾸는 것**이 옳은 질문이다.

## 4. 조합 폭발과 탐색 전략

### 4.1 문제의 크기

```
M1(6) × M2(7) × M3(5) × M4(5) × M5(4) × M6(5) × M7(5) × M8(5) × M9(4) × M10(4)
= 6×7×5×5×4×5×5×5×4×4 ≈ 4,200,000 조합
```
전수 탐색은 불가능하다. **그러므로 탐색 전략 자체가 설계 결정이다.**

### 4.2 3단 탐색 설계

**Stage 0 — 값싼 대리 지표로 사전 가지치기 (LLM 호출 0, 비용 0)** ⭐ 키 없이 가능

LLM 없이도 잴 수 있는 것들:
```
evidence_recall@k      # 정답 근거가 후보에 들어왔는가 (M1,M2,M3,M7 평가)
injection_precision@k  # 주입된 것 중 실제 관련된 비율 (M8 평가)
context_tokens         # 토큰 회계 (M9 평가)
cache_prefix_stability # 턴 간 공통 접두사 길이 (M9 평가)
retrieval_latency      # 검색·리랭크 실측 (M3,M6,M7,M8 평가)
```
→ **M1~M3, M7, M8, M9의 상당 부분이 여기서 걸러진다.** `evidence_recall@k`가 낮은 조합은 어차피 하류에서 못 이긴다. **검색기가 못 찾은 걸 LLM이 답할 수는 없다.**

**Stage 1 — 모듈별 단독 스윕 (OFAT, One-Factor-At-A-Time)**

기준 구성(reference config)을 하나 정하고, **한 번에 한 모듈만** 교체한다.
```
기준: R1원문 + S2턴 + I2dense + W1전부 + C1누적 + G1항상 + T1topk + L1topk + K1앞쪽 + V1없음
      (= 의도적으로 "순진한" 구성. 개선 여지를 최대로)

실행 횟수 = Σ(각 모듈 옵션 수) ≈ 50회
```
각 모듈의 **효과 크기(effect size)**를 측정 → 어떤 모듈이 중요한지 순위를 매긴다.

> ⚠️ **OFAT의 알려진 한계를 정직하게 다룬다.** OFAT는 **상호작용을 놓친다.** 예를 들어 "게이팅(M6)"의 효과는 "선별(M8)"이 이미 정밀하면 작게 나타난다. 완화책 세 가지:
> 1. **기준 구성을 2개** 잡고 각각에서 OFAT를 돌려 결과가 뒤집히는지 본다 (뒤집히면 상호작용이 있다는 증거)
> 2. **기계적으로 상호작용이 예상되는 쌍**은 미리 지정해 Stage 2로 보낸다:
>    - M6 게이팅 × M8 선별 (둘 다 "안 넣기"를 담당 → 중복)
>    - M9 배치 × M1 표현 (표현 형태가 캐시 안정성을 결정)
>    - M4 쓰기정책 × M7 검색 (안 쌓으면 못 찾음)
>    - M5 갱신 × M8 선별 (모순 두 버전이 함께 후보에 오름)
> 3. Stage 0의 값싼 지표로 **더 조밀하게** 스캔해 상호작용 힌트를 얻는다

**Stage 2 — 상위 모듈 교차 (부분 요인 설계)**

Stage 1에서 효과가 큰 상위 3~4개 모듈만 골라 교차한다.
```
상위 4모듈 × 각 3옵션 = 81 조합 → 실행 가능
(또는 2수준 부분요인설계로 16회까지 축소)
```

**Stage 3 — 파레토 프론티어 + 전체 평가**

Stage 2 생존자 + 필수 baseline을 **전 지표 5축**으로 평가.
```
파레토 축: (기억 정확도 × misinjection_rate × $/1k턴 × TTFT p95 × 페르소나 유지도)
```
**다른 조합이 모든 축에서 우월한 조합은 탈락.** 남는 것이 진짜 후보다.

### 4.3 반드시 포함되는 고정 대조군

어떤 탐색을 하든 이 5개는 항상 함께 돌린다.

| ID | 이름 | 역할 |
|---|---|---|
| `A0` | Full-context | 정확도 상한 (비용 상한이기도) |
| `A1` | **Oracle 검색** | **이론적 상한** — FP-3에서 도출: 개선 여지의 크기를 재는 유일한 방법 |
| `A2` | Window-only | 지연·비용 하한 |
| `A3` | **Random-K** | **위생 검사** — 이걸 못 이기면 검색이 작동 안 함 |
| `G1` | **현행 구조 재현** | 현행 기준선 대조군 (계층+RAG+LLM Selector) |
