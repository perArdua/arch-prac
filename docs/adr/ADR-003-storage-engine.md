# ADR-003: 저장소 엔진 — 벡터 DB를 쓸 것인가

- **상태:** 제안됨 (실측으로 재검증 필요)
- **일자:** 2026-09-03
- **관련:** ADR-002, ADR-006
- **근거 문서:** [03 FP-1](../03-architecture-modules.md), [06 §3](../06-data-model.md)

## 맥락

메모리 검색을 위해 전용 벡터 데이터베이스를 도입할 것인가. 업계 기본값은 "그렇다"이고, 나도 처음엔 Qdrant를 전제했다. 그런데 **왜 그것이어야 하는지를 근본까지 따라가 보니 전제가 성립하지 않았다.**

## 결정 동인

1. 검색 지연 (TTFT 예산 200~400ms 중 일부)
2. 회상 정확도
3. **운영 복잡도 / 장애 지점 수**
4. 데이터 정합성 (사실 갱신과 임베딩 갱신의 원자성)

## 고려한 선택지

1. **전용 벡터 DB** (Qdrant 등)
2. **Postgres + pgvector**
3. **세션 스코프 인메모리 브루트포스**

## 결정

> **우리는 2번(Postgres + pgvector)을 선택한다. 단 3안과의 실측 비교를 실험으로 남긴다.**

## 근거 — ANN 인덱스의 존재 이유가 성립하지 않는다

벡터 검색은 **항상 단일 대화방 파티션 안에서만** 일어난다. 다른 유저·다른 방의 기억을 검색할 일이 없다(ADR-001).

**카디널리티를 세어보면:**

| 대상 | 1년 후 개수 |
|---|---|
| 사실 | 100~500 |
| 사건 | 1,000~2,400 |
| 해석 | 50~200 |
| 고유명사 | 50~200 |
| **검색 대상 합계** | **1,500~3,000** |

**✅ 실측 완료** ([11 실험 6](../11-experiment-results.md), numpy 중앙값 20회)

| N (대화방당) | 256차원 int8 지연 | 메모리 |
|---|---|---|
| 3,000 *(우리 규모)* | **0.13 ms** | **0.73 MB** |
| 100,000 | 2.25 ms | 24 MB |
| **1,000,000** | **18.6 ms** | 244 MB |

```
브루트포스 (우리 규모)        0.13 ms
Qdrant 네트워크 왕복(문헌값)  1~5 ms      ← 검색 연산은 세지도 않았다
메모리 파이프라인 예산        200~400 ms
```

> **네트워크 왕복만으로도 브루트포스보다 10~40배 느리다.**
> 그리고 **100만 벡터도 18.6ms**로 예산 안에 들어온다 —
> **카디널리티 추정([06 §3.1](../06-data-model.md))이 300배 틀려도 이 결정이 안 바뀐다.**
> ANN 인덱스가 필요해지는 지점은 우리 규모보다 두세 자릿수 위다.

> **이 규모에서는 전용 벡터 DB가 브루트포스보다 느리다.**
> ANN 인덱스는 *"N이 커서 선형 탐색이 불가능하다"*를 전제로 존재한다. 유저-캐릭터 파티션에서는 그 전제가 거짓이다.
> 유저 100만이면 총 30억 벡터지만 **쿼리가 파티션을 넘지 않으므로**, 필요한 건 거대 ANN 인덱스가 아니라 **작은 인덱스 100만 개**다. 답은 샤딩이지 HNSW가 아니다.

**그럼 왜 3안(인메모리)이 아니라 2안인가:**
- 영속성·트랜잭션이 공짜로 따라온다. 사실 갱신과 임베딩 갱신을 **한 트랜잭션**으로 묶을 수 있다(stale propagation 방어)
- 3안은 8MB→0.8MB 축소를 전제해야 하고(차원 축소·양자화), 그 손실이 미검증이다
- 이런 서비스의 서버 팀은 대개 관계형 DB와 트랜잭션에 이미 익숙하다 — 팀이 이미 잘 아는 도구다

**시장 증거:** 유사 서비스 A·B·C **누구도 벡터 검색을 제품 전면에 내세우지 않는다.** 전부 문서와 필드 기반이다.

**보안 근거:** 벡터 계층에서 권한을 강제해도 그래프 순회 등 다른 경로로 우회 가능하다는 보고가 있다. 저장소가 하나면 권한 검사 지점도 하나다.

## 결과

**좋아지는 것**
- 새 인프라 0. 장애 지점이 늘지 않는다
- 사실·임베딩 정합성이 트랜잭션으로 보장된다
- 인덱스 선행 컬럼을 `chat_id`로 두면 파티셔닝도 불필요하다

**감수하는 것**
- pgvector는 대규모 ANN에서 전용 DB보다 느리다 — **우리 규모에선 무관하지만, 규모가 바뀌면 문제가 된다**
- 벡터 검색 관련 운영 도구(모니터링·튜닝)가 전용 DB보다 빈약하다

**임베딩 크기 주의:** 3,000개 × 1024차원 float32 = **12.3MB로 원문 텍스트(0.9MB)의 13배**다. 차원 축소(1024→256) 또는 int8 양자화가 사실상 필수다.

## 재검토 트리거

- **유저-캐릭터 쌍당 검색 대상이 50,000개를 넘으면** → 전용 벡터 DB 재검토
- 유저 간 공유 메모리(월드 상태 등)가 도입되면 → 파티션 전제가 깨진다. 즉시 재검토
- pgvector 검색 p95가 20ms를 넘으면 → 인메모리 또는 전용 DB 🔄 *(2026-09-10) pgvector는 아직 안 쟀다. 같은 자에 선 **프로토타입 경로**(SQLite + Python 어휘 루프)의 값은 ≈ 3,000행에서 닿는다 — 이 트리거의 발화가 아니다. 아래 «미해결» 🔄*
- **실험 D7·D12 결과가 이 결정을 뒤집을 수 있다** — 브루트포스가 유의하게 빠르면 3안으로, 회상이 크게 떨어지면 1안으로

## 미해결

> 🔄 **2026-09-10 괴리 처분이 이 절을 만들었다** ([docs/17](../17-gap-disposition.md) 검§1-1 · 검§1-11 · 검C1). 이 ADR에는 미해결 절이 없었고, 아래 둘은 연구 문서(`.omc/research/`)에만 적혀 있었다.

- **프로토타입의 검색 경로는 이 ADR이 잰 경로가 아니다.** 위 «3,000개 0.13 ms»는 **numpy 내적**의 실측이다. `prototype/memory.py`의 `Memory.retrieve`는 SQLite에서 방의 행을 전부 읽어 **Python 루프**로 행마다 `bigrams`를 다시 계산한다(`embed` 모드는 순수 Python 코사인). 인덱스(`CREATE INDEX`)도 FTS도 없고, 벡터는 `embedding` 테이블에 JSON 문자열로 들어간다. 색인 21행에서는 계측에 안 잡히는 비용이라 결론을 흔들지 않지만, «우리 규모에서 0.13 ms»를 **이 프로토타입의 수**로 옮겨 적으면 안 된다. 🔓 **열리는 조건:** 색인 1,500행 이상(위 «우리 규모»의 하한)인 코퍼스에서 `retrieve`의 p95를 n ≥ 100으로 잰 값이 생기는 순간 — 그 값이 위 재검토 트리거(p95 > 20 ms)와 같은 자에 선다.
  - 🔄 **축 라운드 (2026-09-10) — 이 조건이 참이 됐다. 값이 생겼다** (레인 B가 만든 계측기 · 마감 파도가 다시 뽑았다). 재현: `PYTHONIOENCODING=utf-8 python -B experiments/retrieve_scaling.py` (LLM 0회 · `%TEMP%` DB). 21행 틀(`eval` 색인 · 평균 요약 18.9자 · τ 미만 5행)을 되풀이해 N행 합성 색인을 만들고, N마다 `retrieve`를 **n = 130회**(워밍업 5 제외 · 라운드마다 N 순서를 섞음) 부른다. ⚠️ **지연은 기계·부하의 함수다 — 아래 수는 같은 실행 안에서만 비교한다.** 한 기계(논리 CPU 20 · Python 3.13.5)에서 2분 간격으로 돈 두 실행을 나란히 적는다:

    | 3,000 *(«우리 규모» 상한)* | 18.290 · **20.195** ms | 18.148 · **19.186** ms | **24.748 · 24.024** ms | 3.161 · 3.276 ms |

    - **`retrieve` p95가 20 ms를 넘는 행 수 ≈ 3,000** — 사전 등록 격자(21 · 100 · 500 · 2,000 · 5,000)에서 내삽한 값이 1회차 **2,996** · 2회차 **3,063**. gate+retrieve는 ≈ **2,420 · 2,467**. 모든 행이 τ를 통과하는 최악 분포에서는 ≈ 2,298 · 2,292. 앞선 레인 B의 네 실행은 `eval` 분포 2,938~3,094 · 전부 τ 통과 2,241~2,343 · gate+retrieve 2,382~2,489였다(다른 시각 — 섞어 비교하지 않는다).

SQL만의 p95는 같은 실행 `retrieve` p95의 ⅙ 안팎이다 — **나머지는 행마다 `bigrams`를 다시 계산하는 Python 루프의 몫이다**([docs/17](../17-gap-disposition.md) 검B3). 🔄 **w8code (2026-09-11) — 그 몫을 내용 주소 메모로 걷었다.** 설계 둘을 비교했다 — (가) 쓰기 시점 측면 테이블(스키마 5→6)은 백필을 파이썬 토크나이저로만 채울 수 있어 새 마이그레이션에 백필이 들어가는 순간 U5 지뢰(롤백을 겪은 DB에서 빈 범위가 백필을 조용히 건너뛴다)가 열리고, 요약이 바뀌거나 지워질 때 따라가야 할 무효화 표면이 하나 는다 · (나) 요약 **문자열 자체가 키인** `functools.lru_cache`(상한 16,384 · 반환 `frozenset`)는 낡을 수 없다 — 키가 내용이고 «누가 살아 있나»는 SQL이 거른다. 강화 병합은 요약을 안 바꾼다(병합 분기는 계수·가중치만 올리고 저장소 전체에 요약 갱신 0곳). → **(나)를 골랐다.** 대가: 메모를 비운 첫 턴(콜드)은 오늘과 같거나 조금 느리고(아래 ×1.07 · ×1.11), 상한보다 서로 다른 요약이 많으면 LRU 순차 훑기가 거의 다 빗나간다(상한 1,000 · s0 적중 2.3 %). eval3 3,000행 · 같은 실행 안 n=130: 웜 `retrieve` p95 ×0.40 · ×0.40 · ×0.38(22.9→9.2 · 22.0→8.8 · 20.4→7.7 ms) · 콜드 ×1.07 · ×1.11 · ×0.80 · 턴(게이트+검색) 웜 ×0.42 · ×0.43 · ×0.39 · 검색 반환·게이트 어휘·판정은 다섯 코퍼스에서 바이트 같다. 재현 `experiments/retrieve_memo.py`. 위 표의 틀(요약 21종 되풀이)은 워밍업 뒤 늘 웜이라 재실행 곡선은 **웜 곡선**이다 — 20 ms 교차 추정 N ≈ 8.7k~10.4k(검색) · 6.8k~7.4k(게이트+검색) · SQL만이 이제 검색 p50의 절반 이상이다. 다음 비용은 토큰화가 아니라 행을 꺼내는 쪽이다(위 1·2회차 값과 배수로 잇지 않는다 — 다른 실행이다).
    - 🔴 **이 교차점은 위 «우리 규모»(1,500~3,000행) 안에 떨어진다.** 하한에서 p95 ≈ 10 ms(자의 절반), 상한에서 p95가 **자 위에 걸친다**(두 실행이 20 ms의 양쪽 — 19.186 / 20.195), gate+retrieve는 상한에서 이미 넘는다. 즉 «우리 규모에서 0.13 ms»(numpy 내적)와 달리 **이 프로토타입의 경로는 설계 규모의 끝에서 20 ms 자에 닿는다.** 두 수를 나눠 배수로 적지 않는다 — 다른 실행 · 다른 연산(int8 내적 vs 어휘 bigram) · 다른 날이다.
    - ⚠️ **합성 색인의 한계.** 요약 문자열이 21종뿐이라 어휘가 늘지 않는다. 지연(행 수 × 길이의 함수)은 이 방식으로 잴 수 있지만 **꺼낸 수·순위·IDF 분포는 규모 코퍼스의 값이 아니다** — 아래 «규모 코퍼스가 없다»는 그대로다.
  - 🔄 **재검토 트리거와의 관계 — 문자 그대로는 발화하지 않는다.** 트리거 «pgvector 검색 p95가 20ms를 넘으면»의 주어는 **pgvector**다. 잰 것은 이 ADR의 세 선택지 어느 것도 아닌 **SQLite + Python 어휘 루프**이고, pgvector도 브루트포스 numpy도 재지 않았다. 같은 **자**(20 ms)에 섰을 뿐 같은 **대상**이 아니다. 그래서 이 값이 말하는 것은 «pgvector가 느리다»가 아니라 **«프로토타입 경로를 그대로 규모에 올리면 설계 규모 상한에서 트리거의 자에 닿는다»**이고, 그 비용의 대부분이 엔진(SQL — 같은 실행에서 ⅙ 안팎)이 아니라 행마다의 Python 처리(`bigrams` 재계산 포함)다 — 가리키는 수리는 저장 엔진 교체가 아니라 사전 토큰화·역색인(docs/17 검B3 ⏸)이다.
  - 🔄 **상태는 «제안됨» 그대로 둔다 — 판단과 근거** (`.omc/plans/open-questions.md` D6이 그 자리다). ① 채택/수정을 가를 비교 — 위 §결정이 스스로 남긴 «3안과의 실측 비교» · 재검토 트리거의 실험 D7·D12 — 는 여전히 안 했다. 이번 값은 그 비교의 어느 팔도 아니다. ② 교차점은 **결정을 뒤집는 쪽이 아니다** — 뒤집으려면 pgvector 경로가 느리거나(1안으로) 브루트포스가 유의하게 빨라야(3안으로) 하는데 둘 다 안 쟀다. ③ **비용 축과 품질 축을 섞지 않는다.** 이 값은 비용 축이다. 미뤄 둔 엔진 라운드가 다시 열리는 조건(«IDF가 순위를 움직일 수 있는 문항 ≥ 6»)은 **품질 축**이고 오늘 여전히 미달이다([ADR-015](ADR-015-retrieval-modes.md) «미해결» · docs/17 §9). 지연 교차점이 생겼다고 엔진 라운드가 열리지 않고, 엔진 라운드가 열려도 이 교차점이 답하지 않는다. 🔓 **상태를 다시 볼 조건:** pgvector(또는 3안의 브루트포스) 경로의 p95를 **같은 실행 안에서** 이 경로와 나란히 잰 값이 생기는 순간.
- 🔄 **축 라운드 — 벡터의 차원을 코드가 지키지 않는다** ([docs/17](../17-gap-disposition.md) 축-2 · ❔1). 위 «임베딩 크기 주의»의 «1024차원»은 **모델 출력의 성질**이다 — 저장소의 모델 출력 캐시 86/86이 1024차원이고, `prototype/`은 1024를 차원으로 적지도 검사하지도 않는다(코드 토큰 `1024` 6곳은 전부 바이트 단위). `memory._cosine`은 길이가 다른 두 벡터를 `zip`으로 **조용히** 짧은 쪽에서 끊고(`_cosine([1,0,0], [1,0])` → 1.0), `embedding.db_put_vec`은 3차원 벡터도 받아 저장한다. 위 «차원 축소(1024→256)»를 색인과 질의 중 한쪽에만 적용하면 코사인이 앞 256차원만으로 계산돼 **예외 없이 그럴듯한 값**이 나온다. 재현: `PYTHONIOENCODING=utf-8 python -B experiments/vecdim_ppr_probe.py`. 🔓 **열리는 조건:** 저장소에 길이가 다른 벡터가 하나라도 생기는 순간(그 스크립트가 찍는 캐시 길이 분포가 두 값 이상). 🔄 *(w6code · 2026-09-11) 코사인은 이제 길이가 다르면 던지고(`DimMismatch`), 임베딩 검색은 코사인 전에 차원을 맞춰 보고 갈리면 `lexical_fixed`로 강등하며 provenance에 `dim_mismatch`를 남긴다([docs/17](../17-gap-disposition.md) 축-2). «한쪽에만 축소»는 이제 예외 없는 그럴듯한 값이 아니라 **강등 + 기록**이 된다. 저장(`db_put_vec`)은 여전히 아무 차원이나 받는다.*
- **규모 코퍼스가 없다.** 저장 엔진·IDF·ANN 비교는 전부 그것이 선행이고, 21행에서는 어떤 엔진도 가를 수 없다는 것을 [ADR-015](ADR-015-retrieval-modes.md) «미해결»의 엔진 라운드 항목이 실측으로 적는다. 상태 «제안됨»은 그대로 둔다(`.omc/plans/open-questions.md` D6). 🔄 *(eval3 레인) 합성 규모 코퍼스가 생겼다 — `eval3/`(색인 3,000행 × df 레짐 셋). 어휘가 실제로 느는 색인에서 같은 루프의 합성 틀과 나란히 `retrieve` p95 19.739 · 19.344 · 18.923 ms 대 틀 19.103 ms(한 실행 · 두 번째 실행은 모두 0.6 ms 안팎 낮다) — 틀로 잰 교차가 같은 자리에 선다. «실사용 df»는 여전히 없다([docs/17](../17-gap-disposition.md) §13)*
- 🔄 **실험 32 (2026-09-11) — 엔진 비교가 돌았다. 이 결정과의 관계를 품질 축과 비용 축으로 따로 적는다** ([11 실험 32](../11-experiment-results.md) · [docs/17](../17-gap-disposition.md) §14).
  - **품질 축:** Postgres 16 + pg_bigm(GIN · `bigm_similarity`)은 같은 분석기·같은 식의 파이썬 팔과 **순위가 한 자리도 안 다르다**(코퍼스 다섯 열 · 채점 175문항 · 값 차 ≤ 2.2 × 10⁻⁸). OpenSearch도 같다. → 이 결정의 선택(Postgres)이 검색 품질을 움직이는 경로는 «엔진» 칸이 아니라 **그 엔진에서 고르는 분석기와 식**이다. 기본 설정 엔진 구성이 현행을 넘는다는 것은 검출되지 않았다(순위만 본 주 판정 · 홀드아웃 23문항).
  - **비용 축:** 3,000행에서 서버 실행 시간 p50 — Postgres GIN(강제) ≈ 3.8~4.4 ms · 계획기 선택(순차 스캔) ≈ 6.6~7.3 ms · OpenSearch `took` 1 ms 미만. 프로토타입 `retrieve`(SQLite 전량 스캔 + 파이썬 토큰화 · 프로세스 안) ≈ 18~19 ms. **같은 조건이 아니다** — 엔진은 색인을 미리 지었다. 위 🔄의 «SQL 몫이 ⅙ 안팎 — 비용은 행마다의 파이썬 처리»와 같은 쪽을 가리킨다: 비용을 줄이는 자리는 사전 토큰화 · 역색인이고, 그것은 엔진 교체 없이도 할 수 있다([docs/17](../17-gap-disposition.md) 검B3).
  - 🔴 **두 축을 섞지 않는다.** 품질 결론(구현 요인 0)은 «엔진을 쓰지 말라»도 «써라»도 아니고, 비용 값은 품질 판정에 안 들어간다. 재검토 트리거 «pgvector 검색 p95가 20 ms를 넘으면»은 **여전히 발화하지 않는다** — 잰 것은 pg_bigm(어휘)이지 pgvector가 아니다. 상태 «제안됨» 그대로.
- 🔄 **사용자 결정 (2026-09-11) — 엔진(OpenSearch+nori · Postgres+pg_bigm)은 실험 32의 조건에서는 도입하지 않는다. 상태 «제안됨»은 바꾸지 않는다** (정본 `docs/decisions/decisions-0911.md` §4 · [docs/17](../17-gap-disposition.md) §16). 엔진을 «이 조건에서» 들이지 않는 것은 위 세 선택지 사이의 선택(§결정 2번 · 3안과의 실측 비교는 여전히 안 했다)을 닫지 않는다 — 설계를 버린 것이 아니다.
