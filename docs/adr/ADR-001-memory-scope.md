# ADR-001: 메모리의 범위 단위

- **상태:** 제안됨
- **일자:** 2026-09-03
- **관련:** ADR-002, ADR-010
- **근거 문서:** [06 §1](../06-data-model.md), [09 §5.2](../09-what-memory-is-for.md)

## 맥락

캐릭터 챗 서비스는 흔히 "라이브러리"에 채팅 리스트를 둔다. **한 유저가 같은 캐릭터와 여러 대화방**을 가질 수 있다(유사 서비스 C도 동일). 그러면 기억을 어느 단위로 묶을지가 스키마의 기본 키를 결정한다.

유저가 방을 나누는 이유는 대개 **다른 이야기를 하려는 것**이다. 기억이 방을 넘어 새면 그 목적이 파괴된다. 반대로 전부 리셋하면 관계 연속성이 사라진다.

## 결정 동인

1. 서사 무결성 — 방마다 다른 이야기가 성립해야 함
2. 관계 연속성 — 유저는 "기억되는" 느낌을 원함
3. **프라이버시** — 캐릭터 A에게 한 말이 캐릭터 B에게 가는 것
4. 스키마 단순성

## 고려한 선택지

1. **대화방 단위** — 방마다 완전 독립
2. **캐릭터 단위** — 방을 넘어 공유
3. **데이터 종류별 분리** — 종류마다 스코프가 다름

## 결정

> **우리는 3번을 선택한다. 스코프를 3단으로 나누고, 분할 축은 "픽션 안/밖"이다.**

```
character  페르소나·말투·세계관 (제작자 소유, 버전 고정)
chat       관계·서사·사실·사건·부채 전부       ← 픽션 안
user       유저가 직접 등록한 프로필만          ← 픽션 밖, 명시 동의
```

"대화방이냐 캐릭터냐"는 잘못된 이분법이었다. `유저의 실제 직업`은 어느 방에서 말했든 참이고, `"우리는 연인 사이다"`는 이 방에서만 참이다. **데이터마다 참인 범위가 다르다.**

**핵심 하위 결정: 대화에서 추출한 실세계 사실도 `chat` 스코프에 둔다.**
기술적으로는 `user`로 올리는 게 유용하지만, 캐릭터 A에게만 한 말을 B가 아는 것은 **유저가 동의한 적 없는 정보 이동**이다. 로맨틱 AI 컴패니언 프라이버시 연구에서 유저들은 *"모든 말이 검증당하는 것처럼"* 느껴 **자기표현을 주저**한다고 보고한다. 그 억제는 기억할 재료 자체를 고갈시킨다.

단 `realm` 필드로 픽션/실세계를 구분해 **저장은 해둔다.** 나중에 유저 동의로 승격 가능하다 — 저장과 공유는 다른 결정이다(ADR-002).

## 근거

| | 대화방 단위 | 캐릭터 단위 | **3단 분리** |
|---|---|---|---|
| 서사 무결성 | ✅ | ❌ 픽션이 샘 | ✅ |
| 관계 연속성 | ❌ 매번 리셋 | ✅ | ⚠️ 방 안에서만 |
| 프라이버시 | ✅ | ❌ | ✅ |
| 스키마 복잡도 | 낮음 | 낮음 | 중간 |

시장 근거: 유사 서비스 C의 페르소나 기능이 정확히 이 구조다 — 유저가 직접 쓴 것만 모든 캐릭터에 적용되고, 대화에서 추출된 구조화 사실은 해당 대화에 머문다.

## 결과

**좋아지는 것**
- 유저가 방을 나누는 행위가 의도대로 작동한다
- 프라이버시 사고의 반경이 방 하나로 제한된다

**감수하는 것**
- 같은 캐릭터와 새 방을 열면 관계가 처음부터다. 유저가 불만을 가질 수 있다
- → 완화: 새 방 생성 시 *"이전 이야기를 이어받을까요?"* 옵션 (유저의 명시 선택)

**새로 생기는 장애 지점**
- `realm` 판정을 추출기가 틀리면 픽션 사실이 프로필로 승격될 수 있다 → 승격은 반드시 유저 확인을 거친다

## 재검토 트리거

- 유저의 평균 대화방 수가 1.2개 미만이면 → 방 분리가 실제로 안 쓰이는 것. 캐릭터 단위로 단순화 검토
- *"다른 방에서 말했는데 왜 모르냐"*는 불만이 상위권이면 → 선택적 공유 UI 도입 검토
- **되돌리기 방향에 주의:** 공유를 나중에 여는 것은 쉽지만, 이미 샌 정보는 닫을 수 없다. 그래서 닫힌 쪽에서 시작한다
