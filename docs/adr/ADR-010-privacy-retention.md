# ADR-010: 프라이버시와 데이터 보존

- **상태:** 제안됨 — **⚠️ 법무 검토 필요**
- **일자:** 2026-09-03
- **관련:** ADR-001, ADR-002, ADR-004
- **근거 문서:** [06 §6](../06-data-model.md), [09 §5.2](../09-what-memory-is-for.md), [03 FP-7·FP-8](../03-architecture-modules.md)

## 맥락

캐릭터 챗 서비스는 로맨스·BL 장르를 다루고 **집착·통제·노예** 같은 태그를 쓰는 경우가 많다. 유저는 매우 사적인 것을 말한다.

**여기서 두 가지가 충돌한다.** 기억을 잘하려면 유저에 대해 많이 알아야 하는데, 많이 아는 것 자체가 유저를 불편하게 만든다. 로맨틱 AI 컴패니언 프라이버시 연구에서 실제로 나온 반응:

> 사용자들은 챗봇에게 **"감시당한다"**는 인상에 불편해하고, *"모든 말이 검증당하는 것처럼"* 느껴 **자기표현을 주저**한다. **기억을 선택적으로 지울 수 없다는 점**이 불안을 키우고, 트라우마에 대해 저장된 기억이 **정서적으로 견딜 수 없게** 만든 사례도 있다. 그리고 **잘못된 기억은 프라이버시 불안을 유발한다** — *"이게 틀렸으면 또 뭐가 저장되어 있는 거지?"*

## 결정 동인

1. 법적 준수 (개인정보보호법)
2. **제품 리스크** — 법에 안 걸려도 유저가 떠난다
3. 기억 품질 (너무 조이면 기능이 죽는다)
4. 되돌릴 수 있는 방향으로 시작하기

## 결정

> **① 민감 범주는 추출·구조화·색인하지 않는다. 원문에만 남긴다.**
> **② 원본 로그는 지우지 않는다 — 삭제는 기술 결정이 아니라 법률·정책 결정이다.** 🔄 *(w31i · 2026-09-12 · Fable 최종 재검증 N3 · 사용자 결정 Q10 = (c))* **이 결정이 재생성의 가리기 단위 «턴 하나»와 만나면 같은 턴의 안 지운 사실도 그 세션 요약에서 빠진다** — 원본 턴을 고치지 않으므로 지운 사실의 원본 턴을 재생성 프롬프트에서 통째로 가리고, 사실에서 턴으로 가는 대응은 턴 하나뿐이다(스팬 없음 · ADR-011 미해결). 안 지운 사실은 [알고 있는 것] · 검색 복사본에는 남는다(재현 `.omc/notepads/w26final/probes26_out.txt` P1 — 턴 3의 «나비»가 재생성 본문에서 사라짐). 처분은 문서 + 특징짓기 시험이다(턴 통째 가림 유지 — 보호가 요약 커버리지보다 앞선다). **열리는 조건:** 추출기가 사실 → 스팬 대응을 줄 때 — 그때 가리기 단위 자체가 바뀌므로 스팬 치환(Q10 (a))을 함께 연다 · 처분표 [docs/17](../17-gap-disposition.md) §18-6
> **③ 유저에게 기억을 보고·수정·삭제할 수 있는 표면을 제공한다.**
> **④ 대화에서 추출한 것은 대화방을 넘지 않는다 (ADR-001).**

## 근거

### ① 왜 "저장은 하되 구조화는 안 하는가"

세 결정의 비용 구조가 완전히 다르다.

| 결정 | 비용 | 고유 리스크 |
|---|---|---|
| 저장 | ~$0.00005/유저·월 | 법적 보관 책임 |
| **색인** | ~$0~0.3 | **검색 가능해진다** ⭐ |
| 주입 | ~$10~25 | 오주입 |

**색인의 진짜 비용은 돈이 아니다.** 원문 로그에 묻혀 있는 것과 구조화되어 질의 가능한 것은 다르다.

> `fact(유저, 성적_선호, "...")` 같은 레코드는 **유저가 준 데이터가 아니라 우리가 만들어낸 프로파일**이다.

한국 개인정보보호법상 민감정보(사상·신념·건강·**성생활**)는 별도의 명시적 동의를 요구한다. 대화에서 이를 **추출·구조화·색인하는 것**은 원문 보관과 법적 성격이 다를 수 있다.

**→ 설계:** 추출기에 **민감 범주 거부 목록**. 해당하면 L5/L6에 만들지 않고 **L0 원문 검색으로만** 접근한다. L4 요약에서도 추상 수준을 낮춘다.

⚠️ **나는 법률 전문가가 아니다. 실제 서비스라면 법무 검토가 필요하다.** 다만 설계 단계에서 이 구분을 인지하고 구조를 만들어두는 것과 나중에 붙이는 것은 난이도가 완전히 다르다.

### ② 왜 원본을 지우지 않는가

```
저장 비용:  유저당 월 $0.000046  (턴당 200B × 월 10,000턴 = 2MB)
LLM 비용:   유저당 월 $24.75
비율:       약 1/500,000
```

모든 파생 데이터(요약·사실·사건·해석)는 언제든 버리고 원본에서 다시 만들 수 있어야 한다. 왜냐하면 **스키마가 바뀌기 때문**이고, 스키마가 바뀌는 이유는 **무엇이 중요한지를 미리 알 수 없기** 때문이다. 메모리 시스템은 본질적으로 계속 틀리면서 고쳐지는 시스템이다.

> **→ 원본 삭제는 엔지니어링 결정이 아니라 법률·정책 결정이다.**
> *"용량 때문에 오래된 로그를 지웁시다"*는 5자릿수 틀린 판단이다.

⚠️ **단, "언제든 재생성 가능"은 과장이었다.** 전면 재추출은 유저당 $0.08~0.64, 100만 유저면 **$82K~$640K**다. 저장의 1,600~13,000배다. 연 1~2회 하는 대공사이므로, 스키마는 **추가적으로만** 진화해야 하고 파생 데이터는 **버전 태그를 붙여 공존**시킨다.

**보존 정책:**
```
계정 삭제 요청     → L0 포함 전부 삭제 (법적 의무)
개별 기억 삭제 요청 → user_deleted 플래그 + 색인 제거. 원문은 보존 여부를 유저가 선택
대화방 삭제        → 해당 chat 스코프 전부
비활성 계정        → 법정 보존기간 후 정책에 따라
```

> #### 🔴 «+ 색인 제거»가 **`delete_item` 경로에서는 참이 아니었다** (2026-09-10에 고침)
>
> 위 줄의 *"user_deleted 플래그 **+ 색인 제거**"*는 결정으로 적혀 있었고, [ADR-011](ADR-011-derivation-propagation.md)의 결정표가 그것을 *"검색 색인(event 복사본)은 즉시 제외"*로 못박았다. **구현이 그 결정과 달랐다.**
>
> 사실이 **바뀌는** 경로(`_invalidate_derived`)는 색인 복사본을 알아보고 `user_deleted=1`로 즉시 뺐다. 그런데 **유저가 부르는 `delete_item`에는 그 분기가 없어** 모든 파생물을 `stale`에만 넣었고, 읽기 경로(`retrieve()`·게이트 어휘)는 `stale`을 보지 않는다 — 둘 다 `user_deleted=0`만 본다.
>
> → **«바꾸면 빠지고, 지우면 남는다».** 지운 사실의 색인 문장이 **계속 검색되고 게이트를 발화시켰다.** 개인정보 삭제를 이걸로 만족했다고 말할 수 없는 상태가, *"만족한다"*고 적힌 채로 있었다.
>
> **고친 것은 결정이 아니라 배선이다.** `delete_item`이 `_invalidate_derived`를 재사용한다(사본 하나 줄었다 — F12). 시험은 [`prototype/tests/test_deletion.py`](../../prototype/tests/test_deletion.py) 11개이고, **고치기 전에 먼저 빨갛게 만든 뒤** 고쳤다. 「조용한 쪽」(안 지운 사실은 여전히 검색·발화된다)을 짝으로 건다 — 과잉 제거는 누수와 같은 크기의 결함이다.
>
> ⚠️ **여전히 참이 아닌 것:** L0 원본은 그대로 남는다(위 *"원문은 보존 여부를 유저가 선택"*). 그리고 `digest`·`interpretation`은 **stale 표시까지**이고 재생성 잡은 아직 없다(ADR-011 미해결).

### ③ 왜 유저 편집 표면이 필수인가 — 세 개의 독립적 이유

1. **심리적 안전.** *"기억을 선택적으로 지울 수 없다"*는 것 자체가 불안의 원인이다. 삭제 기능은 교정 수단이기 이전에 안전장치다
2. **자동은 반드시 틀린다.** 망각 정책에는 최적해가 없다(ADR-005). *"절대 안 틀리는 시스템"*을 만드는 건 불가능하고, **"틀렸을 때 고칠 수 있게 하는 것"이 압도적으로 싸다**
3. **지도 신호.** 유저가 핀을 꽂은 것 = "중요하다" 라벨, 지운 것 = 부정 신호, 노트에 적은 것 = 시스템이 놓친 것의 정답지. **유사도로는 잴 수 없는 효용(utility)의 유일한 지도 신호다**

시장 전원이 이미 이렇게 한다 — 유사 서비스 C의 자유 서술 기억·핀 십여 개·구조화 사실, 유사 서비스 B의 유저 메모 수백 자 → 수천 자, 유사 서비스 A의 프로필. 그리고 **메모리 용량은 이미 과금 상품**이다.

### ④ 음의 되먹임 — 이게 가장 위험하다

```
과잉 기억 → 감시받는 느낌 → 자기표현 억제 → 기억할 재료 고갈 → 기억 품질 하락
```

**과잉 기억이 기억의 원천을 고갈시킨다.** 이건 법적 리스크가 아니라 순수한 제품 리스크이고, 지표로 잡기도 어렵다(유저가 말을 안 하는 걸 어떻게 재는가). → `over_recall_discomfort`를 평가 지표에 넣은 이유다(ADR-009).

## 결과

**좋아지는 것**
- 민감 범주가 검색 가능한 프로파일이 되지 않는다
- 유저가 자기 기억을 통제할 수 있어 불안이 줄고, 그 편집이 시스템을 개선한다

**감수하는 것**
- 민감 범주를 안 쓰면 **그 영역의 기억 품질이 떨어진다.** 롤플레이 장르 특성상 이게 핵심 소재일 수 있다 — **정면으로 감수하는 트레이드오프다**
- 거부 목록이 과하면 정상적인 감정 대화까지 걸러진다

**새로 생기는 장애 지점**
- 민감 범주 판정을 추출기가 틀리면 어느 쪽으로든 사고가 난다 → **보수적으로(거부 쪽으로) 기울인다**
- 유저 삭제 요청이 파생 데이터 전체에 전파되어야 한다 → 삭제도 provenance를 타고 전파

## 재검토 트리거

- **법무 검토 결과** → 이 ADR 전면 재작성 가능
- 민감 범주 거부로 인한 품질 하락이 유저 불만 상위권에 오르면 → **명시적 동의를 받고 저장하는 옵트인** 검토
- 유저 삭제 요청 빈도가 높으면 → 자동 추출이 과하다는 신호. 추출 임계 상향
- 감시 불쾌감 지표가 개선 없이 유지되면 → 기억 주입량 자체를 줄이는 방향 재검토

- **③ 편집 표면 중 구현은 `relationship.user_locked` 하나다.** `event.user_pinned`는 읽기·쓰기 0이라 **«핀 = 항상 주입»이 없다**. `fact`에는 `user_locked`가 없다. `digest_meta.user_edited_at`을 쓰는 곳도 0이다([ADR-016](ADR-016-summary-layer.md) U7).
