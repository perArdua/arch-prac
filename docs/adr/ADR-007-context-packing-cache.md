# ADR-007: 컨텍스트 배치와 캐시 전략

- **상태:** 제안됨
- **일자:** 2026-09-03
- **관련:** ADR-002, ADR-006, ADR-008
- **근거 문서:** [03 FP-2](../03-architecture-modules.md), [05 §1](../05-cost-latency-reality.md), [07 A3](../07-assumptions-audit.md)

## 맥락

프롬프트 안에서 블록을 **어떤 순서로 놓을 것인가.** 이건 취향 문제로 보이지만 실제로는 **비용을 결정하는 수학**이다. 그리고 동시에 **품질(주목도)도 결정한다.**

캐시 히트는 입력 단가의 **10%**다. 접두사가 1토큰이라도 바뀌면 그 뒤가 전부 무효가 된다.

## 결정 동인

1. 캐시 적중률 (비용의 최대 45%를 좌우)
2. 주목도 (lost-in-the-middle 회피)
3. 시간 순서의 명료함

## 결정

> **블록을 "공유 범위 × 변경 빈도" 오름차순으로 배치한다.**

```
1. 시스템 프롬프트        전 유저 공통      변경 없음     ← 최대 공유
2. 페르소나·세계관·말투    캐릭터 전체 공통   버전 변경 시
3. 관계 상태 · 캐릭터 자기기억  이 방          느림
4. 씬 상태 · 부채           이 방            중간
5. 장기 요약 · 세션 요약     이 방            세션마다
6. 최근 10~15턴            이 방            append      ← append는 prefix 유지
7. 검색된 기억             이 방            매 턴 교체   ← 반드시 맨 뒤
8. 현재 발화
```

> ### 🔄 정렬 기준이 셋이다 — 프로토타입에서 추가 ([13 발견 2](../13-prototype.md))
>
> ```
> ① 공유 범위        전 유저 > 캐릭터 > 방
> ② 내용 변경 빈도    같은 블록의 내용이 얼마나 자주 바뀌나
> ③ 존재 변경 빈도    ⭐ 블록이 있다가 없어지나       ← 새로 발견
> ```
>
> **부채(L9)를 "결정적 주입"이라며 앞쪽에 뒀더니 접두사가 57%로 떨어졌다.**
> 백오프로 나타났다 사라질 때마다 **그 뒤 전부가 무효화**되기 때문이다.
>
> > **개념을 잘못 쓰고 있었다.** `결정적 주입 = "조건이 맞으면 반드시 들어간다"`이지 **"앞쪽에 놓는다"가 아니다.**
> > 존재 자체가 조건부인 블록은 **뒤쪽이 맞다** — 나타났다 사라져도 깨뜨릴 게 적고,
> > lost-in-the-middle상 **끝도 고주목 위치**라 손해가 없다.
>
> 뒤로 옮기자 **접두사 57% → 100%.**

> ### ⭐ 추가 결정 — 최근 턴 윈도우는 **청크 단위로 축출**한다
> ([11 §3](../11-experiment-results.md) 실측으로 추가된 항목)
>
> 슬라이딩 윈도우는 append가 아니다. 1턴씩 밀면 **앞에서 빠지는 evict**이고, evict는 접두사를 첫 토큰부터 깨뜨린다.
> ```
> 1턴 축출  : [T1..T10] → [T2..T11]   접두사 전멸, 매 턴
> 청크 축출 : [T1..T10] → append 9턴 → [T11..T20]   10턴 동안 안정
> ```
> **실측: 캐시 적중 49.6% → 78.6%, 입력 비용 $17.22 → $9.12 (47%↓).**
> **배치 순서 재정렬(29%↓)보다 큰 레버다.** 그리고 축출 로직 몇 줄이다.
>
> ⚠️ 대가: 윈도우 크기가 10~20턴 사이에서 출렁이고, 축출 직후 최근 맥락이 얇아진다. **품질 영향은 미측정.**
> ⚠️ 청크 크기를 키우려면 그 위 블록(`scene` 5턴 등)의 변경 주기도 함께 늘려야 한다 — 두 결정이 결합되어 있다.

## 근거 — 규칙이 수학에서 직접 나온다

**왜 캐시가 작동하는가 (5단계):**

1. 캐시 히트가 싼 이유는 **prefill 연산을 건너뛰기** 때문이다
2. 건너뛸 수 있는 이유는 각 토큰의 **Key/Value를 재사용**하기 때문이다
3. 재사용이 가능한 이유는 **인과 마스크(causal mask)** 때문이다 — 토큰 `i`는 `j ≤ i`만 볼 수 있으므로 위치 `i`의 K,V는 **앞쪽 토큰에만 의존**한다. 접두사가 같으면 그 구간의 K,V는 비트 단위로 동일하다
4. 1토큰만 바뀌어도 전부 무효인 이유는 두 가지다 — ① **의존성 전파**: 위치 `p`가 바뀌면 `q > p`인 모든 위치가 `p`를 attend하므로 K,V가 달라진다 ② **위치 인코딩**: RoPE는 절대 위치에 비례하는 각도로 회전시키므로, 삽입/삭제하면 뒤쪽 전체의 회전각이 밀린다
5. RoPE가 절대 위치를 쓰는 이유는 — 목표는 상대 위치지만, 내적이 `(m−n)`에만 의존하게 만들기 위해 **개별 벡터에는 절대 위치 회전**을 적용하기 때문이다

> **결론: `append`는 캐시를 유지하지만 `insert`는 파괴한다.** 이건 취향이 아니라 causal attention과 RoPE의 귀결이다.
> **→ 검색된 기억을 최근 대화 *앞*에 넣고 있다면, 그것만으로 캐시가 매 턴 전멸한다.** 코드 위치 한 줄 문제인데 비용 영향은 알고리즘 교체급이다.

**왜 "변경 빈도"가 아니라 "공유 범위 × 변경 빈도"인가:**

캐릭터는 **유저 간에 공유된다.** 인기 캐릭터 하나를 1만 명이 쓰면 `[시스템][페르소나][세계관]` ~900토큰은 **1만 명에게 동일한 접두사**다.

| | 유저 내 캐시 | **유저 간 캐시** |
|---|---|---|
| 적중 조건 | 같은 유저가 곧 다시 옴 | **누구든 같은 캐릭터를 쓰면 됨** |
| 세션 간 만료 | 몇 시간 쉬면 만료 | **인기 캐릭터는 사실상 상시 히트** |

이건 자체 서빙에서도 확인된다 — SGLang RadixAttention은 접두사 중복 60% 이상 워크로드에서 TTFT를 크게 줄이고, 대규모 사업자들이 **수백 대 GPU 간 KV Cache 공유**를 다음 목표로 잡고 있다.

**주목도와의 상충 — 다행히 같은 답을 가리킨다:**

lost-in-the-middle 때문에 정확도는 정보 위치에 대해 **U자 곡선**을 그리고, 중간이면 30% 이상 떨어진다. 구조적 원인은 **RoPE의 long-term decay**가 먼 토큰 쌍의 내적 유사도를 줄이고 **softmax가 이를 증폭**하는 것이다.

> **같은 RoPE가 두 곳에서 작동한다.** 절대 위치 회전 → 캐시 무효화를 결정, long-term decay → 주목도를 결정.
> **비용과 품질을 하나의 메커니즘이 지배하고, 배치가 두 축에 모두 걸린 유일한 결정이다.**
> 그리고 캐시 규칙(가변 블록은 맨 뒤)과 주목도 규칙(중요한 건 양 끝)이 **충돌하지 않고 같은 답**을 준다.

## 결과

**좋아지는 것**
- 캐시 적중률 상승으로 입력 비용이 최대 67% 감소 (실측 대상)
- 검색된 기억이 컨텍스트 끝에 있어 주목도도 높다

**감수하는 것**
- ⚠️ 검색된 기억이 **최근 대화보다 뒤**에 오면 시간 순서가 혼란스러울 수 있다. 명시적 라벨(*"[과거 기억]"*)로 완화하되, **실험으로 확인해야 한다**
- 캐시 최적화가 **신규·비인기 캐릭터에는 이득이 없다** → 롱테일 캐릭터가 구조적으로 비싸다 (ADR-008에서 다룸)

**측정 필수 항목:** `cache_hit_ratio`를 반드시 함께 리포트한다. 이게 없으면 비용 비교가 무의미하다.

## 재검토 트리거

- Provider가 명시적 캐시 breakpoint를 지원하면 → 수동 경계 설정으로 더 최적화 가능
- **Interactions API를 채택하면** → 그쪽은 explicit caching 미지원이라 이 전략과 배타적일 수 있다. 어느 쪽이 큰지 실측 후 재결정 (ADR-008)
- 시간 순서 혼란이 실측에서 확인되면 → 검색 기억을 최근 대화 *앞*으로 옮기고 캐시 손실을 감수

- **실제 블록 순서가 위 표와 다르다.** `build_context`의 volatility: system 0 · persona 1 · `speech_rules` 1 · `알고 있는 것` 2.5 · `relationship` 3 · digest lifetime 4 · session 5 · `scene` 7 · `recent` 8 · `debt` 8.5 · `retrieved` 9 · 발화 10. 위 표와 다른 곳: ① **씬이 요약 뒤**다(표는 앞) ② 부채가 최근 턴 뒤다(위 🔄 «정렬 기준이 셋» — 이미 적혀 있다) ③ `speech_rules`가 **맨 앞**이다 — [docs/06](../06-data-model.md) §L1은 «컨텍스트 끝쪽에 재주입»을 설계했고 그 효과를 재려던 실험 D1은 안 돌았다. 🔄 *(w24c · 2026-09-12 · Fable 검토 B-4 · R12 · R12b · 계획 «B-4»)* ④ **최근 턴 창과 직전 세션 요약이 같은 구간을 두 번 싣는다.** 세션 첫 턴 24번 중 23번 `recent` 창이 직전 세션의 턴을 담고(R12), 직전 세션 요약이 있는 세션 시작에서는 그 요약이 덮는 구간의 끝(`covers_to_seq`)이 정확히 그 턴이다(23/23 · R12b). 창은 청크 단위 축출(위 ⭐ 추가 결정 · 캐시)이고 `build_context`는 세션 경계를 `session_start` 불리언으로만 안다 — **규칙이 없다.** 오늘 소크·정밀도에는 `digest_session`이 비어 실제 중복은 0이고, 요약 층이 도는 제품 경로에서만 생긴다. 코드 0 — 규칙을 넣으면 `ctx.tokens`가 움직여 `digest_budget` 분포와 소크 토큰이 근거 없이 이동한다. 🔓 **열리는 조건:** `regen_job`을 부르는 실사용 호출자가 생기는 순간([ADR-016](ADR-016-summary-layer.md) U8). 🔄 *(w33k · 2026-09-12 · 마감 K · Fable 계획 2 N6)* **요약 층이 돌면 lifetime × 최신 세션 블록의 중복은 둘째 경계부터 늘 있다** — lifetime은 세션 요약 전량(K = N)을 재료로 쓰므로 최신 세션 요약의 본문을 품고, 세션 블록(M = 1)이 같은 본문을 또 싣는다 · 크기 = 최신 M개 세션 요약 본문. 첫 lifetime 문턱(Q3 · M+1)이 없애는 것은 **첫 경계의** 중복뿐이다(같은 문장이 regen_job 문턱 주석 줄 끝 · ADR-016 U8 행 끝 w31i). 규칙이 없다는 위 판단과 열리는 조건은 그대로다.
