## 1. 문제 진술 (한 문장)

> 유저 1인당 대화 턴이 수천~수만으로 누적되는 캐릭터 롤플레이 서비스에서,
> **응답 1회당 컨텍스트를 상수 크기로 유계(bounded)하면서도**
> 과거 사건·관계·발언의 회상 정확도를 유지하고, 특히 **낡은 사실 재생과 없던 사건 날조를 억제**하는
> 메모리 구조를 결정한다.

### 1.1 성공 기준 (이 숫자를 못 맞추면 실패)

| 항목 | 목표 | 근거 |
|---|---|---|
| 컨텍스트 크기 | 턴 수 N과 **무관한 상수** | `O(N²)` 비용 붕괴 회피 |
| 회상 정확도 | **Full-context baseline의 95% 이상** | 품질 손실 상한 |
| Stale-fact rate | **Full-context baseline 이하** | 몰입 파괴 방지 |
| Hallucination rate (abstention) | **Full-context baseline 이하** | 없던 사건 날조 방지 |
| TTFT p95 | **최근 N턴만 쓰는 baseline 대비 +300ms 이내** | 롤플레이 체감 지연 |
| 턴당 비용 | Full-context 대비 **1/10 이하** | 무료 유저 원가 |

> 핵심 트릭: **정확도는 Full-context를, 지연은 Window-only를 기준선으로 잡는다.** 서로 다른 기준선을 쓰는 이유는, 이 둘이 각각 두 축의 실질적 상한/하한이기 때문이다.

### 1.2 범위 밖 (명시적으로 안 함)

- 프로덕션 수준 구현, 멀티테넌시, 인증, 스케일 테스트
- 멀티모달(이미지/음성) 메모리
- 모델 파인튜닝 / 파라메트릭 메모리
- 유저 간 공유 메모리(월드 상태)

→ ADR에 "지금은 안 하지만 언제 필요해지는가"로 기록한다.

## 2. 가설 (실험으로 참/거짓을 가릴 것)

각 가설은 **반증 가능한 형태**로 쓴다. "좋아질 것이다"가 아니라 "X 지표가 Y 이상 차이날 것이다".

### H1 — 캐시 레이아웃 가설 ⭐ 최우선

> **주장:** 메모리 알고리즘을 바꾸는 것보다, 프롬프트 안에서 **가변 블록을 뒤로 미는 것**만으로 턴당 비용이 더 크게 떨어진다.
>
> **구체:** 동일한 메모리 내용을 넣더라도
> `[persona][검색결과][최근턴]` (가변 블록이 앞) 배치 대비
> `[persona][안정 프로필][최근턴][이번 턴 검색결과]` (가변 블록이 뒤) 배치가
> **캐시 적중 토큰 비율을 2배 이상 높이고 턴당 비용을 40% 이상 낮춘다.**
>
> **반증 조건:** 비용 차이가 15% 미만이면 H1 기각. → 캐시는 부차적 변수로 강등하고 알고리즘에 집중.

*왜 중요한가:* 사실이라면 "현재 구조에서 코드 20줄만 바꿔도 비용이 반이 됩니다"라는, 당장 적용 가능한 결론이 나온다.

### H2 — Selector 비용 가설

> **주장:** 응답 경로의 LLM Selector는 TTFT의 지배적 요인이며, **크로스인코더 리랭커 또는 룰 기반 스코어링으로 대체해도 회상 정확도 손실이 3%p 미만**이다.
>
> **반증 조건:** 정확도 손실이 5%p 이상이면 H2 기각 → Selector는 값을 한다.

### H3 — 검색 게이팅 가설

> **주장:** 실제로 장기기억 검색이 필요한 턴은 **전체의 30% 미만**이다. 값싼 게이트(룰 + 소형 분류기)로 나머지를 걸러도 회상 정확도는 유지되면서 평균 TTFT와 비용이 유의미하게 개선된다.
>
> **반증 조건:** 게이팅 도입 시 회상 정확도가 3%p 이상 하락하거나, 검색 필요 턴 비율이 60%를 넘으면 기각.

### H4 — 모순 관리 가설

> **주장:** 사실을 **누적만** 하는 저장소는 갱신 시나리오에서 stale-fact를 재생한다. 명시적 무효화(invalidation)를 넣으면 **stale-fact rate가 절반 이하**로 떨어진다.
> 단, 이를 위해 **풀 지식그래프까지는 필요 없고**, `(주어, 속성, 값, valid_from, valid_until)` 수준의 bi-temporal 레코드면 충분하다.
>
> **반증 조건:** bi-temporal 레코드로 stale-fact rate가 절반으로 안 떨어지면 → 그래프 구조 재검토 필요.

### H5 — 단순함 가설 ⭐ 이 검토의 지적 승부처

> **주장:** [MemDelta](https://arxiv.org/pdf/2606.29914)의 지적대로, **동일 토큰 예산에서 통제**하면 정교한 메모리 시스템과 단순 baseline(최근 N턴 + 롤링 요약)의 회상 정확도 차이는 통설보다 훨씬 작다.
> 차이가 실제로 크게 벌어지는 곳은 **multi-session 추론 / temporal / knowledge-update 유형에 국한**된다.
>
> **반증 조건:** 모든 질문 유형에서 정교한 시스템이 baseline을 일관되게 5%p 이상 앞서면 기각.

*왜 중요한가:* 참이면 결론이 "복잡도를 어디에만 지불할 것인가"로 정교해진다. 거짓이어도 "우리 도메인에서는 복잡도가 값을 한다"는 강한 근거가 된다. **어느 쪽이든 답변이 강해지는 유일한 가설.**

### H6 — Provider 네이티브 상태 가설

> **주장:** Gemini Interactions API의 `previous_interaction_id`는 **전송 페이로드**를 줄여줄 뿐, **과금 입력 토큰**은 여전히 히스토리 전체에 비례한다. 즉 `O(N²)` 문제를 해결하지 못한다.
>
> **반증 조건:** `usage` 필드 실측에서 과금 입력 토큰이 턴 수에 비례하지 않으면 기각 → 이 경우 대단히 중요한 발견이므로 별도 ADR로 승격.

*상태:* 공식 문서에 명시 없음. **실측만이 답.** (키 확보 후 최우선 실험)

## 3. 비교 대상 (Arms)

동일 조건에서 나란히 돌릴 방식들. **모두 동일 토큰 예산 / 동일 생성 모델 / 동일 시드.**

| ID | 이름 | 설명 | 역할 |
|---|---|---|---|
| `A0` | **Full-context** | 전체 히스토리 삽입 | 정확도 **상한** 기준선 (비용 상한이기도) |
| `A1` | **Oracle retrieval** | 정답 근거 턴만 삽입 (컨닝) | **이론적 상한** — 개선 여지의 크기를 잰다 |
| `A2` | **Window-only** | 최근 N턴만 | 지연/비용 **하한** 기준선 |
| `A3` | **Random-K** | 무작위 K개 검색 | **위생 검사** — 이걸 못 이기면 검색이 작동 안 하는 것 |
| `B1` | **Window + rolling summary** | 최근 N턴 + 누적 요약 | 현실적 최소 baseline ⭐ |
| `C1` | **Vector RAG (세션 단위)** | 세션 청크 임베딩 top-k | 순진한 RAG |
| `C2` | **Vector RAG (라운드 단위 + 키 확장)** | 턴 단위 + 추출사실을 임베딩 키로 | LongMemEval 권고 반영 |
| `D1` | **사실 저장소 (누적형)** | 추출 사실 누적, 무효화 없음 | H4 비교군 |
| `D2` | **사실 저장소 (bi-temporal)** | `valid_from/until` 무효화 포함 | H4 실험군 |
| `E1` | **문서형 메모리** | 유저당 유계 프로필 문서 1개 | H1·H5 실험군 |
| `F1` | **하이브리드 (제안안)** | 문서형 + bi-temporal 사실 + 게이팅된 이벤트 검색 | **최종 후보** |
| `G1` | **현재 구조 재현** | 계층 메모리 + RAG + LLM Selector | 현행 기준선 대조군 ⭐ |

> `G1`을 반드시 넣는다. **"현재 방식 대비"**가 원래 질문이 명시적으로 요구한 비교축이다.

**축소 시 우선순위:** 시간이 부족하면 `C1`, `D1`을 먼저 뺀다(각각 `C2`, `D2`의 열등 변형). `A0/A1/A2/A3/B1/C2/D2/E1/F1/G1`이 최소 세트.

## 4. 데이터셋 설계

### 4.1 왜 자체 생성인가

LoCoMo(~16K토큰)는 2026년 기준 그냥 컨텍스트에 다 들어가서 변별력이 없고, LongMemEval은 영어 어시스턴트 대화다. 이 도메인은 **한국어 × 롤플레이 × 감정/관계**다. 둘 다 쓰되 **자체 데이터가 주(主)**여야 한다.

### 4.2 자체 데이터 스펙

```
캐릭터: 2명 (성격 대비되게 — 예: 츤데레형 / 다정형)
유저 페르소나: 캐릭터당 1명
세션: 40세션 × 평균 50턴 = 캐릭터당 2,000턴
기간: 6개월치 타임스탬프 (시간 추론 질문을 위해 필수)
언어: 한국어
```

**생성 방식 — 역방향 생성(reverse generation)이 핵심:**

먼저 **사실 대장(fact ledger)**을 설계하고, 그 다음 대화를 생성한다. 순서를 반대로 하면 ground truth를 나중에 라벨링해야 해서 부정확해진다.

```yaml
# fact_ledger.yaml (먼저 작성)
- id: F001
  fact: "유저의 고양이 이름은 나비"
  introduced_at: {session: 3, turn: 12}
  status: valid
- id: F002
  fact: "유저는 마케팅 회사에 다님"
  introduced_at: {session: 1, turn: 5}
  invalidated_at: {session: 22, turn: 8}   # 이직
  superseded_by: F017
- id: F017
  fact: "유저는 스타트업으로 이직함"
  introduced_at: {session: 22, turn: 8}
- id: E004
  type: event
  fact: "유저가 반려묘를 떠나보냄"
  introduced_at: {session: 31, turn: 20}
  emotional_weight: high
```

그 다음 LLM에 "F001을 3세션 12턴에서 자연스럽게 언급하는 대화를 써라"라고 지시해 생성. → **근거 위치가 정확히 알려진 데이터**가 나온다. 이게 `A1 Oracle` arm과 유형별 채점을 가능하게 한다.

**의도적으로 심을 것:**
- 갱신되는 사실 (직업, 거주지, 관계 상태) → knowledge-update 질문용
- 여러 세션에 흩어진 근거 → multi-session 질문용
- 감정적 사건 (이별, 사별, 합격) → 롤플레이 특유의 회상 대상
- 사소한 잡담 대량 (노이즈 60% 이상) → 검색 난이도 확보
- **한 번도 언급 안 된 주제** → abstention 질문용

### 4.3 평가 질문 세트 (60문항, 유형 균등)

| 유형 | 문항 | 채점 |
|---|---|---|
| Single-hop 회상 | 12 | 정답 문자열/의미 일치 |
| Multi-session 추론 | 12 | 정답 일치 |
| Temporal | 12 | 정답 일치 (허용 오차 명시) |
| **Knowledge update** | 12 | **신 사실 = 정답 / 구 사실 언급 = stale** |
| **Abstention** | 12 | **"모른다/기억 안 남" = 정답 / 구체적 서술 = hallucination** |

각 문항에 `gold_answer`, `gold_evidence_turns`, `distractor_answer`(stale용) 를 붙인다.

> ⚠️ 롤플레이 특성상 질문은 **캐릭터에게 자연스럽게 묻는 형태**여야 한다. "F001의 값은?"이 아니라 "야 근데 우리 고양이 이름이 뭐였더라?" 형태. 그래야 실제 서비스 조건과 같다.

### 4.4 공개 벤치마크 병행

`longmemeval_s_cleaned.json`(~500문항 / 히스토리 115K토큰)에서 **100문항 서브셋**만 돌린다. 목적은 순위 경쟁이 아니라 **"우리 하네스가 공개 벤치마크에서도 상식적인 값을 낸다"는 sanity check**. ⚠️ 원본 `longmemeval`은 deprecated — `longmemeval-cleaned` 사용.

## 5. 측정 프로토콜

### 5.1 통제 조건 (MemDelta 교훈 반영)

| 변수 | 고정값 |
|---|---|
| 컨텍스트 토큰 예산 | **4,000 토큰 (전 arm 동일)** — `A0` 제외 |
| 생성 모델 | 전 arm 동일 (예: Gemini 3.x Flash) |
| temperature / seed | 고정 |
| 최근 턴 수 N | 동일 (예: 10턴) |
| 심판 모델 | 고정, arm 정보 비공개(blind) |
| 반복 | arm × 문항당 3회, 평균 + 표준편차 보고 |

> **동일 토큰 예산이 전부다.** 예산을 안 맞추면 "더 많이 넣은 쪽이 이겼다"는 자명한 결과만 나온다. 이 통제를 문서에 명시하는 것만으로 비교의 신뢰도가 달라진다.

### 5.2 지표 정의

```python
# 품질
quality_score      # LLM-as-judge 1~5 (캐릭터 일관성/자연스러움/맥락적합성)

# 기억 정확도
recall_accuracy    # 유형별 정답률
stale_fact_rate    # knowledge-update 문항 중 구 사실을 답한 비율   ↓
hallucination_rate # abstention 문항 중 구체적 서술을 지어낸 비율   ↓
evidence_recall@k  # gold_evidence_turns 중 실제 검색된 비율 (검색기 단독 평가)

# 비용 (턴당)
tokens_in_uncached, tokens_in_cached, tokens_out
cache_hit_ratio    # = tokens_in_cached / tokens_in_total     ⭐ H1의 핵심 지표
cost_per_turn_usd  # write path 상각 + 임베딩 + 인프라 포함
cost_per_1k_turns_usd

# 지연
ttft_ms            # p50 / p95 / p99   ⭐ 롤플레이 체감 지표
total_ms
# 단계별 분해:
gate_ms, retrieve_ms, rerank_ms, select_ms, pack_ms, model_ttft_ms
```

**비용 공식 (write path 상각 포함 — 이걸 빼면 사실 저장소 방식이 부당하게 유리해진다):**

```
cost_per_turn =
    tokens_in_uncached × price_in
  + tokens_in_cached   × price_in × 0.1
  + tokens_out         × price_out
  + (write_path_cost_per_session × batch_discount) / turns_per_session
  + embedding_tokens   × price_embed
  + infra_fixed_cost_monthly / (MAU × avg_turns_per_user)
```

### 5.3 리포트 형태

각 arm에 대해 **한 줄**:

| Arm | 품질 | 회상 | Stale↓ | Halluc↓ | 캐시적중 | $/1k턴 | TTFT p95 | 복잡도 |
|---|---|---|---|---|---|---|---|---|

그리고 반드시 **2차원 산점도 2장**:
1. `회상 정확도 × $/1k턴` (파레토 프론티어를 그린다)
2. `회상 정확도 × TTFT p95`

> 파레토 프론티어 위에 있는 arm만 후보다. 나머지는 "다른 arm이 모든 면에서 더 낫다"로 탈락시킨다. 이 그림 한 장이 리포트의 핵심 슬라이드가 된다.

## 6. 키 없이 시작하는 전략 (2단계 실행)

키가 아직 없으므로 하네스를 **provider-agnostic**하게 짜고, 두 모드를 지원한다.

**Phase 1 — 키 없이 (지금 바로 가능한 것)**
- 더미 대화·질문 세트 생성 (템플릿 + 규칙 기반 + 사실 대장 기반 조립)
- 임베딩: **로컬 다국어 모델** (`BAAI/bge-m3` 또는 `intfloat/multilingual-e5-large`) — 한국어 지원, GPU 없어도 CPU로 2,000턴 처리 가능, **비용 0**
- 벡터 검색: **Qdrant (docker)** — 실제 운영 구조 재현
- 측정 가능한 것: **`evidence_recall@k` (검색기 품질), 토큰 카운트, 캐시 적중률 시뮬레이션, 검색/리랭크 지연** → **H1·H3의 상당 부분이 여기서 이미 검증된다**
- 측정 불가: 응답 품질, stale/hallucination rate, 실제 TTFT

**Phase 2 — 키 확보 후**
- 위에서 만든 컨텍스트를 그대로 모델에 태워 품질·지연·실비용 측정
- H2·H4·H5·H6 검증

### 6.1 키 구매 권고

| 우선순위 | 무엇 | 왜 | 예상 비용 |
|---|---|---|---|
| **1순위** | **Gemini API** | 원래 질문이 언급한 축(Interactions API / Batch / context caching)이 전부 여기 있음. **H6는 Gemini 키 없이는 검증 불가**이고, 이게 검증되면 리포트의 유니크한 발견이 됨. | **$30~60** |
| 2순위 | (선택) OpenAI 또는 Anthropic | LLM-as-judge를 생성 모델과 **다른 벤더**로 두면 자기편향이 줄어 평가 신뢰도가 올라감 | $5~15 |
| 불필요 | 임베딩 API | 로컬 다국어 모델로 충분하고 한국어에서 더 나을 수도 있음 | $0 |

**$30~60 산출 근거** (Gemini Flash 기준, 단가는 ⚠️ 공식 페이지 재확인 필요):
- 더미 대화 생성 2,000턴 × 2캐릭터 ≈ 100만 출력 토큰 → **~$4**
- 평가 실행: 60문항 × 10 arm × 3회 = 1,800콜 × 평균 4K입력 = 7.2M 입력 토큰 → **~$6**
- `A0 Full-context` arm: 히스토리 200K토큰 × 60문항 × 1회(반복 축소) = 12M 입력 → **~$9** ← *가장 비싼 항목*
- LLM-as-judge 1,800회 → **~$2**
- write path(사실 추출·요약) 배치 → **~$2**
- 재실행/시행착오 여유 2배 → **총 $30~50**

> **비용 방어책:** `A0 Full-context`는 반복 1회로 줄이고, 히스토리를 500턴 서브셋으로 별도 측정해 **외삽 곡선**을 그린다. (어차피 `O(N²)`를 보여주는 게 목적이므로 500/1000/2000턴 3점만 실측하면 곡선이 나온다.) 이것만으로 $9 → $2.
